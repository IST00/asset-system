# 资产系统建设方案

## 1. 项目背景

本系统用于公司内部资产管理。公司约 400 人使用，资产数量预计超过 5000 个，同时在线使用人数预计 30 到 50 人。

系统先在本地运行，后续部署到公司内网服务器，并计划集成到飞书中使用。

## 2. 已确认需求

### 2.1 使用范围

- 使用场景：公司内部资产管理
- 用户规模：约 400 人
- 并发规模：约 30 到 50 人
- 资产规模：5000 个以上
- 系统类型：Web 系统
- 客户端范围：响应式 Web，不开发 iOS 或 Android 原生 App
- 网络要求：第一版不支持离线盘点，扫码和提交时必须能够访问系统
- 系统语言：第一版仅简体中文
- 金额币种：第一版仅人民币，不做多币种和汇率换算
- 初期部署：本地运行
- 正式部署：公司内网服务器
- 后续集成：飞书应用或飞书工作台

### 2.2 核心能力

- 飞书单点登录
- 权限管理
- 所有资产操作都需要审批
- 审批流程集成飞书审批
- Excel 导入导出
- 二维码资产标签
- 条形码资产标签
- 操作日志
- 审计记录

## 3. 技术方案

### 3.1 后端技术

- 开发语言：Python 3.12
- 后端框架：FastAPI
- 数据库：MySQL 8.4 LTS，兼容公司已有 MySQL 8.0
- 数据库字符集：utf8mb4
- Redis：Redis 7
- ORM：SQLAlchemy
- 数据库迁移：Alembic
- 数据校验：Pydantic
- 鉴权方式：本地开发账号使用 JWT；第一版正式使用前接入飞书单点登录
- Excel 处理：openpyxl
- 二维码生成：qrcode
- 条形码生成：python-barcode
- 飞书接口调用：httpx
- Python 依赖版本写入锁定文件，升级时统一测试后调整。

### 3.2 后端分层架构

后端采用分层结构，避免把所有代码都写在一个文件里，方便后续维护和扩展。

```text
请求进入系统
  -> 路由层 routes
  -> controller 层
  -> service 实现层
  -> repository 数据层
  -> MySQL 数据库
```

各层职责如下：

| 层级 | 职责 |
| --- | --- |
| 路由层 | 定义接口地址，例如新增资产、查询资产、发起审批 |
| Controller 层 | 接收请求，调用业务服务，组织返回结果 |
| Service 实现层 | 写核心业务逻辑，例如资产领用、归还、报废、审批通过后变更资产状态 |
| Repository 数据层 | 专门负责数据库增删改查 |
| Model 层 | 定义数据库表结构 |
| Schema 层 | 定义接口请求参数和返回数据格式 |
| Middleware 中间件 | 处理日志、登录鉴权等通用逻辑 |

### 3.3 前端技术

确认结果：前端使用 `Vue 3 + TypeScript + Vite + Naive UI`。

- Node.js：22 LTS。

- Vue 3：负责构建资产台账、审批、盘点和权限管理等页面。
- TypeScript：为前端数据增加类型检查，减少字段写错和接口使用错误。
- Vite：负责本地启动和正式打包，提高开发速度。
- Naive UI：提供表格、表单、弹窗、树形选择、分页和提示等后台管理组件。
- Vue Router：负责页面地址和菜单跳转。
- Pinia：负责保存登录用户、权限、字典等前端公共状态。
- 前端需要支持响应式布局，同一套系统可以在电脑和手机浏览器中使用。
- 资产台账、权限管理等复杂页面以电脑端为主；扫码盘点、资产详情和退库等页面单独优化手机操作体验。

专业词解释：UI 组件库是一套现成的页面零件，例如按钮、表格和输入框。响应式布局表示页面会根据屏幕大小自动调整。Naive UI 主要提供页面组件，手机扫码页面仍需要根据业务单独设计，不能直接把电脑端的大表格缩小后使用。

浏览器兼容范围：

- 电脑端支持新版 Chrome 和 Edge。
- 手机端支持飞书内置浏览器、iPhone Safari 和主流 Android 浏览器。
- 不支持 Internet Explorer。

### 3.4 接口、配置和时间规范

- 后端接口统一使用 `/api/v1` 前缀。
- 正常和错误响应统一包含 `code`、`message`、`data` 和 `request_id`。
- 开发、测试和正式环境使用不同配置文件和数据库。
- 数据库密码、飞书密钥、JWT 密钥等敏感配置只放在环境变量或服务器密钥文件中，不提交到 Git。
- 数据库统一保存 UTC 时间，前端页面、Excel 和报表统一按 `Asia/Shanghai` 北京时间显示。

统一响应示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "req_202607170001"
}
```

专业词解释：API 版本用于保护接口兼容性；统一时区可以避免不同服务器和浏览器造成时间顺序错误。

## 5. 中间件设计

### 5.1 日志中间件

日志中间件用于记录每一次接口访问，方便以后排查问题和做审计。

建议记录内容：

- 请求 ID
- 请求方法
- 请求地址
- 客户端 IP
- 当前用户 ID
- 响应状态码
- 请求耗时
- 异常信息

示例：

```json
{
  "request_id": "req_20260604123456789",
  "method": "POST",
  "path": "/api/v1/assets",
  "user_id": 12,
  "status_code": 200,
  "duration_ms": 43
}
```

日志保留规则：

- 资产履历、审批记录、权限变更记录永久保留。
- 登录日志和安全相关日志保留 1 年。
- 普通接口访问日志和系统运行日志保留 180 天。
- 到期日志由系统定期清理，清理任务需要记录执行时间、数量和结果。
- 日志保留期限只影响日志数据，不删除资产、申请、盘点和附件等业务数据。
- 密码、飞书 App Secret、登录令牌、回调密钥和附件内容不能写入日志。
- 手机号等个人敏感字段在日志和后台查看页面中只显示部分内容。
- 日志中间件需要对请求参数和响应内容执行脱敏后再记录。

专业词解释：日志保留策略按照记录重要程度设置保存时间，永久审计记录不会被普通日志清理任务删除。

### 5.2 鉴权中间件

鉴权中间件用于判断用户是否已经登录。

职责：

- 从请求头读取 token
- 校验 token 是否有效
- 识别当前登录用户
- 放行不需要登录的接口
- 登录会话最长有效 8 小时，连续 2 小时无操作则失效。
- 飞书用户会话失效后重新进行飞书身份认证，本地超级管理员重新输入密码。
- 用户被停用或离职后，已有登录会话立即失效。

本地管理员账号安全规则：

- 密码至少 12 位，并包含大写字母、小写字母、数字和符号。
- 首次登录必须修改初始化密码。
- 新密码不能与最近 5 次密码相同。
- 同一账号连续登录失败 5 次后锁定 15 分钟，锁定和解锁记录安全日志。
- 正式员工只使用飞书登录，不在资产系统中设置或重置本地密码。
- 本地超级管理员忘记密码时，通过登录内网服务器执行专用管理命令重置。

接口安全规则：

- 登录接口同一 IP 每分钟最多请求 10 次。
- 普通接口同一登录用户每分钟最多请求 120 次。
- 超出限制时返回统一错误提示和 `request_id`，不继续执行业务。
- 正式环境 CORS 白名单只允许公司内网正式域名，本地开发允许 `localhost`。

专业词解释：防暴力破解用于限制连续猜测密码；接口限流用于阻止短时间异常大量请求；CORS 白名单用于限制可调用后端的网页来源。

不需要登录的接口示例：

```text
/api/v1/auth/login
/api/v1/auth/feishu/callback
/api/v1/feishu/approval/callback
/api/v1/health
/docs
/openapi.json
```

## 6. 权限设计

系统采用 RBAC 权限模型，并增加数据权限。系统需要支持全量权限自定义，可以在权限管理中配置角色、权限和数据范围。

### 6.1 角色建议

系统内置默认角色，同时支持管理员自定义角色。

默认角色：

- 超级管理员
- 系统管理员
- 资产管理员
- 部门资产管理员
- 部门负责人
- 普通员工
- 财务人员
- 审计只读人员

自定义角色能力：

- 新增角色
- 编辑角色
- 删除角色，系统内置角色可禁止删除
- 给角色分配菜单权限
- 给角色分配按钮权限
- 给角色分配接口权限
- 给角色分配数据权限范围
- 给用户分配一个或多个角色

### 6.2 权限示例

```text

asset:amount:update

asset:export
```

### 6.3 数据权限范围

```text
ALL              全公司
DEPARTMENT       当前部门
DEPARTMENT_TREE  当前部门及下级部门
SELF             仅本人
CUSTOM           自定义部门范围
```

默认权限规则：

- 普通员工：默认只能查看自己名下资产。
- 资产管理员：默认可以查看全公司资产。
- 超级管理员：默认可以查看和管理全部数据。
- 其它角色：由超级管理员在权限管理中自定义配置。

权限变更审计规则：

- 超级管理员新增角色、修改角色权限或调整用户角色不需要审批。
- 保存前必须填写变更原因并进行二次确认。
- 系统永久保存修改前权限、修改后权限、操作人、时间、原因和受影响用户。
- 权限变更记录不能编辑或删除。

专业词解释：权限审计用于还原谁在什么时候给哪个角色或用户增加、取消了什么权限。

## 7. 审批设计

系统原则：资产操作先生成申请单，审批或确认完成后才真正修改资产数据。

标准流程：

```text
用户发起操作
  -> 系统生成申请单
  -> 根据操作类型进入飞书流程或系统内部流程
  -> 审批或确认完成
  -> 系统执行资产变更
  -> 写入资产生命周期记录
  -> 写入操作日志
```

流程处理方式：

- 领用：接入飞书审批或飞书确认。
- 退库：接入飞书审批或飞书确认。
- 其它操作：在资产系统内部完成审批、确认和记录。

申请人与审批人分离规则：

- 本地开发阶段只有超级管理员时，允许超级管理员提交并确认自己的申请，方便功能测试和初始化数据。
- 正式使用后，报废、批量导入、盘点结果确认等重要操作，申请人不能审批自己提交的申请。
- 新增资产入库属于明确例外：提交人同时拥有入库审批权限时，可以审批自己提交的入库申请。
- 系统按操作类型提供“是否允许申请人自审”的配置开关。
- 没有自审权限时，审批按钮不向申请人显示，后端接口也必须再次校验，避免绕过页面直接审批。
- 审批记录需要保存申请人、审批人、审批时间、审批结果和审批意见。

专业词解释：职责分离是指提交申请和批准申请由不同的人完成。前端隐藏按钮只能改善操作体验，后端校验才是真正的权限保护。

审批拒绝规则：

- 审批人拒绝申请时必须填写拒绝原因。
- 申请被拒绝后，不修改资产台账、资产状态、使用人、存放地点等正式数据。
- 申请人可以根据拒绝原因修改申请内容后重新提交。
- 重新提交时生成新一轮审批记录，并关联原申请，便于查看完整过程。
- 原来的申请内容、审批意见和拒绝记录永久保留，不能直接修改或删除。
- 拒绝和重新提交都要写入操作日志；涉及具体资产时，还要在资产履历中显示。

专业词解释：审批留痕是指系统永久保存每次提交、审批、拒绝和重新提交的过程，方便以后查询责任和还原事情经过。

审批撤回规则：

- 申请尚未审批完成时，申请人可以主动撤回。
- 系统内部申请在资产系统中撤回。
- 领用、退库等飞书申请在飞书中撤回，飞书通过回调通知资产系统同步为“已撤回”。
- 已审批完成并且已经修改资产正式数据的申请不能直接撤回。
- 已执行的业务需要通过对应的正常流程处理，例如已完成领用后需要走退库流程，不能用撤回恢复。
- 撤回时保存撤回人、撤回时间和撤回原因，原申请和已有审批记录继续保留。
- 飞书重复发送撤回通知时，系统只能处理一次，避免重复写入资产履历或操作日志。

专业词解释：状态同步是指飞书里的审批状态发生变化后，资产系统自动更新为相同状态。回调是飞书主动发送给资产系统的一条状态通知。

审批催办规则：

- 系统不做自动审批提醒，不按照等待时长自动发送消息。
- 待审批申请保留“催办”能力，由有权限的人员主动发起。
- 申请人可以催办自己提交且仍在等待审批的申请。
- 超级管理员和审批管理员可以催办全部待审批申请。
- 自定义角色是否可以催办，由角色权限配置决定。
- 没有催办权限的人员不显示催办按钮，后端接口同时校验催办权限和数据范围。
- 同一个申请对同一个当前审批人，每 1 小时最多催办一次。
- 未满 1 小时再次催办时，系统提示“已经催办，请稍后再试”，不重复发送通知。
- 催办频率限制由后端执行，避免绕过页面重复调用接口。
- 催办只通知当前审批人，不会自动通过、拒绝或修改资产数据。
- 系统内部审批的催办记录保存在资产系统中。
- 领用、退库等飞书审批在飞书审批单中进行催办。
- 每次催办需要记录催办人、催办时间、对应申请和当前审批人。

催办权限编码建议：

```text
approval:urge
```

专业词解释：自动提醒是系统到达设定时间后主动发消息；催办是用户手动点击按钮，提醒当前审批人尽快处理。

审批转交规则：

- 当审批人请假、离职或选择错误时，待审批任务可以转交给另一位有相应审批权限的人员。
- 系统内部审批由超级管理员或审批管理员执行转交。
- 转交时必须填写转交原因。
- 转交完成后，原审批人失去该申请的处理权限，新审批人成为当前审批人。
- 飞书审批在飞书中完成转交，资产系统通过飞书回调同步当前审批人和审批状态。
- 转交不会新建业务申请，也不会修改资产正式数据。
- 系统永久保存原审批人、新审批人、转交操作人、转交时间和转交原因。
- 转交操作写入系统操作日志；涉及具体资产时同步显示在资产履历中。

专业词解释：审批转交是把尚未处理的审批任务交给另一位审批人，原申请内容和编号保持不变。

多层审批规则：

- 系统内部审批支持按照操作类型配置一层或多层审批。
- 每一层可以指定具体用户，也可以指定角色作为审批人来源。
- 审批按照层级顺序执行，前一层通过后，下一层才能开始处理。
- 任意一层拒绝后，整个申请变为“已拒绝”，后续层级不再继续。
- 所有层级都通过后，系统才执行资产新增、编辑、转移、维修、报废、导入或盘点结果变更。
- 审批流程配置修改后只对新申请生效，已经提交的申请继续使用提交时保存的流程，避免审批过程中人员和规则突然变化。
- 领用和退库继续使用飞书中配置的审批或确认流程，资产系统同步审批结果。

内部审批示例：

```text
报废申请
  -> 第 1 层：资产管理员审批
  -> 第 2 层：财务人员审批
  -> 全部通过后：资产状态变为已报废
```

专业词解释：多层顺序审批是指申请按设定顺序逐层确认。流程快照是提交申请时保存一份当时的审批规则，之后修改流程配置不会影响正在审批的旧申请。

同层多人审批规则：

- 每个审批层级可以单独选择“或签”或“会签”。
- 或签：同一层多名审批人中任意一人通过，这一层即为通过，其余人员的待审批任务自动结束。
- 会签：同一层所有审批人都通过，这一层才为通过。
- 会签过程中任意一人拒绝，该层立即拒绝，整个申请结束，后续审批人不再处理。
- 默认审批方式为或签；需要多人共同负责的重要操作可以改为会签。
- 系统需要记录每位审批人的处理结果、处理时间和审批意见。

审批方式编码建议：

```text
OR_SIGN   或签，任意一人通过
AND_SIGN  会签，所有人员通过
```

专业词解释：或签适合由同一岗位中的任意一人处理；会签适合必须由多名负责人共同确认的业务。

按角色确定审批人规则：

- 审批层可以指定某个具体用户，也可以指定某个角色。
- 指定角色时，系统在提交申请的当下，查找该角色下符合所属公司、数据权限且账号有效的人员。
- 系统将查到的具体人员保存为本次申请的审批人名单，也就是审批人快照。
- 申请提交后，角色成员新增、移除、停用或数据权限变化，不自动改变已经生成的审批人名单。
- 已有申请需要更换审批人时，使用审批转交功能并保留转交记录。
- 如果提交时某一层找不到符合条件的审批人，系统禁止提交，并明确提示缺少审批人员和对应层级。
- 停用审批流程或修改角色配置前，系统需要提示是否存在尚未完成的审批，但不能直接删除历史审批记录。

专业词解释：审批人快照是指提交申请时把本次实际审批人员名单固定并保存下来。数据权限用于避免其他公司的角色成员审批不属于自己管理范围的资产。

批量申请和整单审批规则：

- 一张领用、退库、转移、维修或报废申请可以包含多件资产。
- 选择主资产时，系统自动带出其附属资产，主资产和附属资产作为同一批次处理。
- 同一张申请中的资产必须使用相同的业务参数，例如转移给同一个使用人、同一个地点，或进入同一次维修。
- 审批人对整张申请统一通过或拒绝，第一版不支持只批准其中部分资产。
- 提交前系统逐件检查资产状态、权限、主附关系和是否存在未完成申请。
- 只要有一件资产不符合条件，整张申请不能提交；页面需要列出具体资产编码和失败原因。
- 所有审批层级通过后，在同一个数据库事务中执行整张申请，保证全部成功或全部失败。
- 每件资产都需要单独写入资产履历，并关联同一个申请编号。

专业词解释：整单审批表示审批人对申请中的全部资产作出同一个决定。数据库事务可以保证批量变更不会出现一部分成功、一部分失败。

审批期间资产锁定规则：

- 资产存在未完成的领用、退库、转移、维修或报废申请时，不能再次发起会修改资产数据的申请。
- 主资产进入审批时，其附属资产一起锁定；附属资产单独进入审批时，需要检查是否会与主资产的待办操作冲突。
- 锁定期间允许查看资产、导出有权限的数据、打印标签和参加盘点。
- 锁定期间的盘点只记录实际扫码结果，不直接执行会与待审批申请冲突的资产变更。
- 申请审批通过并执行完成、被拒绝或被撤回后，系统自动解除对应资产的业务锁定。
- 页面需要显示锁定原因、申请编号、操作类型和申请人，并允许有权限的用户进入申请详情。
- 前端发起操作前进行提示，后端提交接口必须再次检查，防止重复请求绕过页面限制。

专业词解释：业务锁定是指资产有一项变更正在审批时，暂时禁止再次发起冲突的变更，但资产仍然可以正常查看和盘点。

审批通过后的执行失败规则：

- 审批结果和业务执行结果分别记录，不能因为执行失败把已经完成的审批改回待审批。
- 所有审批层级通过后，审批状态记为“已通过”，系统再执行正式资产变更。
- 如果执行过程中发生数据库异常、数据校验失败或外部接口异常，执行状态记为“执行失败”。
- 批量申请使用数据库事务，执行失败时整张申请中的资产全部保持原样。
- 执行失败后，相关资产继续保持业务锁定，避免发起冲突操作。
- 管理员排除故障后可以重新执行原申请，不需要重复审批。
- 重新执行前必须再次校验资产状态和申请内容，且不能修改已经审批通过的申请数据。
- 如果申请内容需要修改，必须关闭原申请并重新提交一张新申请。
- 系统保存执行失败原因、失败时间、重试人、重试时间和每次重试结果。

重新执行权限规则：

- 超级管理员默认拥有重新执行权限。
- 资产管理员需要拥有重新执行权限后才能操作。
- 普通申请人和审批人默认不能重新执行失败申请。
- 自定义角色可以在权限管理中配置重新执行权限。
- 重新执行前，页面显示失败原因、申请内容和涉及的资产清单。
- 后端重新执行接口必须校验权限、数据范围、申请审批状态和执行状态。
- 每次重新执行都写入操作日志；涉及具体资产时同步显示在资产履历中。

重新执行权限编码建议：

```text
approval:execution:retry
```

终止执行规则：

- 执行失败且确认不再重试时，可以使用“终止执行”结束本次业务处理。
- 超级管理员默认拥有终止执行权限。
- 资产管理员和自定义角色需要单独配置终止执行权限。
- 终止执行时必须填写原因，并进行二次确认。
- 终止后不修改资产数据，执行状态记为“已终止”，并解除相关资产的业务锁定。
- 原审批结果、执行失败原因和全部重试记录永久保留。
- 终止后如果仍要进行同一业务，必须重新创建申请并重新审批。
- 终止执行写入操作日志；涉及具体资产时同步显示在资产履历中。

终止执行权限编码建议：

```text
approval:execution:terminate
```

执行状态补充：

```text
TERMINATED  已终止
```

专业词解释：终止执行是保留已完成的审批记录，但明确放弃本次资产变更，用于解除长期无法处理的失败申请和资产锁定。

审批流程版本管理规则：

- 审批流程配置支持“草稿”和“已发布”状态。
- 管理员编辑流程时先保存为草稿，草稿不会被业务申请使用。
- 管理员检查操作类型、审批层级、审批人、或签和会签规则后，点击“发布”才正式生效。
- 每次发布生成一个新的流程版本号，新提交的申请使用最新已发布版本。
- 已经提交的申请继续使用提交时保存的流程版本和审批人快照，不受新版本影响。
- 已经被申请使用过的流程版本不能修改或删除，只能停用并永久保留。
- 停用流程后不能再提交对应操作的新申请，但不影响正在审批或已经完成的历史申请。
- 发布、停用和恢复流程都需要写入系统操作日志。

流程状态建议：

```text
DRAFT      草稿
PUBLISHED  已发布
DISABLED   已停用
```

专业词解释：流程版本管理是每次正式发布都保存一个不可修改的版本，让系统能够查清每张申请当时使用的审批规则。

审批流程管理权限规则：

- 超级管理员默认拥有审批流程的查看、编辑、发布和停用权限。
- 系统增加“审批管理员”默认角色，默认拥有审批流程的查看、编辑、发布和停用权限。
- 资产管理员默认只能查看审批流程，不能编辑、发布或停用。
- 自定义角色可以分别配置查看、编辑、发布和停用权限。
- 编辑权限只允许维护草稿，不能直接让草稿生效。
- 发布和停用属于重要操作，页面需要二次确认并写入系统操作日志。
- 后端接口必须分别校验对应权限，不能只依赖前端按钮控制。

审批流程权限编码：

```text
approval:flow:view      查看审批流程
approval:flow:edit      新建和编辑流程草稿
approval:flow:publish   发布审批流程
approval:flow:disable   停用或恢复审批流程
```

专业词解释：权限拆分可以让某个角色只负责编辑草稿，另一个角色负责正式发布，减少审批规则被误改后直接生效的风险。

新增资产入库默认审批规则：

```text
有新增权限的人员填写资产
  -> 提交入库申请
  -> 对应所属公司的资产管理员审批并确认入库
  -> 审批通过后资产正式进入台账
```

- 入库申请允许提交人与审批人为同一个人。
- 提交人必须同时拥有新增资产权限和入库审批权限，才能审批自己提交的入库申请。
- 没有入库审批权限的提交人仍需等待有权限的资产管理员审批。
- 入库自审规则在本地开发和正式环境中都可以使用。
- 提交入库申请时立即生成并占用正式资产编码，不等待审批通过。
- 审批被拒绝或申请被撤回后，已经生成的资产编码标记为“未入库作废”，永久不再复用。
- 审批通过并执行成功后，资产才成为正式台账数据，并生成标签和资产履历。
- 后续可以通过审批流程管理增加其他审批层级。

专业词解释：入库自审是指同一个人既提交入库申请又完成入库确认，但这个人必须同时拥有提交和审批两项权限。

审批状态建议：

```text
PENDING     审批中
APPROVED    已通过
REJECTED    已拒绝
WITHDRAWN   已撤回
```

执行状态建议：

```text
NOT_STARTED  未执行
PROCESSING   执行中
SUCCESS      执行成功
FAILED       执行失败
```

专业词解释：审批与执行分离是把“审批人是否同意”和“系统是否成功修改资产”作为两个状态保存，这样系统故障不会覆盖真实审批结果。

需要管理的操作包括：

- 资产新增
- 资产编辑
- 资产领用
- 资产归还
- 资产调拨
- 资产维修
- 资产报废
- 资产导入
- 资产盘点结果确认
- 资产标签批量打印，可按管理要求决定是否审批

## 8. 飞书集成设计

飞书集成分为四部分：

- 飞书单点登录
- 飞书组织架构同步
- 飞书领用流程
- 飞书退库流程
- 飞书自主盘点任务通知和手动催办

第一版正式上线飞书集成边界：

- 飞书负责单点登录、员工部门同步、个人资产领用确认、员工退库和盘点消息通知。
- 资产转移、维修、报废、Excel 导入、盘点异常处理和权限管理继续在资产系统内部完成。
- 资产系统内部审批结果和资产履历不依赖飞书审批单保存。

后续需要在飞书开放平台准备以下信息：

```text
FEISHU_APP_ID
FEISHU_APP_SECRET
FEISHU_REDIRECT_URI
FEISHU_APPROVAL_USE_ASSET_CODE
FEISHU_APPROVAL_RETURN_ASSET_CODE
FEISHU_CALLBACK_VERIFICATION_TOKEN
FEISHU_CALLBACK_ENCRYPT_KEY
```

飞书回调安全规则：

- 所有回调先验证飞书签名和验证令牌，再解密事件内容。
- 验证失败的请求直接拒绝，不执行业务变更。
- 使用飞书事件 ID 做去重，同一个事件只处理一次。
- 重复回调返回成功，但不能重复修改资产、审批或履历。
- 回调处理保存事件 ID、事件类型、接收时间、处理结果和错误原因，密钥和原始敏感内容不写日志。

专业词解释：幂等处理表示同一回调即使重复发送，系统也只执行一次业务变更。

本地开发阶段可以先使用本地账号登录和模拟审批，等业务流程稳定后再接入真实飞书。

第一版用户处理方式：

- 本地开发保留本地超级管理员账号。
- 本地开发允许通过环境变量开启测试员工登录，用于验证自主盘点、查看本人资产和退库等员工流程。
- 测试员工登录只能在开发环境启用，正式环境必须关闭。
- 第一版正式投入公司使用前，必须完成飞书单点登录、员工同步和部门同步。
- 正式员工、部门、上下级关系从飞书自动同步，不在资产系统中重复手动创建真实员工。
- 普通员工通过飞书登录进入系统，本地超级管理员继续作为维护和应急账号保留。
- 飞书员工和部门每天凌晨自动同步一次，同时提供管理员手动同步入口。
- 同步失败保存失败原因并允许重新执行，不直接删除历史人员或部门记录。
- 飞书同步发现员工离职或停用后，立即禁止其登录，但保留人员资料和全部历史记录。
- 系统生成“离职人员名下资产”清单，由管理员办理退库、转移和盘点责任交接。
- 飞书同步发现员工部门变化后，自动更新该员工名下资产的使用部门。
- 部门跟随更新不改变资产所属公司和资产编码，也不需要审批，但需要写入资产履历和同步日志。

建议环境变量：

```text
APP_ENV=development
ENABLE_DEV_MOCK_LOGIN=true
```

正式环境必须配置：

```text
APP_ENV=production
ENABLE_DEV_MOCK_LOGIN=false
```

条件必填规则：

- 资产标记为附属资产时，必须选择一台有效的主资产。
- 设备序列号对所有资产分类都不是必填项，有序列号时填写，没有时可以留空。

专业词解释：固定必填表示任何新增资产都必须填写；条件必填表示只有满足特定情况时才必须填写，例如附属资产必须选择主资产。

设备序列号规则：

- 所有资产分类的设备序列号都允许为空。
- 设备序列号一旦填写，必须在正式资产、待入库申请和待确认导入任务中保持唯一。
- 比较重复时忽略英文字母大小写和前后空格，例如 `ABC123` 与 `abc123` 视为相同。
- 发现重复时，系统显示警告并阻止新增、提交审批或确认导入，不能强行跳过。
- 警告信息需要显示已有记录的资产编码、资产名称和记录状态，方便管理员核查。
- 已报废资产的序列号仍然参与重复检查；确实不是同一序列号时，可以修正填写内容或留空。
- Excel 同一文件内部出现重复序列号时，整批校验失败。

专业词解释：唯一校验表示已经填写的序列号不能重复；序列号留空不受限制，可以有多件资产不填写序列号。

采购金额规则：

- 第一版金额币种统一为人民币。
- 采购金额保留两位小数，数据库字段使用 `DECIMAL(18,2)`。
- 金额必须大于或等于 `0.00`，不允许负数。

- 资产来源为“采购”且金额为 `0.00` 时，系统显示明显警告，管理员确认后仍可提交。
- Excel 导入中的金额必须是有效数字，系统统一转换并显示为两位小数。
- 采购金额是采购价和财务入账金额，不随资产使用时间或折旧减少。

## 10. Excel 导入导出设计

基础资料导入入口：

- 在“基础字典”菜单下增加“公司编码导入”和“资产分类导入”两个独立页面。
- 两类导入都提供标准模板下载、文件上传、校验预览、错误报告和管理员确认。
- 导入时沿用原有公司编码和资产分类编码，不由新系统重新生成。
- 公司编码导入支持公司名称、上级公司编码、上级公司名称、层级和状态。
- 资产分类导入支持分类编码、分类名称、使用期限（月）、默认计量单位、上级分类编码、上级分类和状态。
- 上级编码必须已经存在，或者同时出现在当前文件中；系统按照上级编码建立层级关系。
- 编码重复、父级不存在、层级循环或必填字段缺失时，整批校验失败。
- 基础资料导入任务需要先预览并由管理员确认，确认后整批写入，全部成功或全部失败。
- 正式资产导入前，必须先完成公司编码和资产分类编码导入。
- 公司和分类编码一旦导入并被使用，任何人都不能修改。
- 再次导入已存在的公司编码时，不新增重复记录，预览并更新公司名称、上级公司和状态。
- 再次导入已存在的分类编码时，不修改编码，预览并更新名称、上级分类、使用期限、默认计量单位和状态。
- 顶级公司和顶级分类的上级编码允许为空；非顶级记录必须填写有效上级编码。
- 公司编码和分类编码统一按文本读取和保存，保留前导零及字母。
- 导入文件中没有出现的现有编码保持不变，不自动停用或删除。
- 同一个文件内出现重复编码时整批失败，并显示所有重复行号。
- 拥有对应导入权限的管理员可以上传并自己确认，不需要另一人审批，但必须预览差异并二次确认。
- 公司和分类管理页面支持导出当前完整层级，导出文件可以修改后重新导入。
- 已确认导入不能一键撤销；发现错误时通过下一次正确导入进行前向修正。
- 每次更新保存修改前后值、导入任务编号、操作人和时间。

基础资料导入导出权限建议：

```text
organization:import
organization:export
asset_category:import
asset_category:export
```

基础资料导入顺序：

```text
导入公司编码
  -> 导入资产分类编码
  -> 同步飞书员工和部门
  -> 导入历史资产台账
```

专业词解释：基础主数据是资产引用的公司、分类等标准资料，先导入主数据可以保证每条资产都能找到正确编码。

导入流程：

```text
下载模板
  -> 填写 Excel
  -> 上传 Excel
  -> 系统解析
  -> 系统校验
  -> 生成导入结果
  -> 生成导入任务
  -> 管理员查看预览和错误信息
  -> 管理员确认导入
  -> 正式写入资产
```

导入原则：上传 Excel 后不直接入库，必须先生成导入任务。管理员确认无误后，系统再正式写入资产数据。

Excel 导入资产编码规则：

- Excel 中已经填写历史资产编码时，沿用原编码，并检查格式、重复和编码占用记录。
- Excel 中没有填写资产编码时，系统先校验整份文件；所有数据行全部通过后，在导入任务进入待确认状态时直接批量分配正式资产编码。
- 新生成的资产编码在导入预览中显示，管理员确认前可以逐行核对。
- 只要存在一行校验错误，整份文件都不生成资产编码，也不能确认入库。
- 导入任务被取消、拒绝或最终不再入库时，已经生成的编码标记为“未入库作废”，永久不复用。
- 管理员确认导入并执行成功后，编码状态从“待审批入库”变为“已正式入库”。
- 批量生成编码时，仍然按照“顶级公司 + 资产分类”分别递增，并防止多人同时导入产生重复编号。

专业词解释：批量预分配编码是指整份 Excel 全部校验通过后，对没有历史编码的数据一次性生成正式编号，然后在导入预览中交给管理员检查。

Excel 整批校验和入库规则：

- 只要 Excel 中存在一行或一个字段错误，整个导入任务都不能确认入库。
- 系统需要在预览页面列出错误行号、资产标识、错误字段、填写内容和错误原因。
- 管理员可以下载错误报告，修改原文件后重新上传并生成新的校验结果。
- 所有数据全部校验通过后，系统才生成缺失的资产编码并开放“确认导入”按钮。
- 管理员确认并完成审批后，整批资产在同一个数据库事务中写入正式台账。
- 第一版不支持只导入正确行，避免部分成功造成资产漏导、重复导入或对账困难。

导入任务状态补充建议：

```text
VALIDATION_FAILED      校验失败
PENDING_CONFIRMATION   待管理员确认
```

专业词解释：整批校验、整批入库表示同一个 Excel 文件中的资产必须全部正确后才能一起进入正式台账，不能只导入其中一部分。

Excel 字典未匹配警告规则：

- 资产来源、计量单位或存放地点单元格有内容，但无法匹配现有字典时，不作为整批校验错误。
- 导入预览显示警告、Excel 行号、字段名称和原始填写内容。
- 管理员确认导入后，对应正式字段保存为空，并标记为“待补充”。
- Excel 原始文字保存在导入任务明细中，并与正式资产关联，资产详情可以查看。
- 第一版不在导入预览中自动补建来源、计量单位或地点字典。
- 后续补充正式字段后，原始导入内容和补充记录继续保留，便于追查。

警告类型建议：

```text
SOURCE_NOT_MATCHED    资产来源未匹配
UNIT_NOT_MATCHED      计量单位未匹配
LOCATION_NOT_MATCHED  存放地点未匹配
```

专业词解释：警告通过表示系统发现数据不完整或无法匹配时进行提示，但管理员仍可以确认导入；原始值保留用于后续核对和补充。

信息待补充清单规则：

- 第一版提供独立的“信息待补充”清单，也可以从资产列表按信息完整状态筛选。
- 信息完整状态包括“完整”和“待补充”。
- 清单显示资产编码、资产名称、缺失字段、Excel 原始内容、导入任务编号和导入时间。
- 支持逐件补充来源、计量单位和存放地点。
- 支持多选资产后批量补充相同的标准值。
- 首页显示待补充资产总数，并可以点击进入清单。
- 所有缺失字段补齐后，系统自动把资产标记为“完整”并移出待补充清单。
- 每次补充保存操作人、时间、修改前后内容，并写入资产履历和操作日志。
- 补充历史导入产生的空缺来源、计量单位和存放地点不需要审批，保存后立即生效。
- 直接补充只允许从空值补为标准字典值；已经有值的字段需要修改时，继续按照正常资产编辑或地点变更规则处理。

信息完整状态建议：

```text
COMPLETE     完整
INCOMPLETE   待补充
```

专业词解释：数据质量清单是把资料不完整的资产集中展示并持续跟踪，避免历史导入的空值长期无人处理。

Excel 新增导入规则：

- 第一版资产 Excel 导入只用于新增资产，不允许覆盖或更新系统中已有资产。
- Excel 中填写的资产编码如果已经存在于正式资产台账、待入库申请或编码占用记录中，整批校验失败。
- 错误信息需要显示 Excel 行号、重复资产编码和系统中对应记录的状态。
- 不允许通过新增导入修改现有资产的金额、使用人、部门、地点、状态或主附关系。
- 现有资产资料通过资产编辑和对应业务流程修改，使用人、地点和状态通过领用、退库、转移、维修、报废或盘点确认变更。
- 后续如需批量修改，单独设计“资产批量更新模板”、字段权限、差异预览和审批流程，不能复用新增导入接口直接覆盖。

专业词解释：新增导入只创建不存在的资产；更新导入会修改已有资产。两种功能分开可以避免错误 Excel 覆盖大量正式资产数据。

导入模板：系统需要提供标准 Excel 导入模板，防止字段缺失、字段顺序错误、格式不统一导致数据偏差。

导入模板建议包含：

- 标准字段表头
- 必填字段标记
- 示例数据
- 字段填写说明
- 下拉选项，例如资产状态、来源、计量单位、资产分类
- 日期格式说明
- 金额格式说明

导入校验内容：

- 必填字段是否为空
- Excel 历史导入中资产来源、计量单位和存放地点允许为空，作为页面新增必填规则的导入例外
- 条件必填字段是否符合资产分类、主附关系和使用类型要求
- 资产编码是否重复
- 资产分类是否存在
- 部门是否存在
- 使用人是否存在
- 日期格式是否正确
- 金额格式是否正确
- 状态是否合法

导出内容：

- 资产台账导出
- 部门资产导出
- 使用人资产导出
- 审批记录导出
- 盘点结果导出

## 11. 资产状态设计

资产台账中的资产状态只保留以下四种：

```text
IDLE       闲置
IN_USE     在用
REPAIRING  维修中
SCRAPPED   已报废
```

状态规则：

- 闲置：资产可被领用、调拨或分配。
- 在用：资产已经被领用，或公共设备已经由管理员确认投入使用。
- 维修中：资产正在维修，暂时不能正常领用。
- 已报废：资产已经报废，不再作为正常资产使用。

注意：丢失、盘点异常不进入资产台账状态，只在盘点结果中出现。

在用状态规则：

- 个人领用设备：必须有人领用后，资产状态才变为在用。
- 公共设备：可以不挂到具体使用人，但必须挂到对应地点。
- 公共设备领用或投入使用时，不需要用户签字。
- 公共设备需要管理员签字确认后，资产状态才变为在用。

建议增加资产使用类型字段：

```text
usage_type
```

使用类型建议：

```text
PERSONAL  个人使用
PUBLIC    公共使用
```

个人使用和公共使用的区别：

| 使用类型 | 是否需要使用人 | 是否需要地点 | 谁确认 |
| --- | --- | --- | --- |
| 个人使用 | 需要 | 可选 | 领用员工确认 |
| 公共使用 | 使用人填写为设定的地点名称 | 需要 | 管理员确认 |

公共资产规则：

- 公共资产和个人资产按照“使用人”的角色区分。
- 系统中需要支持创建“公共使用”角色。
- 当资产的使用人属于“公共使用”角色时，该资产按公共资产处理。
- 页面仍然显示“使用人”字段。
- 公共资产的使用人显示为地点名称，例如“会议室A”“前台”“公共办公区”。
- 公共资产的存放地点显示真实物理位置，例如“上海办公室 3 楼 A 会议室”。
- 公共资产不需要员工个人签收，由管理员确认投入使用。
- 为避免和系统权限角色混淆，建议把“公共使用”角色归到使用对象类型或资产使用角色中，不和系统管理员、资产管理员这类权限角色混在一起。

建议使用人类型：

```text
EMPLOYEE      员工
PUBLIC_PLACE  公共地点或公共使用对象
```

建议公共使用对象示例：

```text
会议室A
前台
公共办公区
仓库
机房
录播间
```

判断规则：

```text
使用人是员工 -> 个人资产逻辑
使用人属于公共使用角色 -> 公共资产逻辑
```

公共使用对象登录规则：

- 公共使用对象不需要登录系统。
- 公共使用对象不需要飞书账号。
- 公共使用对象只作为资产“使用人”选项存在。
- 公共使用对象由管理员维护。
- 公共资产相关确认由管理员完成。
- 新增公共使用对象时，系统自动生成 `PUB` 加至少 6 位流水号，例如 `PUB000001`。
- 公共使用对象名称在系统中必须唯一；同名会议室需要增加办公室、楼层等前缀区分。
- 已被资产或历史记录使用的公共对象不能删除，只能停用。
- 停用后不能用于新增领用或转移，已有资产继续显示，并生成待退回或转移清单。

建议字段：

```text
users.is_login_allowed
users.user_type
users.public_object_code
```

其中：

```text
员工：is_login_allowed = true
公共使用对象：is_login_allowed = false
```

使用人来源规则：

- 真实员工从飞书自动同步。
- 公共使用对象在资产系统中由管理员手动维护。
- 公共使用对象不参与飞书人员同步。
- Excel 导入资产时，使用人既可以匹配飞书员工，也可以匹配公共使用对象。

建议数据来源字段：

```text
source
```

来源示例：

```text
FEISHU_SYNC    飞书同步
MANUAL         系统手动维护
IMPORT         Excel 导入创建或匹配
```

存放地点规则：

- 存放地点做成可维护的地点字典。
- 存放地点支持上下级层级。
- 地点字典不关联公司，所有公司共用同一套地点数据。
- 新增、领用、退库、转移和盘点时，不按照资产所属公司过滤地点。
- 地点名称允许在不同上级节点下重复，例如上海办公室和北京办公室都可以有“A会议室”。
- 同一个上级地点下面不允许出现两个完全同名的地点。
- 地点编码在整个系统中唯一，页面选择和 Excel 导出优先显示完整地点路径，避免同名地点混淆。
- 新增地点时由系统自动生成全局唯一编码，格式为 `LOC` 加至少 6 位流水号，例如 `LOC000001`。
- 地点编码生成后不能修改；地点改名或移动层级时继续使用原编码。
- 资产选择存放地点时，从地点字典中选择。
- 不建议普通用户随意手填存放地点，避免同一个地点出现多种写法。
- 盘点任务可以按存放地点或某个地点及其下级地点筛选资产。
- 资产页面只选择“存放地点”，“区域名称”和“区域名称（短）”不允许手工填写。
- 系统根据选中的地点节点及其完整层级路径，自动生成区域简称和区域完整名称。
- Excel 导入和导出继续保留“区域名称（短）”“区域名称”“存放地点”字段，兼容现有模板。
- Excel 导入时以地点编码或完整地点路径作为主要匹配依据，区域字段用于辅助校验一致性。
- 资产履历保存地点变更前后的名称快照，地点字典以后改名不会覆盖历史履历文字。
- 每个地点节点增加“允许存放资产”开关，区分只用于组织层级的节点和可以实际选择的节点。
- 具体房间等末级地点默认允许选择；办公室、楼层等上级地点由管理员按实际需要设置。
- 已被资产使用的地点后来关闭“允许存放资产”后，历史和当前资产仍正常显示，但新增、领用、退库和转移时不能再选择该地点。
- 已被资产、盘点任务、申请或历史记录引用的地点不能删除，只能停用。
- 有下级节点的地点不能直接删除。
- 只有从未被引用且没有下级节点的错误地点，超级管理员才能删除。
- 删除前必须二次确认并写入操作日志，被删除地点的编码永久不复用。
- 地点节点移动到新的上级节点时，其全部下级地点一起移动并重新生成完整路径。
- 使用这些地点的资产继续关联原地点 ID，当前页面自动显示新路径，不需要逐件发起资产转移。
- 地点移动前显示受影响的下级地点数量和资产数量，操作人必须填写原因并二次确认。
- 资产履历中的旧地点名称和路径快照保持不变。
- 相关地点或下级地点存在进行中的盘点任务时，禁止移动，盘点完成后才能操作。
- 地点移动需要记录移动前后上级节点、完整路径、操作人、时间和原因。

地点字典权限规则：

- 超级管理员默认拥有地点查看、新增、编辑、移动、停用和删除权限。
- 资产管理员默认拥有地点查看、新增、编辑、移动和停用权限，但不能删除地点。
- 普通员工只能查看和选择有权限使用的地点，不能维护地点字典。
- 自定义角色可以分别配置各项地点权限。
- 删除接口除检查 `location:delete` 权限外，还必须执行未引用、无下级节点和超级管理员身份校验。
- 地点移动、停用和删除必须写入操作日志。

地点权限编码：

```text
location:view      查看和选择地点
location:create    新增地点
location:edit      编辑地点名称和资料
location:move      移动地点层级
location:disable   停用或恢复地点
location:delete    删除未使用地点
```

专业词解释：细粒度权限是把查看、新增、移动、停用和删除拆成独立权限，可以按角色只开放实际需要的操作。

地点维护审批规则：

- 新增地点由拥有 `location:create` 权限的人员直接完成，并记录操作日志。
- 编辑从未被引用的地点由拥有 `location:edit` 权限的人员直接完成，并记录操作日志。
- 修改名称、移动层级或停用已经被资产、盘点任务、申请或历史记录引用的地点，需要提交资产系统内部审批。
- 地点变更申请保存变更前后内容、受影响的下级地点和资产数量。
- 审批通过并执行成功后，地点变更才正式生效。
- 删除符合条件的未使用错误地点，由超级管理员二次确认后直接完成，不接入审批流程。
- 地点维护审批只在资产系统内部完成，不接入飞书。

专业词解释：按影响范围审批是根据操作是否影响现有资产和业务记录决定是否审批，避免普通地点录入产生不必要的流程。

地点层级示例：

```text
上海办公室
  -> 3楼
    -> A会议室
    -> B会议室
  -> 4楼
    -> 公共办公区
仓库
机房
录播间
```

建议地点表：

```text
asset_locations
```

建议字段：

```text
id
location_code
location_name
location_short_name
parent_id
parent_location_code
level
path
status
is_selectable
remark
created_at
updated_at
```

管理人规则：

- 管理人作为资产字段保留。
- 管理人表示某件资产的责任管理员。
- 资产责任管理员只能选择飞书同步且账号有效的在职真实员工。
- 责任管理员不要求拥有资产管理员系统角色。
- 飞书同步发现责任管理员离职或停用后，系统生成“待更换责任管理员”资产清单。
- 离职人员继续显示在历史履历中，但不能再被新资产选择。
- 资产管理员表示系统权限角色，控制用户能不能管理资产系统。
- 管理人和资产管理员角色不是同一个概念。
- 一个资产的管理人可以是某个具体员工。
- 一个拥有资产管理员角色的用户，可以管理权限范围内的资产。

示例：

```text
资产名称：MacBook Air
使用人：刘欣宇
管理人：周保祥
```

说明：刘欣宇是资产使用人，周保祥是这件资产的责任管理员。

供应商规则：

- 供应商做成可维护字典。
- 资产选择供应商时，从供应商字典中选择。
- 供应商编码由系统自动生成，格式为 `SUP` 加至少 6 位流水号，例如 `SUP000001`，生成后不能修改。
- 供应商全称不能重复；统一社会信用代码允许为空，但填写后不能重复。
- 比较供应商名称时去除前后空格；发现相同名称或信用代码时警告并阻止新增。
- 已停用的同名供应商应恢复启用，不能重复创建新记录。
- 新增供应商时只有供应商全称必填，供应商编码由系统生成。
- 统一社会信用代码、联系人、联系电话、地址和备注均为选填。
- 新增供应商默认状态为“启用”。
- 资产的供应商字段不是必填项，暂时无法确认供应商时可以留空。
- 超级管理员默认拥有供应商查看、新增、编辑、停用、恢复和删除未使用记录的权限。
- 资产管理员默认拥有供应商查看、新增、编辑、停用和恢复权限，但不能删除。
- 普通员工只能查看和选择供应商。
- 自定义角色可以分别配置供应商权限。
- 已被资产、合同、申请或历史记录使用的供应商不能删除，只能停用。
- 供应商新增、编辑、停用、恢复和删除操作都需要记录日志。

- 普通附件只允许 PDF、Word、Excel、JPG、PNG 和 HEIC。

- 盘点照片继续使用单张原文件最大 10MB 的独立限制。

资产领用规则：

- 资产领用接入飞书流程。
- 个人资产默认由资产管理员在系统创建领用单并指定员工，不要求员工先提交申请。
- 系统向员工发送飞书确认，默认不增加部门负责人审批；后续可以通过流程配置增加审批层级。
- 员工未处理时，领用单保持“待员工确认”，不自动通过、自动取消或修改资产状态。
- 资产管理员可以手动催办或取消待确认领用单。
- 员工可以在飞书拒绝领用，但必须填写原因；拒绝后资产保持原状态并通知资产管理员。
- 拒绝记录永久保留，管理员修改信息后需要重新发起新的领用确认。
- 个人资产有人领用并确认收到后，资产状态变为“在用”。
- 个人资产领用后，使用人变为领用员工。
- 使用部门根据领用员工自动带出。
- 公共资产投入使用时，由管理员确认。
- 公共资产投入使用只在资产系统内完成，允许提交人与确认人为同一个人，不发送飞书确认。
- 公共资产停止使用并退回闲置时，由有权限的管理员在系统直接操作，不走飞书。
- 管理员填写退回存放地点后，系统清空公共使用对象并把资产状态改为闲置，允许同一人确认。
- 公共资产确认后，资产状态变为“在用”。
- 公共资产的使用人显示为公共使用对象名称。
- 公共资产的存放地点填写真实物理位置。
- 领用完成后写入资产生命周期记录和操作日志。

个人资产领用流程：

```text
资产管理员创建领用单并指定员工
  -> 飞书发送员工收货确认
  -> 员工确认收到设备
  -> 系统更新使用人
  -> 系统自动带出使用部门
  -> 资产状态变为在用
  -> 写入资产生命周期记录
```

资产退库规则：

- 资产退库接入飞书流程。
- 员工发起退库后，进入飞书流程。
- 管理员验收资产后，确认退库完成。
- 管理员确认退库完成时，需要填写退库后的存放地点。
- 退库验收发现设备损坏时，管理员仍然完成退库，同时记录设备状况、说明和照片。
- 退库完成后如需维修，再单独发起维修流程，不让损坏情况阻止解除员工使用责任。
- 退库完成后，系统清空使用人。
- 退库完成后，资产状态变为“闲置”。
- 退库完成后，写入资产生命周期记录和操作日志。

退库流程：

```text
员工发起退库
  -> 飞书流程确认
```

资产维修规则：

- 维修流程只在资产系统内部完成，不接入飞书。
- 拥有维修权限的管理员可以直接发起维修，不需要单独审批。
- 维修完成时必须由管理员确认，允许维修发起人与完成确认人为同一个人。
- 主资产发起维修时，页面展示其全部附属资产，但默认只选择主资产。
- 管理员可以明确勾选需要一起送修的附属资产，被勾选资产进入同一张维修单。
- 未勾选的附属资产状态保持不变，主附关系在维修期间保持不变。
- 发起维修时，系统记录维修前资产状态。
- 维修期间，资产状态变为“维修中”。
- 管理员确认维修完成后，维修流程才结束。
- 维修完成后，资产状态恢复为维修前状态。
- 同一张维修单中，每件资产分别恢复自己维修前的状态。
- 如果维修前是在用，修好后恢复为在用。
- 如果维修前是闲置，修好后恢复为闲置。
- 如果无法维修，可以转入报废流程。
- 维修费用和维修供应商均为选填。
- 维修费用使用人民币两位小数，允许 `0.00`，不允许负数。
- 维修费用只进入维修记录，不修改资产采购金额。
- 维修完成后写入资产生命周期记录和操作日志。

```text

  -> 资产状态变为维修中
  -> 填写维修供应商、维修费用、送修日期
  -> 管理员确认维修完成
  -> 填写维修结果和完成日期
  -> 系统恢复维修前状态
  -> 写入资产生命周期记录
```

资产报废规则：

- 报废流程只在资产系统内部完成，不接入飞书。
- 管理员发起报废。
- 报废默认使用两层顺序审批：第一层资产管理员，第二层财务人员。
- 报废申请人不能审批自己提交的报废申请。
- 主资产发起报废时，系统必须展示全部附属资产并要求逐件选择去向。
- 附属资产去向包括：一起报废、解除主附关系变为普通资产、转挂到另一台有效主资产。
- 存在未选择去向的附属资产时，主资产报废申请不能提交。
- 不能让未报废附属资产继续挂在已报废主资产下面。
- 一起报废的主资产和附属资产进入同一张报废申请，但每件资产分别填写报废回收金额和备注。
- 解除关联或转挂关系与主资产报废在审批通过后一起执行，整单全部成功或全部失败。
- 报废时需要填写报废原因。
- 报废时需要填写报废回收金额，也就是处置资产时实际回收的金额。
- 报废回收金额使用人民币两位小数，允许 `0.00`，不允许负数。
- 报废日期默认使用最终一层审批通过并执行成功的日期。
- 超级管理员可以纠正报废日期，纠正不需要审批但必须填写原因、二次确认并记录履历。
- 报废时可以上传报废证明附件。
- 管理员确认报废后，资产状态变为“已报废”。
- 管理员确认报废后，系统写入报废日期，也就是 Excel 中的“清理日期”。
- 报废后的资产不再进入正常可用资产统计。
- 报废完成后写入资产生命周期记录和操作日志。

报废流程：

```text

  -> 填写报废原因
  -> 填写报废回收金额
  -> 上传报废证明，可选
  -> 管理员确认报废
  -> 资产状态变为已报废
  -> 系统写入报废日期
  -> 写入资产生命周期记录
```

资产编辑规则：

- 普通资产资料修改不需要审批，拥有修改权限的人员保存后直接生效。
- 超级管理员默认可以修改除资产编码外的全部资产字段。
- 资产管理员和其他角色需要由超级管理员授予资产修改权限及对应字段权限。
- 实际可修改范围继续受数据权限控制，超级管理员不受普通数据范围限制。
- 资产编码从生成时起任何人都不能修改，包括超级管理员。
- 待入库申请的所属公司或资产分类填写错误并导致编码错误时，需要撤回或拒绝原申请后重新创建，原编码作废且不复用。
- 资产状态、使用人、使用部门和存放地点默认通过领用、退库、转移、维修、报废、盘点确认等业务流程变更。
- 超级管理员可以直接修正资产状态、使用人、使用部门和存放地点；其他角色获得相应字段权限后也可以直接修正。
- 直接修正业务字段不需要审批，但必须填写修改原因并二次确认。
- 直接修正仍需满足业务一致性，例如个人资产状态为“在用”时必须有使用人，使用部门跟随使用人自动生成；已报废状态需要完整报废信息。
- 历史 Excel 导入导致存放地点为空时，从“信息待补充”清单首次补充地点不需要审批，属于明确例外。
- 资产分类、金额、购入日期属于关键字段，修改不审批，但需要对应管理员或字段权限，并写入资产履历。
- 修改资产分类后不重新生成资产编码，原资产编码永久保持不变。
- 修改金额除需要资产修改权限外，还需要 `asset:amount:update` 字段权限。
- 备注、照片、附件、自定义属性等资料字段，允许有权限的用户编辑。
- 所有资产编辑都需要记录变更前数据、变更后数据、操作人和操作时间。
- 历史空缺资料补充虽然不审批，仍必须记录变更前后数据、原始导入值、操作人和操作时间。

资产批量编辑规则：

- 第一版支持多选资产后批量修改相同字段。
- 默认支持批量修改资产名称、资产分类、规格型号、计量单位、来源、供应商、责任管理员、购入日期、备注等资料字段。
- 金额批量修改除 `asset:batch:update` 外，还需要 `asset:amount:update` 权限。
- 资产编码永远不能批量修改。
- 使用人、使用部门、状态和已有存放地点不放入普通批量编辑，继续使用领用、退库、转移、维修、报废、盘点确认等批量业务流程。
- 操作人需要同时拥有 `asset:batch:update`、对应字段权限和覆盖全部所选资产的数据权限。
- 保存前显示选中资产数量、资产清单和字段修改前后内容，并进行二次确认。
- 批量编辑不需要审批，使用数据库事务保证整批全部成功或全部失败。
- 每件资产分别写入资产履历，整次操作使用同一个批量操作编号关联。
- 普通批量编辑选择主资产时，不自动勾选或修改附属资产。
- 页面展开显示附属资产，需要一起修改时由操作人明确勾选。
- 主附资产一起转移继续使用资产转移流程，不受普通批量编辑规则影响。

专业词解释：批量编辑是一次给多件资产修改相同资料；批量操作编号可以把每件资产的履历关联到同一次操作。

资产管理界面和查询规则：

- 首页显示资产总数、闲置、在用、维修中、已报废、待审批、盘点进度、待补充资料和离职员工名下资产。
- 左侧菜单包括首页、资产台账、领用退库、转移、维修、报废、盘点、审批、导入导出、基础字典、组织人员、权限管理和日志。
- 资产列表默认显示资产编码、名称、分类、状态、使用人、使用部门、地点、责任管理员、所属公司和购入日期，金额默认不显示。
- 用户可以保存个人列显示偏好；没有金额权限时不能选择金额列。
- 筛选条件包括资产编码、所属公司、分类、状态、使用人、部门、地点、责任管理员、供应商、来源、购入日期和信息完整状态。
- 资产编码筛选支持一次粘贴多个编码，使用换行、逗号或空格分隔，并按完整编码精确匹配。
- 多编码筛选结果显示匹配数量和未匹配编码，重复输入的编码自动去重。
- 快速搜索支持资产编码、名称、设备序列号、使用人和收货单号的包含匹配。
- 资产列表默认每页 50 条，可切换 20、50、100 条，并保存个人选择。
- 资产详情使用基本信息、照片附件、主附资产、资产履历、维修记录、报废信息、盘点记录和相关审批标签页。
- 批量操作默认只选当前页；选择全部筛选结果时显示总数并二次确认。
- 员工手机端重点提供本人资产、扫码盘点、领用确认和退库；管理员手机端提供资产详情和盘点处理，复杂配置和批量管理主要在电脑端完成。

专业词解释：多个资产编码精确匹配表示每个输入值必须与完整资产编码完全相同，适合一次查询一批指定资产，不会把相似编号混入结果。

本地开发数据库规则：

- 第一版本地开发使用 Docker Compose 启动 FastAPI、MySQL 8.4、Redis 7 和 Nginx。
- 正式前端文件由 Nginx 提供，Nginx 同时把 `/api` 请求转发到 FastAPI。
- 后端通过 `.env` 配置 MySQL 连接信息。
- 本地数据库名建议为 `asset_system`。
- 本地数据库用户建议为 `asset_user`。
- MySQL 数据需要挂载到本地 volume，避免容器重启后数据丢失。
- 后续内网服务器部署时，也可以沿用 Docker Compose 方式。
- 开发、测试和正式环境使用不同的环境配置、数据库和文件目录，不能共用正式数据。
- `.env`、数据库密码和飞书密钥不提交到 Git，项目只提供不含真实秘密的 `.env.example`。
- 所有数据库表结构变化通过 Alembic 迁移脚本执行，正式执行迁移前必须完成数据库备份。
- 正式数据库禁止通过管理工具直接手工改表。

建议环境变量：

```text
MYSQL_HOST=localhost
MYSQL_PORT=3306
MYSQL_DATABASE=asset_system
MYSQL_USER=asset_user
MYSQL_PASSWORD=请在本地 .env 中配置
```

专业词解释：Docker Compose 可以把 MySQL、后端服务等一起编排启动。本地开发使用 Docker Compose，可以减少手动安装数据库带来的环境差异。

Redis 使用规则：

- 第一版 Docker Compose 中加入 Redis。
- Redis 先作为基础设施预留，业务轻量使用。
- Redis 可用于登录状态、飞书回调去重、Excel 导入任务状态、接口限流等场景。
- 后续如果增加异步任务队列，也可以复用 Redis。

建议环境变量：

```text
REDIS_HOST=localhost
REDIS_PORT=6379
REDIS_PASSWORD=请在本地 .env 中配置，可本地为空
REDIS_DB=0
```

专业词解释：Redis 是内存数据库，适合保存临时状态和缓存。它可以帮助系统处理重复回调、任务进度和登录状态等高频数据。

异步任务规则：

- 第一版先做轻量异步任务设计，不强制引入复杂任务队列。
- Excel 导入使用导入任务表记录状态、进度和结果。
- Excel 导出第一版可以先同步处理，后续数据量变大后改为后台任务。
- 批量标签生成第一版可以先同步处理，后续数据量变大后改为后台任务。
- 飞书组织同步使用同步任务表记录进度和结果，后续可接入后台任务队列执行。
- 预留 Celery、RQ 或 Dramatiq 等任务队列能力。

任务状态建议：

```text
PENDING     待处理
PROCESSING  处理中
SUCCESS     成功
FAILED      失败
CANCELLED   已取消
```

专业词解释：异步任务是指把耗时操作放到后台执行，页面不需要一直等待。第一版先用任务表记录状态，后续再升级为真正的任务队列。

本地文件存储规则：

- 第一版使用本地文件存储，文件统一保存在 `backend/storage` 目录。
- 资产照片和业务附件保存在 `backend/storage/assets`。
- Excel 导入文件保存在 `backend/storage/imports`。
- Excel 导出文件保存在 `backend/storage/exports`。
- 生成的标签文件保存在 `backend/storage/labels`。
- Excel 导出、盘点报告和批量标签等临时生成文件保留 7 天后自动删除，需要时可以重新生成。
- 临时文件删除不影响资产、导入任务、盘点结果和导出操作日志。
- 系统定期清理过期临时文件，并记录清理时间、文件数量、空间大小和失败原因。
- MySQL 数据库只保存文件路径、原始文件名、文件类型、文件大小、上传人和上传时间等信息，不把整个文件直接存进数据库。
- 文件访问必须经过后端权限检查，不能因为知道文件路径就直接下载。
- 文件存储代码使用统一接口封装，后续部署到内网服务器时可以切换到 MinIO，不需要修改资产、维修、报废等业务逻辑。
- `backend/storage` 中的实际业务文件不提交到 Git，项目中只保留目录说明文件。

建议环境变量：

```text
STORAGE_TYPE=local
STORAGE_LOCAL_ROOT=backend/storage
```

专业词解释：本地文件存储就是把照片、合同和 Excel 文件保存在运行系统的电脑或服务器硬盘中。MinIO 是内网里专门管理文件的服务，数据量增大或多台服务器共同运行时更方便。统一接口封装表示业务代码只调用“上传、下载、删除文件”等固定功能，以后更换存储位置时不用重写业务流程。

正式内网部署和备份规则：

- 正式环境使用公司内网域名和 HTTPS。
- 使用 Nginx 接收浏览器请求并转发到 FastAPI，前端静态文件也由 Nginx 提供。
- HTTPS 是飞书登录、飞书内打开页面和手机浏览器调用摄像头的正式环境基础条件。
- MySQL 数据库和 `backend/storage` 文件目录每天自动备份一次，默认保留 30 天。
- 数据库备份和文件备份使用同一备份批次编号，避免恢复后附件与数据库记录不一致。
- 每月执行一次恢复测试，验证数据库和附件能够一起还原。
- 备份执行结果、文件大小、开始时间、完成时间和失败原因需要记录并供管理员查看。
- 正式内网服务器建议至少 4 核 CPU、8GB 内存和 300GB 数据盘。
- 当前阶段可以在同一台服务器部署 MySQL、Redis、FastAPI 和 Nginx。
- 备份必须保存到另一块磁盘、NAS 或其它服务器，不能只保存在系统数据盘。
- 数据库和接口按至少 5 万件资产、100 名同时在线用户设计容量。

专业词解释：Nginx 是系统对外访问的入口，负责 HTTPS 和请求转发。恢复测试是把备份实际还原到测试环境，确认备份文件真正可用。

健康检查和故障告警规则：

- 提供存活检查接口，判断 FastAPI 程序进程是否运行。
- 提供就绪检查接口，检查 MySQL、Redis 和必要存储目录是否可用。
- Docker 根据健康状态自动重启异常服务。
- 数据库备份失败、飞书同步失败或飞书回调连续失败时，通过飞书消息通知超级管理员和指定系统管理员。
- 告警记录故障类型、发生时间、错误摘要、恢复时间和处理状态。
- 告警消息不能包含数据库密码、飞书密钥或用户令牌。

建议接口：

```text
GET /api/v1/health/live
GET /api/v1/health/ready
```

专业词解释：存活检查判断程序是否运行，就绪检查判断数据库等依赖是否正常，故障告警负责通知维护人员。

历史数据迁移和上线规则：

- 正式迁移使用一份最终确认的资产 Excel 作为唯一基准文件，不同时导入多个版本。
- 正式上线前至少执行两次完整迁移演练，检查字段、编码、人员、公司、分类、数量和金额。
- 历史状态只允许映射为闲置、在用、维修中和已报废，无法识别的状态整批校验失败。
- 最终导出旧数据后进入数据冻结期，旧系统或原 Excel 暂停修改，紧急变化单独登记后补录。
- 迁移后按照所属公司、资产分类和状态核对资产数量及采购金额，总数和金额一致后才能通过验收。
- 历史员工优先按飞书用户 ID 或员工编号匹配；只有姓名且姓名唯一时才允许自动匹配。
- 员工重名、找不到员工、公司编码不存在或分类编码不存在时，整批校验失败。
- 历史资产编码不变时继续使用旧标签，不强制全部重印；损坏或内容不完整时从新系统补打。
- 正式迁移前备份旧数据和新系统空库，旧系统保留至少 30 天只读访问。
- 上线前提供管理员操作手册、员工领用退库说明、手机盘点说明和常见问题，并完成管理员实操培训。

专业词解释：迁移演练用于提前发现导入问题，数据冻结用于防止迁移期间新旧数据继续变化，回退方案用于严重故障时恢复上线前状态。

盘点扫码方式：

- 支持手机扫描二维码。
- 支持手机扫描条形码。
- 员工自主盘点只允许真实扫描二维码或条形码，不提供手动输入资产编码完成盘点的入口。
- 标签损坏、二维码无法识别或摄像头无法扫码时，员工不能把该资产提交为已盘点，需要联系盘点管理员处理。
- 盘点管理员和超级管理员可以在任务资产清单中勾选资产，直接标记为“已盘点”。

扫码盘点规则：

- 扫到二维码时，系统识别资产并记录盘点结果。
- 扫到条形码时，系统按资产编码匹配资产。
- 员工不能通过手动输入编码或只点击清单中的资产提交正常盘点。
- 如果资产属于本次盘点任务范围，记录为已盘点。
- 如果资产不属于本次盘点任务范围，记录为盘盈或异常。
- 员工扫描到系统内存在但不属于本人当前任务的资产时，不能提交完成结果。
- 任务外扫码记录进入异常清单，由盘点管理员决定是否作为盘盈处理。
- 主资产和每件附属资产必须分别扫码，扫描主资产不会自动把附属资产标记为已盘点。
- 扫描主资产后，手机页面显示其附属资产清单、已盘点数量和待盘点数量。
- 扫描附属资产时，页面显示所属主资产编码和名称。
- 盘点结果既按单件资产统计，也显示每套主附资产是否全部完成盘点。
- 盘点不校验主附关系是否符合现场情况，不设置“主附关系异常”结果。
- 扫描附属资产时只确认该独立资产是否存在，不要求选择或扫描现场主资产。
- 盘点结果不会自动建立、解除或转挂主附关系。
- 盘点任务支持“使用人自主盘点”模式，系统按当前使用人把个人资产分配给本人。
- 使用人在手机端查看自己需要盘点的资产，并逐件扫码确认。
- 每件资产提交盘点结果前，必须填写现场实际存放地点并上传现场照片。
- 实际地点优先从地点字典中选择；现场地点尚未建档时，可以选择“临时地点”并手动填写完整描述。
- 临时地点文字不会自动创建地点字典记录，盘点完成后由管理员决定是否维护标准地点。
- 没有填写地点或没有上传照片时，系统不允许提交该资产的自主盘点结果。
- “已找到”结果必须通过扫描资产标签上的二维码或条形码识别资产后才能提交，不能只在清单中点击完成。
- 扫描成功并满足地点、照片要求后，正常结果由系统自动确认，不需要盘点管理员逐条或批量确认。
- 盘点管理员只跟进盘亏、地点差异、临时地点和其它异常结果。
- 员工完成真实扫码、地点填写和照片上传后，点击提交即显示“完成盘点”。
- 盘点管理员或超级管理员勾选任务内资产并标记“已盘点”后，也直接计入完成进度。
- 管理员直接标记不要求扫码、填写地点或上传照片，但必须填写原因。
- 批量标记可以为全部选中资产填写同一个原因。
- 盘点报告分别统计员工真实扫码完成数量和管理员直接标记数量。
- 自主盘点提交后，管理员可以查看员工完成进度、提交地点、照片和提交时间。

盘点异常处理规则：

- 盘点过程中只记录盘点结果和异常，不直接修改资产台账。
- 所有盘点产生的资产变动，都必须在盘点完成后才能处理。
- 盘点完成后，由管理员统一确认异常处理结果。
- 管理员确认后，系统才允许修改资产台账中的使用人、使用部门、存放地点、状态等信息。
- 盘点异常处理完成后，需要写入资产生命周期记录和操作日志。
- 实物是否找到与地点是否一致分别记录，地点不同不改变“已找到”的实物结果。
- 实际地点与台账地点不同或使用临时地点时，只生成地点差异提示，盘点过程中不自动更新台账。

```text
盘亏 -> 盘点完成后管理员确认 -> 记录盘亏处理结果
```

使用人自主盘点规则：

- 有创建权限的人员创建盘点任务并启用“使用人自主盘点”。
- 超级管理员和资产管理员默认拥有盘点任务创建权限，其他角色需要 `inventory:create` 权限。
- 创建任务时必须设置盘点管理员。

- 被设置为该任务盘点管理员的人员可以查看任务进度、执行催办并手动结束该任务。
- 任意一名任务盘点管理员都可以结束任务，系统记录最终结束操作人。
- 任务开始后，超级管理员和当前任务管理员可以增加或移除盘点管理员。
- 管理员名单调整后必须至少保留 1 名，最后一名管理员不能移除自己。
- 新增管理员通过飞书消息收到任务通知；被移除管理员立即失去该任务管理权限。
- 管理员名单变更不需要审批，但保存变更前后名单、操作人和时间。
- 任务发布时固定资产范围、使用人分配和盘点责任人名单，后续台账变化不会自动增减本任务资产。
- 已发布任务范围填写错误时，取消原任务并重新创建，不直接修改任务快照。
- 盘点管理员和超级管理员可以取消尚未正式完成的任务，取消时必须填写原因。
- 取消后保留任务、已提交结果、照片和日志，不允许删除；已正式完成任务不能取消。
- 任何飞书同步且账号有效的在职真实员工都可以被选择为盘点管理员，不要求原本拥有资产管理员角色。
- 被选择后只获得当前盘点任务的管理权限，不获得全公司资产、金额或其它任务权限。
- 公共使用对象不能被选为盘点管理员，因为公共使用对象不能登录。
- 员工离职或账号停用后不能再被选择，进行中任务需要由其他管理员接替。
- 公共使用对象不能登录，因此公共资产由任务管理员按存放地点分组并分配给真实员工盘点。
- 每组公共资产可以指定一名或多名盘点责任人，被指定人员只获得本任务中这些公共资产的盘点权限。
- 多人负责同一组时，第一条有效提交作为正式结果，后续重复提交保留记录但不重复计算。
- 盘点管理员和超级管理员可以直接盘点本任务范围内的公共资产。
- 公共资产盘点责任人不会因此变成资产使用人，也不会获得长期管理权限。
- 员工请假、出差或无法盘点时，任务管理员可以把本次盘点责任转交给其他在职真实员工。
- 责任转交只改变盘点任务分配，不修改资产台账使用人。
- 原责任人尚未提交时可以直接转交；转交后原责任人失去提交权限，新责任人获得权限。
- 已经提交的结果需要先由盘点管理员作废，再重新分配责任人。
- 转交时必须填写原因，并通过飞书通知原责任人和新责任人。
- 系统保存操作人、时间、原因和转交前后责任人。
- 任务结束前，员工可以撤回自己提交且仍待异常复核的结果，修改后重新提交。
- 盘点管理员可以填写原因后把结果退回员工修改，并通过飞书通知员工。
- 正常结果自动确认后，员工不能自行撤回；填写错误时由盘点管理员退回修改。
- 已被管理员确认或任务已经结束的异常结果，员工不能自行修改。
- 每次提交形成新的结果版本，原地点、照片、盘亏理由、撤回和退回记录全部保留。

盘点结果处理状态建议：

- 超级管理员不需要被加入任务，也可以直接结束任何盘点任务。

- 员工只看到分配给自己的盘点资产，不会看到其他员工名下资产。
- 员工逐件扫码、选择实际存放地点、上传现场照片并提交。
- 找不到资产实物时，员工直接点击“盘亏”，然后进入盘亏理由选择。
- 盘亏结果不要求上传实物照片或填写实际地点，但允许填写补充说明。
- 员工提交盘亏后不立即修改资产台账状态，管理员在盘点任务完成后统一复核和处理。
- 盘亏理由必须选择，并使用可维护的盘亏原因字典。
- 默认原因包括“不在本人处、借给他人、送修中、暂时找不到、疑似丢失、其他”。
- 选择“借给他人”时可以补充借用人；选择“其他”时必须填写详细说明。
- 管理员可以新增、排序、启用和停用盘亏理由，历史记录继续显示停用理由原名称。
- 实际地点支持选择标准地点或填写临时地点，两种方式都不能留空。
- 提交只记录盘点事实，不立即修改资产台账中的存放地点。
- 管理员可以查看未提交、已提交和需要复核的资产。
- 主资产和附属资产仍分别提交，不校验两者的挂接关系。
- 管理员发布任务后，系统向每位参与员工发送飞书消息卡片。
- 消息卡片显示任务名称、截止时间、待盘点资产数量和“开始盘点”入口。
- 员工点击消息后直接打开飞书内手机盘点页面。
- 系统不发送定时自动提醒，管理员可以对未完成人员手动催办。
- 盘点催办不设置时间间隔或次数限制，管理员可以连续催办。
- 发布通知和每次催办都保存发送人、接收人、时间、发送结果和对应任务。
- 盘点截止时间为软截止时间，到期后任务标记为“已逾期”，员工仍可继续提交。
- 截止后提交的记录标记为“逾期提交”。
- 只有管理员手动结束任务后，员工才不能继续提交。
- 到达截止时间不会自动把未提交资产判定为盘亏。
- 管理员结束任务前可以修改截止时间，修改前后时间和操作人需要记录日志。
- 管理员手动结束任务时，尚未提交的资产标记为“未完成盘点”，不自动判定为盘亏。
- 结束前显示未完成人数和资产数量并要求二次确认。
- 任务结束后，管理员可以把未完成资产逐件或批量处理为盘亏或无需盘点。
- 转为盘亏时必须选择盘亏理由；标记无需盘点时必须填写原因。

任务结束后的未提交结果：

```text

LOSS         盘亏
EXEMPTED     无需盘点
```
- 单独催办一名员工时直接发送；批量催办时必须显示人数和名单并二次确认。
- 批量发送完成后显示成功人数、失败人数和失败人员，失败人员可以立即再次催办。
- 创建任务时，管理员可以选择是否强制使用手机相机现场拍照。

- 未强制拍照时，使用人可以选择调用相机或从手机相册上传。
- 照片来源规则在任务开始时固定，任务进行中不能随意修改，避免同一任务使用不同标准。

盘点照片数量规则：

- 每件资产最多上传 5 张盘点照片。
- 未达到任务设置的最低照片数量时，盘点结果不能提交。
- 超过 5 张时不允许继续上传，并提示先删除不需要的照片。
- 最低照片数量和照片来源模式一起保存到任务快照中，任务开始后不能修改。

### 14.1 资产编码规则

确认结果：资产编码规则为“所属公司编码 - 资产分类编码 - 至少 4 位流水号”。

说明：系统只保留“所属公司”，不再单独保留“使用公司”。所属公司用于表示资产归哪个公司所有，也用于资产编码和资产统计。资产编码中的公司编码使用顶级公司编码。

示例格式：

```text
所属公司编码-资产分类编码-0001
```

示例：

```text
358466-10100-0001
```

后续系统新增资产时，由系统根据所属公司、资产分类编码自动生成至少 4 位流水号。`1` 到 `9999` 左侧补零，超过后自然增长为 5 位、6 位或更多位。历史资产导入时沿用原有资产编码。

流水号确认结果：同一个顶级公司 + 同一个资产分类编码下，流水号递增。

流水号位数确认结果：流水号至少为 4 位，但不限制最大位数。`9999` 的下一号为 `10000`，`99999` 的下一号为 `100000`。

编码生成时间确认结果：提交新增资产入库申请时，系统直接生成并占用正式资产编码，不采用延迟分配。

编码复用确认结果：入库申请被拒绝或撤回后，已经生成的资产编码永久不复用。系统保留编码占用记录并标记为“未入库作废”，但不在正式资产台账中显示为资产。

编码占用状态建议：

```text
PENDING_STOCK_IN  待审批入库
ACTIVE            已正式入库
VOID              未入库作废
```

系统需要使用独立的编码流水和占用记录，保证多人同时新增资产时不会产生重复编码。

专业词解释：编码占用记录用于保存每个已经生成过的资产编码及其去向。永久不复用可以避免同一个编码在不同时间对应过不同资产或申请。

原问题：资产编码是沿用现在 Excel 里的编号，还是新系统以后自动生成？

专业词解释：资产编码就是每个资产的唯一身份证号。系统里不能重复，例如一台电脑一个编号。

### 14.2 主资产编码

确认结果：系统需要支持“一台主资产下面挂多个附属资产”。附属资产本身仍然按照正常资产规则生成资产编码，不使用专门的附属资产编码。主附关系主要用于前台展示、统计、盘点和资产转移。

编码规则：

```text
主资产：按正常资产编码规则生成
附属资产：也按正常资产编码规则生成
```

示例：

```text
主资产：358466-10100-0001
附属资产：358466-10600-0001
附属资产：358466-10200-0001
```

说明：附属资产不会生成 `358466-10100-0001-01` 这种专门的子编码。

系统能力：

- 新增主资产时，系统按公司、分类生成主资产编码。
- 新增附属资产时，可以选择所属主资产。
- 附属资产编码仍然按自己的所属公司和资产分类生成。
- 主附关系只是资产正式入库后的挂接关系，不改变两件资产各自独立的编码、状态和生命周期。
- 管理员可以手动把一个附属资产挂到某个主资产下面。
- 超级管理员默认可以挂接、转挂和解除主附关系。
- 资产管理员和其他角色需要由超级管理员授予 `asset:relation:update` 权限。
- 操作人必须同时拥有主资产和附属资产的数据权限。
- 主附关系维护不需要审批，保存后直接生效，但必须填写原因。
- 主资产和附属资产的履历都要记录挂接、转挂和解除关系。
- 已报废资产不能建立新的主附关系。
- 建立或转挂关系时，不校验附属资产原来的使用人、使用部门、存放地点和状态是否与主资产一致。
- 挂接成功时，附属资产的使用人、使用部门、存放地点和当前状态直接同步为主资产的值。
- 挂接后，附属资产的使用人、使用部门和存放地点持续跟随主资产变化，不能单独修改。
- 挂接后的资产状态不持续强制同步；维修和报废等状态流程仍按照每件资产分别处理。
- 附属资产存在未完成业务流程或业务锁定时，需先完成或结束流程后才能挂接，避免覆盖正在处理的状态。
- 解除主附关系时，附属资产保留解除当下的使用人、使用部门、存放地点和资产状态。
- 解除后附属资产变为普通资产，不自动清空使用人，也不自动变为闲置。
- 解除后的资产可以单独进行转移、退库、维修或报废。
- 主附关系只允许一层，不允许多层嵌套。
- 一个主资产下面可以挂多个附属资产。
- 一个附属资产同一时间只能挂在一个主资产下面。
- 主资产和附属资产允许属于不同公司，各自保留所属公司和资产编码。
- 建立跨公司主附关系时显示提醒但不阻止，操作人必须同时拥有双方资产的数据权限。
- 按所属公司统计时，每件资产仍然计入自己的所属公司，不跟随主资产改变财务归属。
- 主资产转移时，附属资产只跟随使用人、使用部门和存放地点，所属公司保持不变。
- 主资产不能再作为附属资产挂到另一台主资产下面。
- 附属资产下面不能继续挂其它资产。
- 需要改变资产在关系中的身份时，先解除原关系，再重新挂接。
- 盘点时，主资产和附属资产可以组合展示，方便核对整套设备。
- 页面展示时，附属资产显示在主资产名下。
- 转移主资产时，主资产和附属资产一起转移。
- 统计时，可以按单件资产统计，也可以按主资产套装统计。

主附资产转移规则：

- 如果转移的是主资产，系统自动连同该主资产名下的附属资产一起转移。
- 附属资产跟随主资产同步变更使用部门、使用人和存放地点。
- 部门、所属组织等信息根据使用人自动带出。
- 如果只需要调整某个附属资产，需要先解除或调整主附关系，再单独处理该附属资产。
- 转移记录中需要清楚记录本次转移包含哪些主资产和附属资产。

资产转移规则：

- 资产转移只在资产系统内部审批，不接入飞书。
- 默认使用一层资产管理员审批。
- 正式环境中，转移申请人不能审批自己提交的申请；本地只有超级管理员时允许自审。
- 资产转移时主要选择新的使用人和存放地点。
- 使用部门、组织路径等信息根据使用人自动生成。
- 不建议在转移时手动选择部门，避免部门和归属人不一致。
- 公共设备转移时主要选择新的使用人显示名称、存放地点和管理员。

原问题：主资产编码是不是用来表示一套资产之间的关系？例如电脑是主资产，鼠标、键盘、显示器是附属资产。

专业词解释：主附资产关系就是一个大资产下面挂多个小资产，方便按整套设备管理。

### 14.3 使用公司和所属公司

确认结果：系统只保留“所属公司”，不再单独保留“使用公司”。所属公司用于表示资产归哪个公司所有。后续可以提供公司编码，系统用公司编码参与生成资产编码。

系统处理方式：

- 资产台账中保留所属公司。
- 资产编码使用所属公司编码生成。
- 报表按所属公司统计资产归属。
- Excel 导入时，如果原表有“使用公司”，可以暂时忽略或作为历史导入备注处理。

原问题：使用公司和所属公司有什么区别？是不是“谁在用”和“资产归谁所有”的区别？

专业词解释：使用公司表示当前实际使用资产的公司；所属公司表示资产在财务或产权上归属哪个公司。

### 14.4 清理日期

确认结果：清理日期表示资产报废日期。

系统处理方式：

- Excel 里仍然兼容“清理日期”这个字段。
- 系统内部字段建议命名为 `scrap_date`，意思是报废日期。
- 当资产报废审批通过后，系统自动写入报废日期。
- 资产状态变为“已报废”后，该资产不再进入正常在用资产统计。

原问题：清理日期具体是什么意思？是报废日期、清退日期、资产清查日期，还是别的含义？

专业词解释：清理日期会影响资产状态和报表统计，所以需要先确定它代表哪类业务动作。

### 14.5 使用期限

确认结果：使用期限的单位是月。例如 36 表示 36 个月，也就是 3 年。

系统处理方式：

- Excel 中的“使用期限”继续兼容数字格式。
- 系统内部字段建议命名为 `service_life_months`。
- 系统可以根据“购入日期 + 使用期限”计算预计到期日期。
- 第一版和当前规划都不做使用期限到期提醒，不发送 90 天、30 天或到期通知。
- 到达预计期限不会自动报废，也不会改变资产状态。

示例：

```text
购入日期：2026-06-02
使用期限：36 个月
预计到期日期：2029-06-02
```

原问题：使用期限里的数字单位是什么？例如 36 是 36 个月，还是 36 年，还是 36 天？

专业词解释：使用期限只作为资产资料和预计日期展示，不触发提醒、折旧或自动报废。

### 14.6 资产金额

确认结果：金额表示采购价，也是财务入账金额，不会随着折旧减少。

系统处理方式：

- Excel 中的“金额”字段继续保留。
- 系统内部字段建议命名为 `original_amount`。
- 该字段表示资产原始入账金额。
- 后续即使增加折旧功能，也不会修改这个字段。
- 如果未来需要折旧，可以另外增加“累计折旧”和“资产净值”字段。

示例：

```text
采购价 / 入账金额：7858.62
累计折旧：以后如需要可单独计算
资产净值：以后如需要可单独计算
```

原问题：金额是采购金额、资产原值，还是当前净值？

专业词解释：采购金额是买入价格；资产原值通常是财务入账金额；净值是扣除折旧后的剩余价值。

### 14.7 签字状态

确认结果：签字状态表示资产流程中的确认动作。不同业务场景的确认人不同，后续希望在飞书里完成确认。

确认场景：

- 入库时：管理员确认资产已经入库。
- 领用时：领用员工确认已经收到设备。
- 退库时：管理员确认资产已经退库完成。

 系统处理方式：

- Excel 中继续兼容“签字状态”字段。
- 系统内部字段建议命名为 `confirmation_status`。
- 后续每个流程可以单独记录确认人、确认时间、确认方式。
- 本地开发阶段可以先在系统内模拟确认。
- 飞书集成阶段改为在飞书消息、飞书审批或飞书待办中确认。
- 个人领用设备由领用员工确认。
- 公共设备不需要用户签字，由管理员确认投入使用。

建议增加确认记录表，用于保存每一次确认动作：

```text
asset_confirmations
```

建议字段：

```text
id
asset_id
operation_request_id
confirmation_type
confirmation_status
confirmed_by
confirmed_by_name
confirmed_at
confirmation_channel
feishu_task_id
remark
created_at
```

确认类型 `confirmation_type` 示例：

```text
STOCK_IN_CONFIRM     入库确认
RECEIVE_CONFIRM      领用签收确认
RETURN_CONFIRM       退库确认
```

确认渠道 `confirmation_channel` 示例：

```text
SYSTEM               系统内确认
FEISHU               飞书确认
OFFLINE              线下确认后系统补录
```

原问题：签字状态是员工领用资产时签字确认吗？是在系统里签，还是在线下纸质单签？

专业词解释：签字状态用于证明使用人已经确认收到资产，可以作为责任归属依据。

### 14.8 RFID

确认结果：目前没有实际使用 RFID 功能，系统先保留 RFID 字段。

系统处理方式：

- 资产台账中保留 RFID 字段。
- Excel 导入导出保留 RFID 字段。
- 第一版不做 RFID 设备扫码功能。
- 后续如果公司采购 RFID 标签和读写器，再扩展 RFID 扫描盘点能力。

原问题：你们现在是否已经有 RFID 标签设备？还是只是先预留 RFID 字段？

专业词解释：RFID 是一种无线识别标签，通常用于批量扫描资产，不需要像二维码一样逐个对准扫码。

### 14.9 二维码和条形码

确认结果：资产标签上二维码和条形码都要打印，同时需要展示公司抬头、资产名称、设备序列号和资产编码。

确认标签尺寸：80mm x 30mm。

确认公司抬头：上海黄豆网络科技有限公司。

标签必备内容：

```text
公司抬头
资产名称
设备序列号
资产编码
二维码
条形码
```

系统处理方式：

- 二维码用于手机扫码打开资产详情页。
- 条形码用于扫码枪快速识别资产编码。
- 条形码内容默认使用资产编码。
- 标签支持单个资产打印，也支持批量打印。
- 标签模板后续可以根据标签纸尺寸调整。

原问题：资产标签上二维码和条形码都要打印吗？还是二选一？

专业词解释：二维码适合扫码打开资产详情；条形码适合快速识别资产编号，常用于扫码枪。

### 14.10 飞书审批流程

确认结果：只有领用和退库接入飞书流程，其它资产操作都在资产系统内部完成。

系统处理方式：

- 资产领用：走飞书流程。
- 资产退库：走飞书流程。
- 资产入库：系统内部完成。
- 资产编辑：系统内部完成。
- 资产调拨：系统内部完成。
- 资产维修：系统内部完成。
- 资产报废：系统内部完成。
- Excel 批量导入：系统内部完成。
- 盘点结果确认：系统内部完成。

建议保留统一申请单设计。这样即使有些操作不走飞书，也能在系统里留下审批、确认、操作记录。

原问题：所有资产操作都走同一个飞书审批流程，还是不同操作使用不同审批流程？例如领用一个流程，报废一个流程。

专业词解释：审批流程指审批单要经过哪些人同意，例如员工提交后先部门负责人审批，再资产管理员审批。

### 14.11 盘点功能

确认结果：第一版就要做完整盘点功能，并且要支持手机直接扫码。

系统处理方式：

- 资产管理员可以创建盘点任务。
- 盘点任务可以按所属公司、部门、位置、资产分类筛选资产。
- 系统生成需要盘点的资产清单。
- 盘点人员用手机打开盘点页面。
- 手机扫码识别资产二维码或条形码。
- 扫码后系统自动匹配资产。
- 如果资产在任务清单中，记录为已盘点。
- 如果资产不在任务清单中，记录为盘盈或异常。
- 实际地点与台账不同只记录地点差异提示，不把它改成盘点失败。
- 自主盘点不检查实际使用人和资产状态差异。
- 盘点完成后生成盘点报告。

建议实物盘点结果类型：

```text
FOUND               已找到，现场确认存在
LOSS                盘亏，账上有但实际没找到
SURPLUS             盘盈，实际有但账上不在本次范围内
```

地点差异单独记录：

```text
MATCHED              与台账地点一致
DIFFERENT            与台账地点不同
TEMPORARY            填写了临时地点，需要复核
```

说明：丢失和盘点异常只作为盘点结果出现，不进入资产台账状态。

原问题：第一版是否必须做盘点功能？例如资产管理员拿手机扫码，检查资产是否还在指定地点。

专业词解释：盘点就是定期核对账面资产和实际资产是否存在。地点差异作为单独提示，不会把已经找到的资产改成盘点失败。

### 14.12 折旧功能

确认结果：不做折旧计算。

系统处理方式：

- 系统记录资产金额，也就是采购价/财务入账金额。
- 系统记录使用期限，单位为月。
- 不计算累计折旧。
- 不计算资产净值。
- 不生成折旧报表。
- 后续如果财务需要，可以再单独增加折旧模块。

原问题：第一版是否需要计算折旧？还是先只记录金额，不做财务折旧计算？

专业词解释：折旧是把资产购买成本按月份或年份分摊，常用于财务报表。

### 14.13 飞书组织同步

确认结果：第一版本地开发保留超级管理员和开发测试员工登录；第一版正式投入公司使用前，必须完成飞书单点登录和人员、部门同步。

系统处理方式：

- 创建一个本地超级管理员账号，用于系统配置、开发测试和应急维护。
- 开发环境可以开启测试员工登录，用于本地验证使用人自主盘点等流程。
- 正式环境必须关闭测试员工登录。
- 第一版正式使用前接入飞书单点登录，并从飞书同步员工、部门和上下级关系。
- 普通员工正式使用时通过飞书单点登录进入系统。

建议预留字段：

```text
users.feishu_user_id
users.feishu_open_id
users.feishu_union_id
users.department_id
departments.feishu_department_id
departments.parent_id
```

建议预留接口：

```text
POST /api/v1/feishu/sync/users
POST /api/v1/feishu/sync/departments
```

原问题：员工和部门信息以后是否从飞书自动同步？还是系统里手动维护？

专业词解释：组织同步就是自动从飞书读取部门、员工、上级关系，减少重复录入。

### 14.14 权限范围

确认结果：系统需要支持全量权限自定义。管理员可以在权限管理中自定义角色，并按照角色赋予权限。同时提供默认角色和默认权限范围。

默认权限范围：

- 普通员工：只能查看自己名下资产。
- 资产管理员：可以查看全公司资产。
- 超级管理员：可以查看和管理全部数据。

自定义权限能力：

- 可以新增自定义角色。
- 可以给角色分配权限。
- 可以给角色设置数据范围。
- 可以给用户分配角色。
- 一个用户可以拥有多个角色。
- 权限最终按角色汇总生效。

建议权限管理页面包含：

```text
角色管理
权限配置
菜单权限
按钮权限
数据权限
用户分配角色
```

原问题：普通员工能不能看到全公司的资产？还是只能看自己名下的资产？

专业词解释：数据权限就是控制一个人能看到哪些数据，不只是能不能打开页面。

### 14.15 Excel 导入审批

确认结果：上传 Excel 后先生成导入任务，管理员确认后再正式入库。同时系统需要提供标准导入模板，防止导入数据出现偏差。

系统处理方式：

- 系统提供资产导入模板下载。
- 管理员按照模板填写资产数据。
- 上传后系统先解析 Excel。
- 系统进行字段校验和数据校验。
- 系统生成导入任务，不直接写入资产主表。
- 管理员查看导入预览、成功条数、失败条数和错误原因。
- 管理员确认后，系统正式入库。
- 如果有错误，管理员可以下载错误报告，修改后重新上传。

导入模板作用：

```text
统一字段名称
统一字段顺序
统一日期格式
统一金额格式
减少漏填和错填
减少导入失败
```

原问题：批量导入资产时，是上传后直接入库，还是也需要审批通过后才入库？

专业词解释：批量导入审批可以防止一次性导入大量错误数据。

### 14.16 文件存储

确认结果：第一版使用本地文件存储，文件统一放在后端的 `backend/storage` 目录；MySQL 只保存文件路径和文件信息。后续部署到公司内网时，系统保留切换到 MinIO 的能力。

系统处理方式：

- 资产照片、采购合同、发票、验收单、维修单和报废证明等文件保存在本地硬盘。
- Excel 导入文件、导出文件和标签文件按照用途分目录保存。
- 用户查看或下载文件前，后端先检查登录状态、角色权限和资产数据权限。
- 后续切换 MinIO 时，已有业务接口和页面保持不变，只替换底层文件保存方式。
- 正式部署时，本地文件目录需要纳入服务器备份。

原问题：第一版的照片、附件、Excel 和标签文件保存在本地硬盘，还是一开始就部署独立文件服务？

专业词解释：数据库适合保存文字和数字等结构化信息，不适合直接保存大量照片和文档。MinIO 是可以部署在公司内网的文件存储服务，作用类似公司自己的对象存储。

### 14.17 前端技术

确认结果：前端使用 `Vue 3 + TypeScript + Vite + Naive UI`。

系统处理方式：

- 资产台账、字典、角色权限和系统配置等页面使用 Naive UI 组件。
- 电脑端重点支持大量数据查询、筛选、编辑和导出。
- 手机端重点支持扫码盘点、资产详情、领用和退库操作。
- 手机页面采用适合触摸操作的独立布局，不直接照搬电脑端表格。

专业词解释：Naive UI 是 Vue 3 的页面组件库，可以提供后台系统常用的表格、表单、弹窗和树形菜单。Vite 是前端项目的启动和打包工具。TypeScript 可以帮助开发阶段提前发现字段类型错误。

### 14.18 申请人与审批人分离

确认结果：采用申请人与审批人分离规则，同时兼顾第一版本地开发阶段只有一个超级管理员的情况。

系统处理方式：

- 本地开发和初始化阶段，允许超级管理员确认自己提交的操作。
- 正式使用后，报废、批量导入、盘点结果确认等重要操作默认禁止申请人自审。
- 不同操作可以单独配置是否允许申请人自审。
- 系统页面和后端接口都要检查自审规则。
- 每次审批都记录申请人、审批人、审批时间、结果和意见。

专业词解释：自审就是申请人审批自己提交的申请。职责分离就是让另一个有权限的人负责确认，减少误操作和不合规风险。

### 14.19 审批拒绝和重新提交

确认结果：审批被拒绝后不修改资产数据；审批人必须填写拒绝原因，申请人可以修改内容后重新提交。

系统处理方式：

- 被拒绝的申请保留原内容、拒绝人、拒绝时间和拒绝原因。
- 申请人修改后重新提交时，生成新一轮审批记录。
- 新旧审批记录相互关联，可以查看完整审批过程。
- 原审批记录不能修改或删除。
- 拒绝和重新提交需要记录到系统操作日志；涉及具体资产时同步显示在资产履历中。

专业词解释：新一轮审批表示修改后的申请重新走一次审批，但原来的拒绝记录仍然保留。审批留痕可以避免历史记录被覆盖。

### 14.20 审批撤回

确认结果：审批完成前允许申请人撤回；审批完成并已经执行资产变更后不能直接撤回。

系统处理方式：

- 系统内部申请在资产系统中撤回。
- 领用、退库等飞书申请在飞书中撤回，资产系统自动同步“已撤回”状态。
- 撤回后不修改资产正式数据。
- 已经执行的业务通过退库、转移等正常流程进行后续处理。
- 系统保留撤回人、撤回时间、撤回原因、原申请内容和已有审批记录。
- 撤回操作写入系统操作日志；涉及具体资产时同步显示在资产履历中。

专业词解释：审批完成前表示申请还处于等待处理的状态。状态同步表示飞书中的撤回结果会自动更新到资产系统，不需要管理员重复操作。

### 14.21 审批催办

确认结果：不做自动审批提醒，但保留手动催办功能。

系统处理方式：

- 无论申请等待多久，系统都不会自动发出提醒，也不会自动审批。
- 申请人可以催办自己提交的待审批申请。
- 超级管理员和审批管理员可以催办全部待审批申请。
- 自定义角色可以通过 `approval:urge` 权限配置是否允许催办。
- 没有催办权限的人员不能看到或调用催办功能。
- 同一个申请对同一个当前审批人，每 1 小时最多催办一次。
- 1 小时内重复点击时不发送通知，并提示稍后再试。
- 催办只通知当前审批人，不改变审批状态和资产数据。
- 系统内部审批在资产系统中催办；领用、退库等飞书审批在飞书审批单中催办。
- 系统保存每次催办的人员、时间、申请和审批人信息。

专业词解释：手动催办表示有人主动点击“催办”按钮后才通知审批人，系统不会定时自动发送消息。

催办频率确认结果：采用每 1 小时最多催办一次的规则。计算范围为“同一个申请 + 同一个当前审批人”，更换审批人后可以对新的审批人发起催办。

专业词解释：频率限制是指在一段时间内限制同一操作的执行次数，防止连续点击产生大量重复消息。

### 14.22 审批转交

确认结果：采用审批转交规则，用于处理审批人请假、离职或选择错误等情况。

系统处理方式：

- 系统内部审批由超级管理员或审批管理员转交给另一位有审批权限的人员。
- 转交时必须填写原因。
- 转交后原审批人不能继续处理，新审批人接收待审批任务。
- 飞书审批在飞书中转交，并将结果同步到资产系统。
- 转交不修改申请内容和资产数据。
- 系统永久保存原审批人、新审批人、操作人、时间和原因。

专业词解释：审批转交只是更换负责处理申请的人，不会重新创建申请。审批权限表示新审批人必须有权处理这一类业务。

### 14.23 多层审批

确认结果：系统内部审批采用可配置的多层顺序审批规则。

系统处理方式：

- 不同操作可以配置不同的审批层数。
- 每一层可以指定审批用户或审批角色。
- 前一层通过后才进入下一层。
- 任意一层拒绝后结束整个审批，资产数据不发生变化。
- 所有层级通过后，系统才执行正式资产变更。
- 流程配置调整只影响新申请，已经提交的申请继续按原流程审批。
- 领用和退库按照飞书中配置的流程执行。

专业词解释：多层顺序审批表示需要多层人员按照顺序确认。流程快照表示申请提交时固定当时的审批规则，避免审批进行到一半时因为配置变化而改变审批人。

### 14.24 或签和会签

确认结果：同一审批层同时支持或签和会签，并且每一层可以单独配置。

系统处理方式：

- 或签时，任意一名审批人同意后该层通过，其他人的待审批任务自动结束。
- 会签时，所有审批人都同意后该层才通过。
- 会签中任意一人拒绝，该层和整个申请立即变为已拒绝。
- 默认使用或签，需要多人共同确认时可以配置为会签。
- 每名审批人的意见和处理时间都需要保留。

专业词解释：或签表示多人中一人处理即可；会签表示指定的所有人都必须处理并同意。

### 14.25 按角色确定审批人

确认结果：审批层指定角色时，提交申请时筛选符合角色、所属公司、数据权限且账号有效的人员，并固定为本次审批人。

系统处理方式：

- 申请提交后，角色成员变化不影响已经生成的审批人名单。
- 审批人员后续无法处理时，通过审批转交进行更换。
- 如果任一审批层没有符合条件的审批人，系统禁止提交申请。
- 页面需要明确提示缺少审批人的层级，方便管理员修正流程配置。
- 历史审批人员和处理记录永久保留。

专业词解释：审批人快照就是在提交时保存本次审批人的固定名单，避免角色人员变化导致正在处理的申请突然换人。

### 14.26 批量申请和整单审批

确认结果：领用、退库、转移、维修和报废支持一张申请包含多件资产，并采用整单审批规则。

系统处理方式：

- 主资产被选择时自动带出附属资产。
- 同一张申请中的全部资产执行相同操作和相同目标信息。
- 审批时整张申请统一通过或拒绝，第一版不支持部分批准。
- 提交前逐件校验，任意一件不符合条件时整张申请不能提交。
- 正式执行时全部成功或全部失败。
- 每件资产分别生成资产履历，并关联同一个申请编号。

专业词解释：批量申请是一次选择多件资产；整单审批是对这些资产统一作出审批决定；全部成功或全部失败可以避免资产数据只修改一部分。

### 14.27 审批期间资产锁定

确认结果：资产有未完成的变更申请时采用业务锁定，主资产和附属资产按照关系一起锁定。

系统处理方式：

- 锁定期间不能再次发起领用、退库、转移、维修、报废等冲突操作。
- 锁定期间仍然可以查看、按权限导出、打印标签和扫码盘点。
- 盘点过程中只记录实际情况，不直接修改被锁定资产的数据。
- 申请执行完成、被拒绝或被撤回后自动解除锁定。
- 资产页面显示正在处理的申请编号、操作类型和申请人。
- 页面和后端接口都必须检查业务锁定状态。

专业词解释：业务锁定用于避免同一件资产同时进行互相冲突的流程，例如一边申请领用，一边申请报废。

### 14.28 审批通过后的执行失败

确认结果：采用审批与执行分离规则。审批通过但系统执行失败时，审批结果保留，资产数据整单不变，并允许故障排除后重新执行。

系统处理方式：

- 审批状态保留为“已通过”，执行状态标记为“执行失败”。
- 批量申请全部保持原样，不能只修改部分资产。
- 相关资产继续保持业务锁定。
- 问题解决后可以重新执行原申请，不需要重新审批。
- 重新执行时不能修改已经审批通过的申请内容。
- 如果需要修改内容，则关闭原申请并重新提交审批。
- 系统永久保存失败原因和每次重新执行的人员、时间及结果。

专业词解释：审批与执行分离可以准确区分“审批已经同意”和“系统还没有成功修改数据”，避免故障发生后重复审批。

### 14.29 重新执行权限

确认结果：超级管理员默认可以重新执行；资产管理员和自定义角色需要配置专门权限；普通申请人和审批人默认不能重新执行。

系统处理方式：

- 只有拥有 `approval:execution:retry` 权限且数据范围覆盖相关资产的人员才能操作。
- 重新执行前显示失败原因、原申请内容和资产清单。
- 重新执行不能修改申请内容，也不能替代审批。
- 后端接口再次校验权限和申请状态。
- 每次重新执行都记录操作人、时间和执行结果。

专业词解释：重新执行权限只允许再次运行已经审批通过但执行失败的原操作，不等于审批权限或资产编辑权限。

### 14.30 终止执行

确认结果：执行失败且决定不再重试时，允许有权限的人员终止执行并解除资产锁定。

系统处理方式：

- 超级管理员默认可以终止执行。
- 资产管理员和自定义角色需要配置 `approval:execution:terminate` 权限。
- 终止时必须填写原因并进行二次确认。
- 终止后不修改资产数据，执行状态变为“已终止”。
- 终止后解除相关资产锁定。
- 审批结果、失败原因、重试记录和终止记录永久保留。
- 后续仍需执行该业务时，必须重新提交申请和审批。

专业词解释：终止执行表示放弃这一次已经审批通过但执行失败的变更，不会撤销或删除原来的审批记录。

### 14.31 审批流程版本管理

确认结果：审批流程采用草稿、发布和历史版本保留规则。

系统处理方式：

- 修改流程时先保存为草稿，不立即影响业务。
- 点击发布后生成新版本，新申请使用最新已发布版本。
- 正在审批的申请继续使用原来的流程和审批人名单。
- 已经使用过的流程版本不能修改或删除，只能停用。
- 停用流程不影响历史申请和正在处理的申请。
- 发布、停用和恢复操作需要记录操作日志。

专业词解释：草稿是尚未投入使用的配置；发布是让配置正式生效；流程版本用于保留每次发布时的完整规则。

### 14.32 审批流程管理权限

确认结果：审批流程权限拆分为查看、编辑、发布和停用，按照角色分别配置。

系统处理方式：

- 超级管理员和审批管理员默认拥有全部流程管理权限。
- 资产管理员默认只能查看流程。
- 自定义角色可以分别配置各项流程权限。
- 拥有编辑权限不代表拥有发布权限。
- 发布和停用时需要二次确认并记录操作日志。
- 页面和后端接口都要执行权限校验。

专业词解释：权限拆分表示把流程管理分成多个独立动作，可以让不同人员分别负责编辑和正式发布。

### 14.33 新增资产入库审批

确认结果：新增资产入库允许提交人和审批人为同一个人。

系统处理方式：

- 默认由资产所属公司范围内的资产管理员审批并确认入库。
- 提交人同时拥有入库审批权限时，可以审批自己提交的入库申请。
- 没有审批权限的提交人不能自审，需要等待其他有权限人员处理。
- 入库允许自审的规则在正式环境中也适用。
- 其它操作是否允许自审，继续按照各自流程配置执行。
- 入库审批和执行过程需要完整记录操作日志和资产履历。

专业词解释：入库自审是新增资产流程的专门规则，不表示同一个人可以审批自己提交的报废、批量导入或盘点结果确认申请。

### 14.34 资产编码生成和复用

确认结果：提交入库申请时直接生成正式资产编码，不采用延迟分配；申请被拒绝或撤回后，已经生成的编码永久不复用。

系统处理方式：

- 提交申请时按照“顶级公司编码 + 资产分类编码”取得下一个流水号；不足 4 位时左侧补零，超过后继续自然增长。
- 新编码立即保存为“待审批入库”，避免其他申请重复使用。
- 审批通过并执行成功后，编码状态变为“已正式入库”。
- 申请被拒绝或撤回后，编码状态变为“未入库作废”。
- 作废编码不出现在正式资产台账中，但可以在申请记录和编码占用记录中查询。
- 作废编码永久不重新分配给其他资产。
- 历史资产导入继续使用原资产编码，并检查是否与已有编码或占用记录重复。

专业词解释：直接生成表示申请提交时就取得正式编号。编码不复用表示即使这次没有入库成功，这个编号也不会再次分配，但系统会保留未使用原因。

### 14.35 流水号自动扩位

确认结果：资产编码流水号至少为 4 位，并允许超过 5 位，不设置最大位数。

系统处理方式：

- 流水号 `1` 显示为 `0001`，不足 4 位时在左侧补零。
- `9999` 的下一号显示为 `10000`。
- `99999` 的下一号显示为 `100000`，后续继续自然增长。
- 流水号扩位不会改变前面的顶级公司编码和资产分类编码。
- 数据库中流水号使用整数保存，生成资产编码时再转换成至少 4 位的显示文字。

专业词解释：流水号自动扩位表示编号达到当前位数上限后增加一位继续使用，不会重新从 `0001` 开始，也不会阻止新增资产。

### 14.36 Excel 导入资产编码

确认结果：历史资产沿用 Excel 中原有编码；没有编码的新资产在校验通过并生成导入任务时直接批量生成正式编码。

系统处理方式：

- 有历史资产编码的数据先校验格式和重复，不重新生成编码。
- 没有编码的数据，在整份文件全部校验通过并进入待确认状态时生成并占用正式编码。
- 生成的编码显示在导入预览中，供管理员确认。
- 只要有一行校验失败，整个任务都不生成编码。
- 导入任务被取消或拒绝后，已生成编码标记为“未入库作废”，永久不复用。
- 确认导入成功后，编码状态变为“已正式入库”。
- 批量编码生成需要保证同一顶级公司和分类下的流水号不会重复。

专业词解释：批量预分配编码表示系统在正式导入前，先给校验通过的新资产生成编号，让管理员能够在预览阶段核对完整数据。

### 14.37 Excel 整批校验和入库

确认结果：Excel 导入采用整批校验、整批入库规则，第一版不支持只导入其中的正确数据。

系统处理方式：

- 任意一行存在错误时，整个导入任务不能确认入库。
- 页面显示每条错误的行号、字段、原内容和原因。
- 管理员可以下载错误报告，修改后重新上传。
- 全部数据校验通过后，系统才生成缺失的资产编码并允许确认导入。
- 审批完成后，全部资产一起成功写入；任意一条写入失败时整批回滚。
- 系统保留失败任务和错误报告，方便以后追查。

专业词解释：整批回滚表示正式写入过程中只要一条数据失败，已经写入的同批数据也会撤回，保证不会只成功一部分。

### 14.38 Excel 只允许新增资产

确认结果：第一版 Excel 导入只允许新增资产，不允许覆盖或更新系统中已有资产。

系统处理方式：

- 资产编码已存在于资产台账、待入库申请或编码占用记录时，整批校验失败。
- 页面显示重复编码所在行和系统中对应记录。
- 不能通过新增导入修改已有资产资料、使用人、地点或状态。
- 已有资产通过编辑或领用、退库、转移、维修、报废等正常流程变更。
- 后续需要批量修改时，单独增加批量更新模板、差异预览和审批流程。

专业词解释：把新增导入和更新导入分开，可以避免上传错误文件后覆盖大量正式资产数据。

### 14.39 新增资产必填字段

确认结果：新增资产采用固定必填和条件必填两类校验规则。

固定必填字段：

```text
所属公司、资产分类、资产名称、计量单位、采购金额、购入日期、
资产责任管理员、资产来源、存放地点
```

条件必填规则：

- 附属资产必须选择主资产。
- 设备序列号对所有资产分类都不强制填写。
- 公共资产投入使用时必须选择公共使用对象和存放地点。
- 闲置资产可以不填写使用人，但页面单个新增时仍需填写存放地点。
- 使用期限默认从资产分类带出，有权限的管理员可以调整。
- 页面单个新增和普通后端新增接口执行相同的必填校验。
- Excel 历史资产导入允许资产来源、计量单位和存放地点为空，不阻止整批导入。

专业词解释：条件必填可以让不同类型资产使用不同规则，例如笔记本电脑必须填写序列号，普通桌椅可以不填写。

### 14.40 采购金额格式

确认结果：第一版统一使用人民币并保留两位小数；金额不能为负数，允许零金额但必须填写原因。

系统处理方式：

- 数据库使用 `DECIMAL(18,2)` 保存采购金额。
- 页面和 Excel 中的金额统一显示为两位小数。
- 赠送、调拨等资产可以填写 `0.00`，同时填写零金额原因。
- 来源为“采购”且金额为零时显示警告，管理员确认后可以继续提交。
- 金额仍表示采购价和财务入账金额，不进行折旧减少。

专业词解释：精确金额类型能够准确保存到分，适合财务数据；零金额原因用于说明为什么必填的采购金额为零。

### 14.41 资产来源字典

确认结果：资产来源做成可维护字典。

系统处理方式：

- 默认提供采购、调拨转入、赠送、盘盈补录、租赁和其他。
- 管理员可以新增、改名、排序、启用和停用来源。
- 已被资产或申请使用的来源不能删除，只能停用。
- 停用来源仍显示在历史数据中，但不能用于新增资产。
- Excel 按来源编码或名称匹配；来源为空时允许导入为空。

专业词解释：资产来源字典可以统一填写标准，方便按采购、赠送或调拨等来源准确统计资产。

### 14.42 计量单位字典

确认结果：计量单位做成可维护字典，并允许资产分类设置默认单位。

系统处理方式：

- 默认提供台、个、套、部、件、张和把等常用单位。
- 管理员可以新增、排序、启用和停用单位。
- 已被使用的单位不能删除，只能停用。
- 新增资产选择分类后自动带出默认单位，有权限时可以修改。
- 停用单位继续显示在历史资产中，但不能用于新增资产。
- Excel 按单位编码或名称匹配；单位为空时允许导入为空。

专业词解释：给资产分类设置默认单位，可以减少重复填写和错误，例如选择“笔记本电脑”后自动填写“台”。

### 14.43 设备序列号是否必填

确认结果：所有资产分类都不强制填写设备序列号。

系统处理方式：

- 单个新增和 Excel 导入时，设备序列号都允许为空。
- 资产分类中不提供“序列号必填”配置。
- 有设备序列号时仍建议填写，方便扫码、查询、盘点和售后维修。
- 标签中的序列号为空时，该行显示为空或隐藏，不阻止标签生成。
- 序列号是否重复的处理规则单独确认，不与是否必填混在一起。

专业词解释：非必填表示可以不填写，不代表删除这个字段；以后取得设备序列号时仍可以补充并记录资产履历。

### 14.44 设备序列号重复处理

确认结果：设备序列号可以为空，但填写后发现重复时，系统同时警告并阻止操作。

系统处理方式：

- 重复检查覆盖正式资产、待入库申请、待确认导入任务和已报废资产。
- 比较时忽略字母大小写和前后空格。
- 发现重复时显示已有资产编码、资产名称和记录状态。
- 单个新增不能提交，Excel 导入整批校验失败。
- 不提供强制跳过重复检查的按钮。
- 如果历史数据确实无法确认序列号，可以将该字段留空。

专业词解释：警告加阻止表示系统不仅提示风险，还会禁止继续提交，必须先修正重复序列号或清空该字段。

### 14.45 区域名称和存放地点

确认结果：页面只选择层级存放地点，区域名称和区域名称（短）由系统自动生成；Excel 导入导出继续保留原字段。

系统处理方式：

- 存放地点从可维护的层级地点字典中选择。
- 系统根据地点节点和完整路径生成区域简称及区域完整名称。
- 用户不能单独手填区域字段，避免区域与地点互相矛盾。
- Excel 以地点编码或完整路径进行匹配，区域字段用于兼容原模板和辅助检查。
- 资产当前位置使用地点字典的最新名称，资产履历保留每次变更时的名称快照。

专业词解释：派生字段是根据标准地点自动生成的字段；名称快照是把操作发生时的地点文字保存到历史记录中，后续地点改名也不会改变旧履历。

### 14.46 地点节点是否允许选择

确认结果：地点字典的每个节点增加“允许存放资产”开关。

系统处理方式：

- 办公室、园区等节点可以只用于组织地点层级，不允许资产直接选择。
- 楼层等上级地点可以由管理员按实际情况决定是否允许选择。
- 会议室、仓库区域等具体地点默认允许选择。
- 已被资产使用的地点后来关闭开关，不影响已有资产显示。
- 关闭后，新增资产和后续业务变更不能再选择该地点。

专业词解释：可选节点可以作为资产真实存放地点；不可选节点只用于整理地点树和汇总下级地点。

### 14.47 地点不关联公司

确认结果：公司和地点不建立关联关系，所有公司共用一套地点字典。

系统处理方式：

- 地点表不保存所属公司字段，也不建立公司与地点的关联表。
- 所有公司的资产都可以选择任意启用且允许存放资产的地点。
- 地点选择列表不按照资产所属公司过滤。
- 地点权限继续受角色和数据权限控制，但不使用公司作为地点适用范围。
- Excel 导入只按地点编码或完整层级路径匹配，不校验地点所属公司。

专业词解释：地点与公司解耦表示地点是一套独立的公共基础数据，不会因为资产属于不同公司而重复维护地点。

### 14.48 同名地点处理

确认结果：不同上级地点下面可以出现相同名称；同一个上级地点下面不会也不允许出现两个完全同名的地点。

系统处理方式：

- 地点编码在整个系统中保持唯一。
- 地点名称只要求在同一个上级节点下唯一。
- 地点选择器显示完整层级路径，不能只显示最后一级名称。
- Excel 优先按地点编码匹配，也可以使用完整层级路径匹配。
- 只填写重复的末级名称且无法确定完整路径时，Excel 校验失败并提示选择具体地点。

专业词解释：同级名称唯一表示同一个父地点下面不能重名；不同分支允许重名，并通过地点编码和完整路径区分。

### 14.49 地点编码生成

确认结果：地点编码由系统自动生成。

系统处理方式：

- 编码格式为 `LOC` 加至少 6 位流水号，例如 `LOC000001`。
- 地点编码在整个系统中唯一。
- 编码生成后不能人工修改。
- 地点改名或移动到其他上级节点时，编码保持不变。
- Excel 导入导出优先使用地点编码准确匹配。
- 后续导入已有地点时，可以通过专用模板沿用原地点编码，但必须校验格式和重复。

专业词解释：稳定标识表示地点名称和层级可以变化，但地点编码始终不变，系统能够持续识别为同一个地点。

### 14.50 地点停用和删除

确认结果：地点删除前执行引用检查，已被使用或存在下级节点时不能删除，只能停用。

系统处理方式：

- 已被资产、盘点任务、业务申请或历史记录使用的地点不能删除。
- 有下级地点的节点不能直接删除。
- 只有从未使用且没有下级节点的错误地点，超级管理员可以删除。
- 删除时需要二次确认并记录操作日志。
- 删除后的地点编码永久不复用。
- 停用地点继续显示在历史数据和现有资产中，但新增及后续资产变更不能再选择。

专业词解释：引用检查是删除前确认地点是否已经被其他数据使用，避免删除后资产、盘点和历史记录找不到原地点。

### 14.51 地点层级移动

确认结果：地点移动到新的上级节点时，下级地点一起移动，当前资产自动显示新路径，历史履历保留旧路径。

系统处理方式：

- 移动父节点时，全部下级地点的完整路径一起更新。
- 资产仍然关联原地点 ID，不需要逐件执行资产转移。
- 移动前显示受影响的下级地点数量和资产数量。
- 操作人必须填写调整原因并二次确认。
- 进行中的盘点任务涉及该地点或下级地点时，禁止移动。
- 操作日志保存移动前后上级节点、路径、操作人、时间和原因。

专业词解释：层级级联更新表示移动一个地点节点时，它下面所有地点的完整路径会一起变化，但每个地点自己的编码保持不变。

### 14.52 地点字典权限

确认结果：地点权限拆分为查看、新增、编辑、移动、停用和删除，并按照角色分别授权。

系统处理方式：

- 超级管理员默认拥有全部地点权限。
- 资产管理员默认可以查看、新增、编辑、移动和停用地点，但不能删除。
- 普通员工只能查看和选择地点。
- 自定义角色可以分别配置各项地点权限。
- 删除地点还必须满足从未使用、没有下级节点等业务条件。
- 地点移动、停用和删除需要记录操作日志。

专业词解释：拥有删除权限不代表任何地点都能删除，系统还会继续执行引用检查和下级节点检查。

### 14.53 地点维护审批

确认结果：地点维护采用按影响范围审批，并且只在资产系统内部完成。

系统处理方式：

- 新增地点和编辑从未使用的地点直接保存并记录日志。
- 修改、移动或停用已经被使用的地点需要内部审批。
- 审批页面显示变更前后内容、受影响下级地点数量和资产数量。
- 审批通过并执行成功后变更才生效。
- 删除未使用的错误地点由超级管理员二次确认后直接完成。
- 地点维护不接入飞书审批。

专业词解释：被使用的地点是指已经出现在资产、盘点任务、业务申请或历史记录中的地点，这类变更可能影响当前查询和统计，因此需要审批。

### 14.54 供应商编码和去重

确认结果：供应商编码由系统自动生成；供应商全称不能重复，统一社会信用代码填写后也不能重复。

系统处理方式：

- 编码格式为 `SUP` 加至少 6 位流水号，例如 `SUP000001`。
- 编码生成后不能修改或复用。
- 新增时发现同名供应商或相同信用代码，系统警告并阻止。
- 已停用的同名供应商需要恢复启用，不能重新创建。
- Excel 优先按供应商编码匹配，也可以按供应商全称匹配。

专业词解释：供应商去重用于保证同一个供应商只有一条标准记录，避免采购金额、合同和维修记录被分散统计。

### 14.55 供应商必填资料

确认结果：新增供应商只要求填写供应商全称，其余资料选填；资产的供应商字段也允许为空。

系统处理方式：

- 供应商编码由系统自动生成。
- 供应商全称必填，并执行重复检查。
- 统一社会信用代码、联系人、联系电话、地址和备注选填。
- 新增供应商默认启用。
- 资产新增和 Excel 导入时可以不选择供应商。
- 后续补充或修改供应商资料时需要记录操作日志。

专业词解释：最小必填信息表示先保存能够识别供应商的基本名称，其他联系资料可以以后逐步补齐。

### 14.56 供应商字典权限

确认结果：供应商权限拆分为查看、新增、编辑、停用和删除，并按照角色分别授权。

系统处理方式：

- 超级管理员默认拥有全部供应商权限。
- 资产管理员默认可以查看、新增、编辑、停用和恢复，但不能删除。
- 普通员工只能查看和选择供应商。
- 自定义角色可以分别配置各项权限。
- 已被资产、合同、申请或历史记录引用的供应商不能删除。
- 所有供应商维护操作都需要记录操作日志。

专业词解释：供应商字典权限只控制供应商基础资料，不会自动赋予采购金额查看权限或合同附件查看权限。

### 14.57 导入预览补建供应商

确认结果：Excel 导入预览页面允许有权限的人员直接批量创建未匹配的供应商。

系统处理方式：

- 预览页汇总展示全部未匹配供应商名称及对应 Excel 行。
- 拥有 `supplier:create` 权限的人员可以选择并批量创建。
- 创建前重新检查名称和统一社会信用代码是否重复。
- 创建成功后自动重新校验原导入任务，不需要重新上传文件。
- 没有新增供应商权限的人只能查看错误并联系管理员。
- 供应商创建和任务重新校验都写入操作日志。
- 所有校验错误解决后，导入任务才允许确认入库。

专业词解释：导入预览补建字典表示管理员可以在解决 Excel 错误的同时补齐缺少的标准资料，并继续使用当前导入任务。

### 14.58 页面必填和 Excel 空值例外

确认结果：资产来源、计量单位和存放地点在页面单个新增时必须填写；Excel 导入时如果没有数据，可以保存为空并且不阻止整批导入。

系统处理方式：

- 页面单个新增和普通新增接口必须填写这三个字段。
- Excel 对应单元格为空时，系统记录为空，不作为校验错误。
- 导入预览对空值显示“待补充”提示，但允许管理员继续确认整批导入。
- 导入成功后，资产详情和台账列表显示这些资料尚未补充。
- 后续编辑资产时，需要补齐空缺字段后才能提交修改。
- 数据库字段需要允许历史导入产生空值，业务接口再根据操作场景执行必填校验。

专业词解释：导入例外是为了兼容不完整的历史数据；数据库允许为空不表示日常新增可以不填，页面和后端仍会按照业务场景检查必填项。

### 14.59 Excel 字典未匹配警告

确认结果：Excel 中资产来源、计量单位或存放地点填写了内容但无法匹配字典时，采用警告通过，不阻止整批导入。

系统处理方式：

- 导入预览显示警告和原始填写内容，不记为校验错误。
- 正式字段保存为空并显示“待补充”。
- 原始文字保存在导入任务明细中，并可从资产详情查看。
- 不在预览页自动创建来源、计量单位或地点字典。
- 后续补充标准字段后，仍然保留原始导入值和操作记录。

专业词解释：警告通过与校验失败不同，警告允许继续入库；保留原始值可以避免系统把无法匹配的历史文字直接丢失。

### 14.60 信息待补充清单

确认结果：第一版增加信息待补充清单和批量补充功能。

系统处理方式：

- 资产列表可以按“完整”或“待补充”筛选。
- 清单显示缺失字段及对应的 Excel 原始内容。
- 支持逐件补充，也支持多选资产批量填写相同标准值。
- 首页显示待补充资产数量并可以进入清单。
- 所有缺失项补齐后自动变为“完整”。
- 补充操作写入资产履历和系统操作日志。

专业词解释：信息完整状态用于快速判断资产资料是否齐全，批量补充适合一次处理多件使用相同来源、单位或地点的资产。

### 14.61 待补充资料直接生效

确认结果：补充历史 Excel 导入产生的空缺来源、计量单位和存放地点不需要审批，保存后立即生效。

系统处理方式：

- 单件补充和批量补充都不生成审批申请。
- 超级管理员和资产管理员默认拥有补充权限，自定义角色由超级管理员分配 `asset:data:complete` 权限。
- 操作人只能补充自己数据权限范围内的资产。
- 直接补充只适用于字段当前为空的情况。
- 已经有值后再次修改，继续按照正常资产编辑或地点变更规则处理。
- 保存时记录 Excel 原始值、补充后的标准值、操作人和操作时间。
- 每件资产分别写入资产履历，并写入系统操作日志。
- 全部空缺字段补齐后，资产自动变为“完整”。

专业词解释：直接生效表示保存后立即更新资产，不等待审批；限制为从空值首次补齐，可以避免借补充功能绕过正常变更流程。

### 14.62 资产资料修改权限和审批

确认结果：修改资产信息不需要审批；除资产编码外，超级管理员默认可以修改全部资产信息，资产管理员和其他角色需要由超级管理员授权。

系统处理方式：

- 拥有 `asset:update` 权限且数据范围覆盖该资产时，可以修改允许编辑的资产资料，保存后直接生效。
- 超级管理员默认可以直接修改除资产编码外的全部资产字段。
- 资产管理员和自定义角色需要 `asset:update` 基础权限及对应字段权限。
- 状态、使用人、使用部门和已有存放地点默认通过业务流程变更，但超级管理员或获得对应字段权限的角色可以直接修正。
- 资产分类、金额、购入日期、规格型号、序列号、来源、单位、责任管理员、备注和扩展属性等允许字段可以直接修改。
- 修改资产分类不会重新生成资产编码。
- 修改金额还需要 `asset:amount:update` 权限；查看金额继续需要 `asset:amount:view` 权限。
- 每次修改保存字段级变更前后值、操作人和时间，并写入资产履历和操作日志。

待补充权限确认结果：超级管理员和资产管理员默认拥有 `asset:data:complete` 权限，自定义角色由超级管理员分配；普通员工默认没有。

专业词解释：资产修改权限决定能否编辑普通资料，数据权限决定能修改哪些资产，字段权限还能单独限制金额等敏感字段。

### 14.63 超级管理员和字段修改权限

确认结果：除资产编码外，超级管理员默认可以修改全部资产信息；资产管理员和其他角色需要由超级管理员授权后才能修改。

系统处理方式：

- 超级管理员不受普通资产字段权限和数据范围限制。
- 其他角色先需要 `asset:update` 基础权限，再按照字段分配具体修改权限。
- 状态、使用人、使用部门和存放地点仍建议通过正常业务流程变更，但拥有对应字段权限时允许直接修正。
- 直接修改不走审批，保存后立即生效。
- 修改业务字段时必须填写原因并二次确认。
- 系统继续执行数据一致性校验，不能生成“在用但没有使用人”等不符合规则的数据。
- 所有修改记录字段级前后值、操作人、时间和原因，并写入资产履历及操作日志。

字段权限建议：

```text
asset:status:update     修改资产状态
asset:user:update       修改使用人和自动关联部门
asset:location:update   修改存放地点
asset:amount:update     修改采购金额
asset:category:update   修改资产分类
asset:manager:update    修改资产责任管理员
```

专业词解释：字段权限表示可以只允许某个角色修改特定字段，例如允许修改责任管理员，但不能修改金额和资产状态。

### 14.64 资产编码绝对不可修改

确认结果：资产编码从生成时起任何人都不能修改，超级管理员也不例外。

系统处理方式：

- 资产编码不出现在普通编辑和字段授权列表中。
- 后端所有修改接口都忽略或拒绝资产编码变更。
- 待入库申请的所属公司或资产分类填写错误时，撤回或拒绝原申请后重新创建。
- 原申请生成的编码标记为“未入库作废”，永久不复用。
- 已正式入库的资产即使所属公司或分类以后变化，仍保留原资产编码。
- 二维码、条形码、主附关系和历史记录始终以这个不可变编码关联展示。

专业词解释：绝对不可修改表示该字段没有任何修改入口或特殊权限。资产编码是资产的永久身份证号，不会因为资料变更而重新编号。

### 14.65 资产批量编辑

确认结果：第一版增加资产批量编辑功能，批量编辑不需要审批。

系统处理方式：

- 用户多选资产后，可以给允许编辑的资料字段批量设置相同内容。
- 使用人、使用部门、状态和已有存放地点不进入普通批量编辑，继续通过对应业务流程处理。
- 资产编码永远不能修改。
- 操作人需要 `asset:batch:update`、对应字段权限和全部所选资产的数据权限。
- 金额批量修改还需要 `asset:amount:update` 权限。
- 保存前显示影响范围和修改前后内容，并进行二次确认。
- 整批全部成功或全部失败，每件资产分别写入履历并关联同一个批量操作编号。
- 选择主资产时不自动修改附属资产，需要一起修改时由操作人明确勾选。
- 主附资产转移仍按照转移流程自动一起处理。

专业词解释：批量编辑适合一次整理多件资产的相同资料，数据库事务用于防止只修改成功其中一部分。

### 14.66 批量编辑主附资产范围

确认结果：普通批量编辑只修改操作人明确选中的资产，选择主资产时不自动带上附属资产。

系统处理方式：

- 资产列表可以展开主资产查看附属资产。
- 需要一起修改时，由操作人逐项勾选附属资产。
- 未勾选的附属资产保持原资料不变。
- 保存前预览明确区分主资产和附属资产。
- 资产转移仍使用已确认的主附资产一起转移规则。

专业词解释：显式选择表示系统只处理用户明确勾选的资产，避免主资产和附属资产资料不同却被意外统一覆盖。

### 14.67 主附资产维修范围

确认结果：主资产维修时不自动维修附属资产，采用选择性联动。

系统处理方式：

- 发起主资产维修时展示全部附属资产。
- 默认只选择主资产，管理员可以勾选需要一起维修的附属资产。
- 被选资产进入同一张维修单，未选资产状态保持不变。
- 主附关系在维修期间不改变。
- 维修完成时，每件资产恢复各自维修前的状态。
- 每件资产分别写入维修履历，并关联同一个维修单号。

专业词解释：选择性联动表示系统主动展示关联资产，但不会自动处理，只有明确选中的附属资产才一起进入维修流程。

### 14.68 主资产报废时附属资产去向

确认结果：主资产报废前必须为每件附属资产选择去向，不能让正常附属资产继续挂在已报废主资产下面。

系统处理方式：

- 可选择与主资产一起报废、解除关联变为普通资产，或转挂到另一台有效主资产。
- 任意附属资产没有选择去向时，主资产报废申请不能提交。
- 一起报废的资产进入同一张申请，每件资产分别填写报废回收金额和备注。
- 整张申请统一审批。
- 审批通过后，主资产报废和所有附属资产去向一起执行，全部成功或全部失败。
- 每件资产分别写入履历并关联同一个报废申请编号。

专业词解释：附属资产去向校验用于保证主资产报废后，每件附属资产都有明确状态和关系，不会形成挂在已报废资产下的无效数据。

### 14.69 附属资产单独报废

确认结果：附属资产拥有独立资产编号。单独报废附属资产时，先直接解除主附关系，再把它作为普通资产单独报废。

系统处理方式：

- 主附关系只用于入库后的展示、统计、盘点和联动操作，附属资产仍是完整的独立资产。
- 发起附属资产报废前，操作人先解除它与主资产的当前挂接关系。
- 解除关系后，附属资产变为普通资产，不需要把主资产加入报废申请。
- 附属资产按照普通资产报废流程，单独填写报废原因、回收金额和附件并单独审批。
- 主资产状态、使用信息和其它业务流程不受影响。
- 解除关系记录保存原主资产编码、附属资产编码、操作人、时间和原因，便于查询历史关系。

专业词解释：主附关系是两件独立资产之间的挂接关系，不是资产编号的一部分。解除关系不会删除资产，只是取消当前的主附展示和联动。

### 14.70 主附关系维护权限

确认结果：主附关系维护不需要审批；超级管理员默认可以操作，其他角色需要由超级管理员授权。

系统处理方式：

- 权限编码为 `asset:relation:update`。
- 操作人必须同时拥有主资产和附属资产的数据权限。
- 挂接、转挂和解除关系保存后直接生效。
- 操作时必须填写原因。
- 主资产和附属资产分别写入关系变更履历，并关联同一个操作编号。
- 已报废资产不能新建主附关系。

专业词解释：关系维护权限只控制两件独立资产之间的挂接，不允许修改资产编码，也不会自动获得其它资产编辑权限。

### 14.71 单层主附关系

确认结果：主附关系只允许一层，不支持附属资产下面继续挂其它资产。

系统处理方式：

- 一台主资产可以挂多件附属资产。
- 一件附属资产同一时间只能挂在一台主资产下面。
- 主资产不能同时作为另一台资产的附属资产。
- 附属资产不能再成为其它资产的主资产。
- 调整资产身份时，需要先解除原关系，再重新挂接。
- 后端必须检查循环关系和多层关系，不能只依赖页面限制。

专业词解释：单层主附关系只有主资产和附属资产两级，可以避免多层嵌套造成转移、盘点、维修和报废范围不清楚。

### 14.72 挂接后的信息跟随规则

确认结果：挂接时不校验主附资产原有使用信息是否一致，附属资产直接同步主资产信息；挂接后使用信息持续跟随，维修和报废状态分别处理。

系统处理方式：

- 挂接或转挂成功时，附属资产的使用人、使用部门、存放地点和当前状态立即同步为主资产的值。
- 不要求附属资产在挂接前与主资产信息一致。
- 挂接后，主资产的使用人、部门或地点发生变化时，全部附属资产自动同步。
- 附属资产挂接期间不能单独修改使用人、部门和地点；需要单独处理时先解除关系。
- 资产状态只在建立关系的当下同步一次，之后维修和报废等状态变化按每件资产流程处理。
- 附属资产有未完成流程或业务锁定时不能挂接，防止覆盖正在维修或审批中的状态。
- 挂接同步保存附属资产修改前后值，并写入主资产和附属资产履历。

专业词解释：持续跟随表示附属资产的使用归属和位置始终以主资产为准；状态独立处理可以保留选择性维修和单独报废能力。

### 14.73 解除关系后的资产信息

确认结果：解除主附关系时只取消挂接，附属资产保留当时的使用人、使用部门、存放地点和状态。

系统处理方式：

- 附属资产从“附属资产”变为“普通资产”。
- 不自动清空使用人、部门和地点。
- 不自动把资产状态改为闲置。
- 解除后可以单独发起转移、退库、维修或报废。
- 为单独报废而解除关系时，可以直接进入普通资产报废流程。
- 履历保存原主资产编码、解除时间、操作人、原因和解除时的资产信息。

专业词解释：解除关系保留现状表示系统只取消主附关联，不同时改变资产当前的使用归属和业务状态。

### 14.74 跨公司主附关系

确认结果：允许不同所属公司的资产建立主附关系。

系统处理方式：

- 主资产和附属资产各自保留原所属公司和资产编码。
- 建立关系时显示所属公司不同的提醒，但不阻止操作。
- 操作人必须同时拥有两件资产的数据权限。
- 按公司统计时，每件资产仍计入自己的所属公司。
- 主资产转移时，附属资产跟随使用人、部门和地点，但所属公司不改变。
- 主附展示需要分别显示每件资产的所属公司，避免误认为所有权发生转移。

专业词解释：跨公司主附关系只表示这些资产组合使用，不改变资产所有权、编码和按公司统计的结果。

### 14.75 主附资产逐件盘点

确认结果：扫描主资产后，附属资产不会自动算作已盘点，主资产和每件附属资产都需要分别扫码。

系统处理方式：

- 每个独立资产编码对应一条独立盘点结果。
- 扫描主资产后展示附属资产清单和整套盘点进度。
- 未扫描的附属资产保持“待盘点”。
- 扫描附属资产时提示所属主资产。
- 盘点报告同时提供单件资产结果和整套资产完成情况。
- 主资产已扫描但附属资产未找到时，附属资产按照自己的盘点结果处理。

专业词解释：逐件盘点用于确认每件实物都真实存在，避免看到主资产后误认为键盘、显示器等附属资产也都在现场。

### 14.76 盘点不校验主附关系

确认结果：盘点时不校验主资产和附属资产的关系，只关注每件独立资产是否存在。

系统处理方式：

- 主资产和附属资产继续按照各自编码逐件扫码。
- 不要求盘点人员确认附属资产现场属于哪台主资产。
- 不增加“主附关系异常”盘点结果。
- 盘点过程中和盘点完成后都不会因为扫码自动修改主附关系。
- 主附关系需要调整时，使用独立的关系维护功能。

专业词解释：盘点与关系维护分离表示盘点只核对实物，主附资产如何挂接由管理员在其他功能中单独处理。

### 14.77 使用人自主盘点

确认结果：盘点需要支持使用人自主盘点，每件资产提交时必须填写实际存放地点并上传现场照片。

系统处理方式：

- 盘点任务按使用人把个人资产分配给本人。
- 员工在手机端逐件扫码确认自己名下资产。
- 每件资产都必须选择或填写现场存放地点，并上传盘点照片后才能提交。
- 员工只能看到分配给自己的资产。
- 管理员可以查看每名员工的完成进度、地点、照片和提交时间。
- 提交的地点和照片先进入盘点结果，不直接修改正式资产台账。
- 主资产和附属资产分别盘点，不检查主附关系是否符合现场情况。

专业词解释：自主盘点把实物确认工作分配给实际使用人，照片和地点作为盘点证据，管理员最后统一查看和处理结果。

### 14.78 盘点照片来源设置

确认结果：管理员创建盘点任务时，可以选择强制调用手机相机拍照，也可以允许从相册选择照片。

系统处理方式：

- 任务设置为 `CAMERA_ONLY` 时，盘点页面只显示手机相机拍摄入口。
- 任务设置为 `CAMERA_OR_ALBUM` 时，使用人可以现场拍照或从相册选择。
- 照片来源设置保存在盘点任务中，所有参与人执行同一标准。
- 任务开始后不能修改照片来源模式；确需变更时由管理员结束原任务并重新创建。
- 系统记录上传人、上传时间、资产和盘点任务，不把盘点照片混入普通资产照片。

专业词解释：照片来源模式是盘点任务的固定规则。强制相机适合要求现场证明的盘点，允许相册适合补传已经拍摄的照片。

### 14.79 盘点照片数量

确认结果：管理员创建任务时设置每件资产最少上传 1 至 3 张照片，默认 1 张；每件资产最多上传 5 张。

系统处理方式：

- 最低照片数量只能选择 1、2 或 3。
- 未达到最低数量时不能提交该资产盘点结果。
- 达到 5 张后不允许继续上传。
- 每张照片单独关联盘点任务、资产和提交人。
- 任务开始后不能修改最低照片数量。

专业词解释：照片数量校验用于确保每件资产都有符合任务要求的现场证据，同时限制最大数量，避免上传过多重复文件。

### 14.80 盘点实际地点填写

确认结果：盘点实际地点必须填写，同时支持标准地点和临时地点。

系统处理方式：

- 优先从层级地点字典中选择启用且允许存放资产的标准地点。
- 现场地点未建档时，可以选择“临时地点”并填写完整文字描述。
- 标准地点和临时地点都不能留空。
- 临时地点不会自动写入地点字典。
- 管理员在盘点结果中查看临时地点，并决定是否新增标准地点或如何处理。
- 盘点记录保留提交时的地点文字快照。

专业词解释：临时地点用于记录尚未维护到标准字典中的现场位置，地点文字快照用于保留本次盘点实际填写的内容。

### 14.81 实物结果与地点差异分开

确认结果：员工扫到资产并提交符合要求的地点和照片后，实物结果记为“已找到”；地点不一致只做差异提示。

系统处理方式：

- 实物结果使用“已找到、盘亏、盘盈”。
- 标准地点与台账地点不同，标记为“地点有差异”。
- 使用临时地点时，标记为“需要管理员复核”。
- 地点差异不影响资产“已找到”的结果，也不算盘点失败。
- 盘点过程中不自动修改正式资产地点。
- 任务完成后，管理员可以筛选地点差异并决定更新或保留台账地点。

专业词解释：把实物结果和地点差异分开，可以同时表达“设备确实存在”和“设备位置需要修正”这两件事。

### 14.82 自主盘点不检查使用人和状态

确认结果：自主盘点只确认实物是否存在，不检查使用人和资产状态差异。

系统处理方式：

- 系统按照台账使用人把资产分配给对应员工。
- 员工只能提交“已找到”或“盘亏”。
- 已找到时必须填写实际地点并上传符合任务要求的照片。
- 点击“盘亏”后选择盘亏理由，不要求上传实物照片或填写实际地点。
- 员工不能在盘点页面修改使用人、使用部门和资产状态。
- 盘点不生成“使用人不符”和“状态异常”结果。
- 管理员在任务结束后根据盘点情况，通过领用、退库、转移、维修或报废等正常流程处理台账。

专业词解释：盘点维度表示本次盘点具体检查哪些内容。本系统的自主盘点维度是实物是否存在，地点只作为附加信息，使用人和状态不在盘点中校验。

### 14.83 自主盘点直接标记盘亏

确认结果：使用人找不到资产时，可以直接点击“盘亏”，然后选择盘亏理由。

系统处理方式：

- 自主盘点页面提供“已找到”和“盘亏”两个结果入口。
- 已找到时必须填写实际地点并上传符合任务要求的照片。
- 盘亏时进入理由选择页面，不要求上传实物照片或填写实际地点。
- 盘亏可以填写补充说明。
- 员工提交盘亏只产生盘点结果，不把资产台账状态改成“丢失”。
- 管理员在盘点任务完成后统一复核盘亏资产并记录处理结果。

专业词解释：盘亏是账面存在资产、盘点时没有找到实物的结果，只属于盘点记录，不是资产台账状态。

### 14.84 盘亏理由

确认结果：员工提交盘亏时必须选择盘亏理由，理由使用可维护字典。

系统处理方式：

- 默认提供不在本人处、借给他人、送修中、暂时找不到、疑似丢失和其他。
- 选择“借给他人”时可以填写借用人。
- 选择“其他”时必须填写详细说明。
- 管理员可以新增、排序、启用和停用理由。
- 已被使用的理由不能删除，停用后继续显示在历史盘点记录中。
- 盘亏理由用于统计和管理员复核，不自动修改资产台账状态。

专业词解释：盘亏原因分类用于区分资产暂时不在、借出、送修和疑似丢失等情况，便于管理员采用不同后续处理方式。

### 14.85 第一版飞书登录和人员同步

确认结果：飞书单点登录和人员、部门同步必须在第一版正式投入公司使用前完成。

系统处理方式：

- 本地开发继续使用本地超级管理员账号。
- 开发环境可以启用测试员工登录，验证自主盘点、本人资产和退库等员工功能。
- 测试员工登录由环境变量控制，正式环境必须关闭。
- 正式员工通过飞书单点登录，系统根据飞书身份确定本人资产和权限。
- 员工、部门和上下级关系从飞书同步。
- 本地超级管理员继续保留，用于系统维护和飞书异常时的应急管理。

专业词解释：开发环境模拟登录只用于本地功能测试；正式环境必须使用飞书身份认证，确保自主盘点提交人是真实员工。

### 14.86 飞书自主盘点通知

确认结果：发布自主盘点任务后，通过飞书消息卡片通知员工；不做自动提醒，保留管理员手动催办。

系统处理方式：

- 消息卡片显示任务名称、截止时间和员工待盘点资产数量。
- 卡片提供“开始盘点”入口，点击后打开飞书内手机页面。
- 系统只在任务发布时主动发送一次通知，不定时重复提醒。
- 管理员可以筛选未完成人员并手动催办。
- 手动催办不设置时间限制，可以连续发送。
- 通知和催办都记录发送人、接收人、发送时间、发送结果和任务编号。
- 飞书消息只用于通知，不创建飞书审批单。

专业词解释：飞书消息卡片是带有任务信息和操作入口的通知；它与飞书审批不同，不需要员工在审批中心处理。

### 14.87 盘点催办不限制频率

确认结果：盘点手动催办不设置时间间隔或次数限制，可以连续催办。

系统处理方式：

- 有权限的人员可以随时对未完成员工发送催办消息。
- 同一个任务对同一个员工可以连续催办，系统不做一小时限制。
- 支持单人催办和批量催办。
- 每次催办仍记录操作人、接收人、发送时间、发送结果和任务编号。
- 审批催办仍然保持已确认的每小时一次规则，盘点催办使用独立规则。

专业词解释：盘点催办不限频表示系统不会因为刚刚发送过消息而阻止再次发送；完整发送记录用于后续查询。

### 14.88 盘点批量催办确认

确认结果：单人催办直接发送，批量催办需要二次确认。

系统处理方式：

- 批量催办弹窗显示接收人数和员工名单。
- 操作人点击“确认发送”后才调用飞书消息接口。
- 发送完成后显示成功人数、失败人数和失败人员。
- 失败人员可以立即重新催办，不受时间限制。
- 只有任务负责人、资产管理员或拥有 `inventory:urge` 权限的人员可以催办。
- 批量发送和每名员工的发送结果都需要记录日志。

专业词解释：批量操作二次确认可以减少误点导致的大范围消息发送，同时保留每名员工的实际发送结果。

### 14.89 盘点软截止时间

确认结果：盘点截止时间只标记逾期，不自动关闭任务；员工在管理员手动结束任务前仍可继续提交。

系统处理方式：

- 到达截止时间后，任务和未完成人员显示“已逾期”。
- 截止后提交的盘点结果标记为“逾期提交”。
- 管理员手动结束任务前，员工仍可以扫码和提交。
- 到期不会自动把未提交资产判定为盘亏。
- 管理员可以在任务结束前修改截止时间，并记录修改日志。
- 任务手动结束后不再接受员工提交。
- “结束收集”和“完成盘点”是两个独立操作。
- 盘点管理员结束收集后，任务进入异常处理中，员工不能再提交，未提交资产标记为“未完成盘点”。
- 管理员处理盘亏、地点差异、临时地点和未完成资产后，才可以完成盘点。
- 所有异常和未完成资产必须有处理结果，才能正式完成任务并生成最终报告。
- 任务正式完成后数据锁定，不能继续修改盘点结果。
- 任务处于异常处理中且尚未正式完成时，盘点管理员或超级管理员可以局部重新开放收集。
- 重新开放时选择具体员工或资产、填写原因并设置新的截止时间。
- 已完成的正常结果保持不变，只恢复选中资产的提交权限。
- 系统通过飞书通知被重新开放的员工，并记录操作人、时间、原因和范围。
- 已正式完成的任务不能重新开放，需要新建盘点任务。

最终盘点报告规则：

- 正式完成盘点后生成一个多工作表 Excel 报告。
- 工作表包括盘点汇总、资产明细、盘亏明细、地点差异、临时地点、未完成盘点、无需盘点、管理员代确认和人员完成情况。
- 汇总统计应盘、已盘、盘亏、盘盈、未完成和无需盘点数量。
- 分别统计员工真实扫码和管理员直接标记数量。
- 分别统计正常提交、逾期提交和重新开放后提交数量。
- 人员完成情况显示每名员工的应盘、完成、盘亏和完成时间。
- 资产明细保存实际地点、照片数量、提交人、提交方式和最终处理结果。
- 照片不直接嵌入 Excel 原图，报告提供需要登录和权限校验的查看链接。
- 超级管理员可以导出所有盘点任务报告。
- 当前任务的盘点管理员可以导出自己负责的任务报告。
- 自定义角色需要 `inventory:export` 权限和对应数据范围。
- 普通盘点参与员工只能查看自己的提交结果，不能导出完整任务报告。
- 导出人没有 `asset:amount:view` 权限时，报告不包含资产金额。
- 每次导出记录导出人、时间、任务编号和文件名称。

报告工作表建议：

```text
盘点汇总
资产明细
盘亏明细
地点差异
临时地点
未完成盘点
无需盘点
管理员代确认
人员完成情况
```

盘点任务状态建议：

```text
DRAFT       草稿
IN_PROGRESS 进行中
OVERDUE     已逾期，仍可提交
REVIEWING   已结束收集，异常处理中
COMPLETED   已完成
```

专业词解释：软截止时间用于统计谁没有按时完成，但允许员工继续补交；任务是否真正停止由管理员手动决定。

### 14.90 未提交资产处理

确认结果：管理员结束任务时，未提交资产标记为“未完成盘点”，不自动判定盘亏。

系统处理方式：

- 结束任务前显示未完成人数和资产数量，并进行二次确认。
- 任务结束后，未提交资产统一标记为 `UNSUBMITTED`。
- 管理员确认确实找不到后，可以转为 `LOSS` 并选择盘亏理由。
- 因员工离职、分配错误等无需盘点时，可以标记为 `EXEMPTED` 并填写原因。
- 支持逐件处理和批量处理。
- 未完成、盘亏和无需盘点分别统计并保留处理记录。

专业词解释：未提交与盘亏分离可以避免把“员工没有操作”错误理解成“资产已经丢失”。

### 14.91 盘点管理员和结束权限

确认结果：发起资产盘点时设置盘点管理员；任务盘点管理员可以结束对应任务，超级管理员可以直接结束任何任务。

系统处理方式：

- 创建盘点任务时必须选择盘点管理员。
- 盘点管理员只管理被分配的盘点任务。
- 盘点管理员可以查看进度、催办未完成人员和手动结束任务。
- 超级管理员可以查看并结束所有盘点任务，无需被单独分配。
- 资产管理员角色本身不自动获得结束所有任务的权限，未被分配时不能结束该任务。
- 结束前仍需显示未完成人数和资产数量并二次确认。
- 结束操作记录操作人、时间和结束时的任务统计。

专业词解释：任务级管理员是创建任务时指定的负责人，只管理这一次盘点；超级管理员拥有全局处理能力。

### 14.92 多名盘点管理员

确认结果：一个盘点任务可以设置多名盘点管理员，但至少需要一名。

系统处理方式：

- 多名盘点管理员共同查看任务进度、执行催办和处理任务。
- 任意一名任务管理员都可以手动结束任务。
- 结束前显示其他任务管理员、未完成人数和未完成资产数量，并二次确认。
- 系统记录实际结束任务的管理员和操作时间。
- 超级管理员始终可以查看和结束任务，不需要加入管理员名单。

专业词解释：多负责人协作表示同一个盘点任务可以由多名管理员共同跟进，避免单一负责人请假时任务无法处理。

### 14.93 盘点管理员动态调整

确认结果：盘点任务开始后允许增加或移除盘点管理员，但必须始终至少保留一名。

系统处理方式：

- 超级管理员和当前任务管理员可以调整管理员名单。
- 最后一名任务管理员不能移除自己。
- 新增管理员后通过飞书消息通知对方。
- 被移除管理员立即失去该任务的管理和结束权限。
- 被移除管理员之前的催办、处理等历史记录继续保留。
- 调整不需要审批，但记录操作人、时间和变更前后名单。

专业词解释：任务负责人动态调整用于人员请假、离职或工作交接，管理员名单变化不会影响员工已经提交的盘点结果。

### 14.94 盘点管理员可选人员

确认结果：任何飞书同步且在职的真实员工都可以被设置为某个任务的盘点管理员。

系统处理方式：

- 不要求被选人员原本拥有资产管理员角色。
- 被选中后只获得指定盘点任务的查看、催办、处理和结束权限。
- 不自动获得全公司资产、金额查看或其它盘点任务权限。
- 公共使用对象没有登录能力，不能被设置为盘点管理员。
- 离职或停用员工不能再被选择。
- 进行中任务的管理员离职或停用时，需要由超级管理员或其他任务管理员更换负责人。

专业词解释：任务级临时权限只在一项具体任务中生效，任务结束后不会继续拥有该任务的操作权限。

### 14.95 公共资产盘点责任人

确认结果：公共资产按地点分组，由盘点管理员分配一名或多名真实员工负责盘点。

系统处理方式：

- 公共使用对象不登录，不能自行提交盘点。
- 任务管理员按照存放地点把公共资产分组并指定真实员工。
- 被指定员工只能看到本任务分配给自己的公共资产。
- 盘点仍需逐件扫码、填写实际地点并上传符合任务要求的照片。
- 多人负责同一组时，第一条有效结果计入进度，重复结果保留但不重复统计。
- 盘点管理员和超级管理员也可以直接盘点公共资产。
- 任务分配不会改变公共资产使用人，也不会给员工增加长期资产权限。

专业词解释：公共资产盘点责任人只负责本次现场核对，不是资产使用人，也不是系统中的永久资产管理员。

### 14.96 盘点责任转交

确认结果：员工无法自主盘点时，任务管理员可以把本次盘点责任转交给其他在职员工。

系统处理方式：

- 转交只影响当前盘点任务，不修改资产台账中的使用人。
- 原责任人未提交时可以直接转交。
- 转交后原责任人不能再提交，新责任人获得该资产的盘点权限。
- 已提交结果需要先由任务管理员作废，才能重新分配。
- 原责任人和新责任人都通过飞书收到转交通知。
- 转交必须填写原因，并记录操作人、时间和前后责任人。

专业词解释：盘点责任转交只是更换本次现场核对人员，不属于资产转移，也不会改变资产的正式使用归属。

### 14.97 盘点结果撤回和修改

确认结果：任务结束前，员工可以撤回尚未确认的结果重新提交；盘点管理员可以退回修改。

系统处理方式：

- 员工只能撤回自己提交且状态为“待异常复核”的结果。
- 撤回后可以重新填写地点、照片或盘亏理由。
- 盘点管理员退回时必须填写原因，系统通过飞书通知员工。
- 正常结果由系统自动确认，填写错误时由盘点管理员退回修改。
- 已确认异常结果和已结束任务中的结果不能由员工修改。
- 需要转交责任人时，盘点管理员先作废已提交结果，再重新分配。
- 所有旧版本、旧照片、撤回原因、退回原因和重新提交时间永久保留。

专业词解释：盘点结果版本表示每次重新提交都生成新版本，旧数据不覆盖，管理员可以查看完整修改过程。

### 14.98 正常盘点自动确认

确认结果：正常盘点结果不需要盘点管理员批量确认；只有实际扫描资产码后才能提交，盘点管理员只跟进异常结果。

系统处理方式：

- 员工必须扫描资产标签上的二维码或条形码，不能只在资产清单中点击“已找到”。
- 扫描成功后仍需填写实际地点并上传任务要求数量的照片。
- 满足全部要求后，正常结果自动记为有效并进入已完成数量。
- 员工点击提交后，页面立即显示“完成盘点”。
- 不提供正常结果批量确认功能。
- 盘亏、地点差异、临时地点等结果进入异常清单，由盘点管理员处理。
- 正常结果填写错误时，由盘点管理员退回重新盘点。

专业词解释：正常结果自动确认表示系统根据扫码、地点和照片规则直接接受结果，管理员把精力集中在异常资产上。

### 14.99 真实扫码和管理员直接标记

确认结果：员工只能通过真实扫描二维码或条形码完成盘点；盘点管理员和超级管理员可以勾选任务资产后直接标记为已盘点。

员工处理方式：

- 不提供手动输入资产编码完成盘点的入口。
- 不能只在个人资产清单中点击“已盘点”。
- 必须真实扫码、填写实际地点并上传任务要求数量的照片。
- 点击提交后立即计入完成进度并显示“完成盘点”。
- 标签损坏或无法扫码时，需要联系盘点管理员处理。

管理员处理方式：

- 任务盘点管理员和超级管理员可以在本任务资产清单中勾选一件或多件资产。
- 点击“标记已盘点”后，选中资产直接计入完成进度。
- 不要求填写地点或上传照片，但必须填写直接标记原因。
- 批量标记时可以给全部选中资产使用同一个原因。
- 系统记录处理方式为 `ADMIN_MARKED`，并保存操作人、时间和资产清单。
- 非本任务范围资产不能通过管理员勾选方式标记完成。
- 盘点报告单独显示真实扫码和管理员代确认的数量及占比。

专业词解释：真实扫码表示必须由手机摄像头识别二维码或条形码；管理员直接标记是处理标签损坏或特殊情况的管理入口，两种方式在日志中明确区分。

### 14.100 管理员直接标记要求

确认结果：盘点管理员和超级管理员直接标记资产已盘点时，不需要扫码、地点或照片，但必须填写原因。

系统处理方式：

- 单件和批量标记都需要填写原因。
- 批量操作可以给全部选中资产使用相同原因。
- 标记后立即计入已完成盘点数量。
- 系统保存管理员、时间、原因和资产清单。
- 盘点报告分别统计员工真实扫码和管理员直接标记结果。
- 管理员直接标记不生成或伪造现场照片和实际地点。

专业词解释：管理员代确认是特殊处理方式，保留原因并单独统计可以清楚区分哪些资产经过了员工现场扫码。

### 14.101 结束收集和完成盘点

确认结果：停止员工提交和盘点正式完成分为两个步骤。

系统处理方式：

- 任务处于进行中或逾期状态时，员工可以继续扫码提交。
- 盘点管理员点击“结束收集”后，任务进入“异常处理中”，员工不能再提交。
- 尚未提交的资产标记为“未完成盘点”。
- 管理员继续处理盘亏、地点差异、临时地点和未完成资产。
- 所有异常都有处理结果后，才能点击“完成盘点”。
- 完成后生成最终报告并锁定任务数据。
- 超级管理员可以结束收集和完成任何盘点任务。

专业词解释：收集阶段与结案阶段分离，可以先停止新增提交，再集中处理异常，确保最终报告中的每件资产都有明确结果。

### 14.102 局部重新开放盘点

确认结果：盘点任务结束收集后、正式完成前，允许局部重新开放指定员工或资产补交。

系统处理方式：

- 盘点管理员和超级管理员可以执行重新开放。
- 操作时选择具体员工或资产，不恢复整个任务的全部提交权限。
- 必须填写原因并设置新的截止时间。
- 已完成正常结果保持不变，只恢复选中资产的待提交状态。
- 系统通过飞书通知获得补交权限的员工。
- 操作日志记录操作人、时间、原因、资产和员工范围。
- 已正式完成任务不能重新开放，只能创建新的盘点任务。

专业词解释：局部重新开放只让少量漏交人员或资产重新进入收集阶段，不影响其他已经完成的盘点结果。

### 14.103 最终盘点报告

确认结果：最终盘点报告使用一个包含多个工作表的 Excel 文件。

系统处理方式：

- 盘点汇总展示任务信息和各类数量统计。
- 独立工作表展示资产明细、盘亏、地点差异、临时地点、未完成、无需盘点、管理员代确认和人员完成情况。
- 报告区分员工真实扫码与管理员直接标记。
- 报告区分正常提交、逾期提交和重新开放后提交。
- 资产明细包含地点、照片数量、提交人、提交方式和处理结果。
- 照片使用受登录和权限保护的查看链接，不直接嵌入大量原图。

专业词解释：多工作表盘点报告把汇总和不同类型明细分开，既方便管理层查看总体结果，也方便管理员逐条核对异常。

### 14.104 盘点报告导出权限

确认结果：超级管理员和当前任务盘点管理员可以导出报告；自定义角色按权限和数据范围导出，普通参与员工不能导出完整报告。

系统处理方式：

- 超级管理员可以导出全部盘点任务。
- 盘点管理员只能导出自己负责的任务。
- 自定义角色需要 `inventory:export` 权限，并受数据范围限制。
- 普通员工只能查看自己的提交记录。
- 没有 `asset:amount:view` 权限时，导出文件不包含金额。
- 导出操作记录导出人、时间、任务编号和文件名称。

专业词解释：导出权限决定能否生成文件，字段权限继续决定文件中是否包含金额等敏感信息。

### 14.105 盘点任务创建权限

确认结果：超级管理员和资产管理员默认可以创建盘点任务，其他角色需要 `inventory:create` 权限。创建任务时必须指定至少一名盘点管理员。

专业词解释：创建权限只控制发起任务，任务后续管理权限由盘点管理员名单决定。

### 14.106 盘点任务范围快照

确认结果：任务发布后固定资产清单、使用人和责任人分配，后续台账变化不自动改变当前任务。范围错误时取消原任务并重新创建。

专业词解释：任务快照用于保证同一次盘点从开始到结束使用同一份应盘清单。

### 14.107 取消盘点任务

确认结果：盘点管理员和超级管理员可以取消未正式完成的任务，必须填写原因；取消后保留结果、照片和日志，任务不能删除。已完成任务不能取消。

专业词解释：取消而不删除可以停止错误任务，同时保留已经发生的操作证据。

### 14.108 任务外资产扫码

确认结果：员工扫描到不属于本人当前任务的资产时不能提交完成，系统保留扫码记录并进入异常清单，由盘点管理员决定是否作为盘盈。

专业词解释：任务外扫码表示资产存在于系统，但不在当前员工的任务分配范围中。

### 14.109 盘点照片水印

确认结果：盘点照片自动添加任务名称、资产编码、提交人和提交时间水印，不采集 GPS 定位。

专业词解释：照片水印用于说明照片属于哪次任务和哪件资产，同时避免收集不必要的员工定位信息。

### 14.110 盘点照片格式和压缩

确认结果：支持 JPG、PNG 和 HEIC；单张原文件最大 10MB，上传后转换并压缩到约 2MB，不长期保留未压缩原图。

专业词解释：图片压缩可以降低手机上传时间和服务器存储占用。

### 14.111 飞书组织定时同步

确认结果：飞书人员和部门每天凌晨自动同步一次，同时支持管理员手动同步。失败时保留原因并允许重新执行，不直接删除历史记录。

专业词解释：定时同步会自动读取飞书中的人员和部门变化，手动同步用于需要立即更新的情况。

### 14.112 离职员工处理

确认结果：飞书同步发现员工离职或停用后立即禁止登录，但保留人员和历史数据，并生成离职人员名下资产清单供管理员办理退库、转移和任务交接。

专业词解释：逻辑停用只关闭账号使用能力，不删除员工过去的领用、盘点和操作记录。

### 14.113 内网域名和 HTTPS

确认结果：正式部署使用公司内网域名和 HTTPS，并由 Nginx 转发到 FastAPI。该配置用于飞书登录、飞书内页面和手机摄像头访问。

专业词解释：HTTPS 对浏览器与服务器之间的数据进行加密，也是正式环境使用手机摄像头的重要条件。

### 14.114 数据备份和恢复测试

确认结果：MySQL 和本地文件每天自动备份，默认保留 30 天；数据库与附件使用同一批次备份，每月执行一次恢复测试。

专业词解释：恢复测试是把备份实际还原到测试环境，验证数据库记录和照片、附件可以一起恢复。

### 14.115 个人资产领用发起方式

确认结果：个人资产默认由资产管理员创建领用单并指定员工，员工通过飞书确认收到后资产才变为在用；默认不增加部门负责人审批。

专业词解释：发放式领用是管理员发放设备，员工负责确认实物已经收到。

### 14.116 公共资产投入使用

确认结果：公共资产由资产管理员选择公共使用对象和地点，在系统内直接确认；允许提交人与确认人为同一人，不走飞书。

专业词解释：公共资产没有可登录的个人使用人，因此由管理员完成投入使用确认。

### 14.117 资产转移默认审批

确认结果：资产转移默认在系统内走一层资产管理员审批，正式环境不能自审；主资产和附属资产一起转移。

专业词解释：调拨审批用于确认新的使用人、部门和存放地点。

### 14.118 维修发起和完成确认

确认结果：有权限的管理员可以直接开始维修，不需要审批；结束维修必须由管理员确认，允许同一人发起和确认。

专业词解释：维修闭环表示系统完整记录送修、维修中和确认完成的全过程。

### 14.119 报废默认双层审批

确认结果：报废默认先由资产管理员审批，再由财务审批；报废申请人不能审批自己的申请。

专业词解释：报废双审由资产管理和财务分别确认实物处置及回收金额。

### 14.120 不做使用期限提醒

确认结果：保留使用期限和预计到期日期，但不发送到期提醒，不自动报废，也不改变资产状态。

专业词解释：使用期限只作为资料展示，不触发系统业务动作。

### 14.121 员工部门变化同步资产

确认结果：飞书同步发现员工部门变化后，自动更新其名下资产的使用部门，不修改所属公司和资产编码，并记录履历。

专业词解释：部门跟随使用人表示资产的使用部门始终取当前员工所在部门。

### 14.122 权限变更审计

确认结果：超级管理员调整角色和权限不需要审批，但必须填写原因、二次确认，并永久保存变更前后权限。

专业词解释：权限审计用于查清权限由谁、在什么时间、因为什么原因发生变化。

### 14.123 日志保留时间

确认结果：资产履历、审批和权限变更永久保留；登录及安全日志保留 1 年；普通访问和运行日志保留 180 天。

专业词解释：日志保留策略按照记录的重要程度设置不同保存期限。

### 14.124 附件格式和大小

确认结果：普通附件单个最大 20MB，只允许 PDF、Word、Excel、JPG、PNG 和 HEIC；禁止可执行文件。盘点照片单张原文件最大 10MB。

专业词解释：文件白名单只接受明确允许的文件类型，用于降低恶意文件上传风险。

### 14.125 员工未确认领用

确认结果：员工未处理时领用单保持待确认，不自动通过或取消；资产管理员可以手动催办或取消，资产数据保持不变。

专业词解释：待确认状态表示领用流程尚未完成，资产仍保持原来的使用人和状态。

### 14.126 员工拒绝领用

确认结果：员工可以在飞书拒绝领用，但必须填写原因；资产保持原状态并通知管理员，需要修改后重新发起。

专业词解释：拒收用于记录员工没有收到设备或设备信息不正确。

### 14.127 退库发现设备损坏

确认结果：管理员仍然完成退库并解除员工责任，同时记录设备状况、照片和说明；需要维修时再单独发起维修。

专业词解释：退库与维修分离可以先完成资产交回，再处理设备故障。

### 14.128 公共资产退回闲置

确认结果：有权限的管理员在系统内直接退回公共资产，不走飞书；填写地点后清空公共使用对象并变为闲置，允许同一人确认。

专业词解释：公共资产停用表示设备退出公共使用但仍然可以再次投入使用。

### 14.129 维修费用记录

确认结果：维修费用和供应商选填；费用为人民币两位小数，允许零、不允许负数，并且不改变资产采购金额。

专业词解释：维修成本是单次维修支出，与资产原始采购金额分开保存。

### 14.130 报废金额和日期

确认结果：报废回收金额允许零、不允许负数并保留两位小数；报废日期默认为最终审批执行成功日期，超级管理员可填写原因后纠正。

专业词解释：处置回收金额是报废时实际收回的钱，不是资产损失金额。

### 14.131 标签 PDF 打印

确认结果：第一版生成 80mm x 30mm 标签 PDF，支持单个和批量生成，通过浏览器选择打印机，不开发专用打印机驱动。

专业词解释：浏览器打印可以兼容不同品牌打印机，专用驱动集成可以在后续有明确设备型号时再增加。

### 14.132 二维码详情权限

确认结果：扫码后必须登录，并按照本人资产、盘点任务、角色和数据范围显示内容；金额继续受字段权限保护。

专业词解释：扫码后鉴权可以防止知道二维码链接的人绕过系统权限查看资产信息。

### 14.133 登录会话有效时间

确认结果：登录会话最长 8 小时，连续 2 小时无操作后失效；飞书用户重新认证，本地管理员重新输入密码。

专业词解释：会话有效期控制登录状态可以持续多长时间，降低长期未退出账号被他人使用的风险。

### 14.134 敏感日志脱敏

确认结果：密码、飞书密钥、登录令牌和附件内容不得写入日志；手机号等敏感数据只显示部分内容。

专业词解释：日志脱敏是在保留排错信息的同时隐藏认证凭据和个人敏感数据。

### 14.135 资产分类编码不可修改

确认结果：分类编码创建后任何人都不能修改，分类名称和层级可以调整，已有资产编码保持不变。

专业词解释：稳定编码保证同一个分类不会因为改名而变成新的分类编号。

### 14.136 资产分类停用和删除

确认结果：已被资产或历史记录使用的分类不能删除，只能停用；从未使用且没有下级分类时，超级管理员可以删除。

专业词解释：引用检查用于保护历史资产和申请中的分类关系。

### 14.137 新增资产分类

确认结果：分类编码由有权限管理员手动填写并全局唯一；名称、默认使用期限、默认计量单位必填，非顶级分类还需选择上级分类。

专业词解释：分类主数据是新增资产时使用的标准分类资料。

### 14.138 公司编码不可修改

确认结果：公司编码被使用后不能修改；公司名称和层级变化不重新生成历史资产编码。

专业词解释：组织编码不可变可以保证资产编码在公司组织调整后继续稳定。

### 14.139 公共使用对象编码和名称

确认结果：公共对象编码由系统自动生成 `PUB` 流水号，名称必须唯一，同名地点需要增加办公室或楼层前缀。

专业词解释：公共对象去重可以避免在使用人选择列表中出现无法区分的相同名称。

### 14.140 公共使用对象停用

确认结果：已被使用的公共对象不能删除，只能停用；停用后不能新选，并生成相关资产的待退回或转移清单。

专业词解释：停用不删除可以保留历史资产使用关系。

### 14.141 资产责任管理员范围

确认结果：责任管理员只能选择飞书同步的在职真实员工，不要求拥有资产管理员角色；离职后生成待更换清单。

专业词解释：业务责任人负责具体资产，不等于拥有系统管理权限。

### 14.142 资产照片数量和封面

确认结果：资产照片选填，每件最多 10 张，可设置一张封面；单张最大 10MB，支持 JPG、PNG 和 HEIC并自动压缩。

专业词解释：封面照片是资产列表和详情默认显示的主图。

### 14.143 附件作废和照片删除

确认结果：合同、发票、验收、维修和报废附件不能彻底删除，只能作废并上传替代版本；普通资产照片可删除但必须记录日志。

专业词解释：附件版本留痕可以保留错误文件和替代文件之间的历史关系。

### 14.144 临时导出文件有效期

确认结果：Excel、盘点报告和批量标签文件保留 7 天后自动删除，需要时重新生成；业务数据和导出日志不删除。

专业词解释：临时导出文件过期可以减少服务器空间占用和敏感文件长期存放风险。

### 14.145 首页数据看板

确认结果：首页显示资产状态数量、待审批、盘点进度、待补充资料和离职人员名下资产等核心统计。

专业词解释：数据看板用于进入系统后快速了解资产总体情况和待办事项。

### 14.146 系统左侧菜单

确认结果：菜单按资产台账、业务流程、盘点、审批、导入导出、基础资料、权限和日志等模块组织，并按权限显示。

专业词解释：功能导航只显示当前用户有权使用的系统入口。

### 14.147 资产列表默认字段

确认结果：默认显示编码、名称、分类、状态、使用人、部门、地点、责任管理员、所属公司和购入日期，金额默认隐藏。

专业词解释：默认列是用户首次进入资产列表时看到的主要信息。

### 14.148 个人列显示偏好

确认结果：用户可以保存个人显示列设置；没有金额权限的人不能选择金额列。

专业词解释：列偏好只影响当前用户的页面显示，不修改资产数据。

### 14.149 资产筛选和多编码匹配

确认结果：筛选条件增加资产编码，并支持一次输入多个资产编码进行精确匹配；其他筛选包括公司、分类、状态、使用人、部门、地点、责任管理员、供应商、来源、购入日期和完整状态。

系统处理方式：

- 多个资产编码可以使用换行、逗号或空格分隔。
- 每个编码按完整值精确匹配，不使用模糊查询。
- 重复输入自动去重。
- 查询后显示匹配数量和未匹配编码清单。

专业词解释：多编码精确匹配适合把 Excel 或消息中的一批资产编号直接粘贴查询，结果不会混入相似编码。

### 14.150 资产快速搜索

确认结果：一个搜索框支持按资产编码、名称、序列号、使用人和收货单号进行包含匹配。

专业词解释：模糊搜索只输入部分文字也能找到相关资产。

### 14.151 资产列表分页

确认结果：默认每页 50 条，可选择 20、50、100 条，并保存用户个人选择。

专业词解释：分页可以避免一次加载全部资产导致页面变慢。

### 14.152 资产详情标签页

确认结果：详情页包含基本信息、照片附件、主附资产、资产履历、维修、报废、盘点和相关审批标签页。

专业词解释：标签页把同一资产的不同类型资料分区展示。

### 14.153 跨页批量选择

确认结果：默认只选择当前页；用户主动选择全部筛选结果时显示总数并二次确认。

专业词解释：跨页选择可以对当前查询条件下的多页资产执行同一批量操作。

### 14.154 手机端功能范围

确认结果：员工手机端提供本人资产、扫码盘点、领用确认和退库；管理员手机端提供资产详情和盘点处理，复杂管理主要在电脑端完成。

专业词解释：移动端适配围绕现场和员工常用操作设计，不直接缩小复杂的电脑管理页面。

### 14.155 Python 和后端依赖版本

确认结果：使用 Python 3.12，并固定 FastAPI、SQLAlchemy 等依赖版本，统一测试后再升级。

专业词解释：固定依赖可以避免自动升级第三方组件导致系统突然不可用。

### 14.156 MySQL 版本和字符集

确认结果：优先使用 MySQL 8.4 LTS 和 utf8mb4，同时保持对公司已有 MySQL 8.0 的兼容。

专业词解释：utf8mb4 可以完整保存中文、字母和特殊字符，LTS 是长期维护版本。

### 14.157 Redis 版本

确认结果：使用 Redis 7，保存登录状态、回调去重、任务状态和接口限流等临时数据。

专业词解释：Redis 适合处理读取频繁、生命周期较短的临时状态。

### 14.158 前端构建环境

确认结果：使用 Node.js 22 LTS、Vue 3、TypeScript、Vite 和 Naive UI，并锁定前端依赖版本。

专业词解释：前端构建环境用于本地开发和生成正式可部署的网页文件。

### 14.159 Docker Compose 服务编排

确认结果：本地和内网使用 Docker Compose 编排 FastAPI、MySQL、Redis 和 Nginx，正式前端文件由 Nginx 提供。

专业词解释：服务编排可以用一套配置统一启动、停止和更新系统服务。

### 14.160 开发测试正式环境隔离

确认结果：开发、测试和正式环境使用独立配置、数据库和文件目录；密码和飞书密钥不提交到 Git。

专业词解释：环境隔离可以防止开发测试误操作正式公司数据。

### 14.161 Alembic 数据库迁移

确认结果：所有表结构变化通过 Alembic 脚本执行，正式迁移前先备份，禁止直接手工改正式数据库表。

专业词解释：数据库迁移脚本可以追踪每次结构变化并支持按顺序升级。

### 14.162 API 版本和统一响应

确认结果：接口使用 `/api/v1` 前缀，正常和错误响应统一返回 `code、message、data、request_id`。

专业词解释：API 版本可以在以后升级接口时保护已有前端和集成功能。

### 14.163 系统时区

确认结果：数据库保存 UTC 时间，页面、Excel 和报表按 `Asia/Shanghai` 北京时间显示。

专业词解释：统一时区可以避免日志、审批和飞书回调时间顺序混乱。

### 14.164 浏览器兼容范围

确认结果：电脑支持新版 Chrome 和 Edge；手机支持飞书内置浏览器、iPhone Safari 和主流 Android 浏览器；不支持 IE。

专业词解释：浏览器兼容范围用于明确开发测试必须覆盖哪些运行环境。

### 14.165 本地管理员密码策略

确认结果：本地管理员密码至少 12 位并包含大小写字母、数字和符号，首次登录必须修改，不能与最近 5 次密码相同。

专业词解释：密码策略用于降低简单密码和重复密码造成的账号风险。

### 14.166 登录失败锁定

确认结果：同一账号连续输错 5 次后锁定 15 分钟，锁定和解锁都记录安全日志。

专业词解释：登录锁定可以降低程序不断猜测密码的风险。

### 14.167 本地管理员密码重置

确认结果：正式员工使用飞书登录；本地超级管理员忘记密码时，只能登录内网服务器执行专用管理命令重置。

专业词解释：服务器重置要求具备服务器管理权限，不能通过公开登录页面随意重置超级管理员。

### 14.168 接口访问限流

确认结果：同一 IP 登录接口每分钟最多 10 次，普通接口同一用户每分钟最多 120 次，超出后提示稍后再试。

专业词解释：接口限流用于防止暴力登录、程序异常或误操作产生大量请求。

### 14.169 CORS 域名白名单

确认结果：正式环境只允许公司内网正式域名调用接口，本地开发允许 `localhost`，不开放任意网页来源。

专业词解释：CORS 白名单规定哪些网页地址可以调用后端接口。

### 14.170 飞书回调验证和去重

确认结果：飞书回调必须验证签名并解密，同一事件只处理一次，重复通知不能重复修改资产。

专业词解释：幂等处理可以保证重复回调不会产生重复领用、退库或审批记录。

### 14.171 服务健康检查

确认结果：提供存活和就绪检查，分别检查程序进程以及 MySQL、Redis和存储；Docker 在服务异常时自动重启。

专业词解释：健康检查用于自动判断系统是否能够正常接收和处理请求。

### 14.172 系统故障飞书告警

确认结果：备份失败、飞书同步失败或回调连续失败时，通过飞书通知超级管理员和指定系统管理员，并保留告警记录。

专业词解释：故障告警用于技术问题发生时及时通知维护人员，不属于审批或盘点提醒。

### 14.173 自动化测试范围

确认结果：资产编码、状态、权限、审批、导入和盘点需要单元及接口测试，电脑和手机关键流程需要浏览器自动化测试。

专业词解释：自动化测试可以在每次修改代码后重复检查旧功能是否仍然正常。

### 14.174 正式上线验收

确认结果：正式上线前在测试环境完成飞书、导入、标签打印、领用退库、手机盘点、权限和备份恢复测试，由业务负责人确认后上线。

专业词解释：上线验收是用真实业务场景确认系统达到正式使用条件。

### 14.175 历史数据基准文件

确认结果：正式迁移使用一份最终确认的资产 Excel 作为唯一基准文件，避免多个版本重复导入。

专业词解释：基准文件是正式迁移唯一认可的数据来源。

### 14.176 历史数据迁移演练

确认结果：正式上线前至少进行两次完整试导入，验证编码、字段、人员、公司、分类、数量和金额。

专业词解释：迁移演练是在测试环境提前执行完整导入流程。

### 14.177 历史资产状态映射

确认结果：历史状态只转换为闲置、在用、维修中和已报废，无法识别时整批校验失败，不自动猜测。

专业词解释：状态映射把旧数据状态转换为新系统标准状态。

### 14.178 正式迁移数据冻结

确认结果：最终导出旧数据后暂停旧系统和原 Excel 修改，紧急变化单独登记并在迁移后补录。

专业词解释：数据冻结用于防止迁移期间新旧数据继续产生差异。

### 14.179 迁移后数据对账

确认结果：按所属公司、分类和状态核对资产数量及采购金额，总数和金额一致后才通过迁移验收。

专业词解释：数据对账用于验证迁移前后没有漏导、重复或金额变化。

### 14.180 历史员工匹配

确认结果：优先按飞书用户 ID 或员工编号匹配，只有姓名唯一时才按姓名匹配；重名或无法匹配时整批失败。

专业词解释：人员映射用于把旧资产使用人准确关联到飞书真实员工。

### 14.181 公司和分类主数据校验

确认结果：历史资产中的公司编码和分类编码必须已经存在，匹配失败时整批导入失败，不能临时创建或留空。

专业词解释：主数据校验保证每件资产引用经过确认的公司和分类编码。

### 14.182 历史资产标签处理

确认结果：资产编码不变时继续使用旧标签，不强制全部重印；标签损坏或内容不完整时再补打。

专业词解释：标签平滑迁移可以减少上线时一次性重贴全部资产的工作。

### 14.183 上线回退准备

确认结果：正式迁移前备份旧数据和新系统空库，旧系统保留至少 30 天只读访问，严重问题时可以回退。

专业词解释：回退方案用于新系统发生重大故障时恢复上线前状态。

### 14.184 使用说明和培训

确认结果：提供管理员手册、员工领用退库说明、手机盘点说明和常见问题，上线前完成管理员实操培训。

专业词解释：用户培训用于确保实际使用人员掌握关键业务流程。

### 14.185 公司和分类编码导入入口

确认结果：系统提供独立的公司编码导入和资产分类编码导入页面、模板、预览、错误报告和确认功能，完整沿用原有编码体系。

系统处理方式：

- 公司和分类编码均按字符串保存，不重新生成。
- 通过上级编码建立公司和分类层级。
- 父级缺失、编码重复或形成循环层级时整批失败。
- 管理员确认后整批写入，全部成功或全部失败。
- 公司和分类导入完成后，才能正式导入历史资产。

专业词解释：基础资料导入入口用于先建立原有公司和分类编码体系，再让资产台账准确引用这些标准编码。

### 14.186 已存在公司编码更新

确认结果：再次导入相同公司编码时不新增记录，预览名称、上级公司和状态差异后更新。

专业词解释：按编码更新使用不可变编码识别同一家公司，只修改可维护资料。

### 14.187 已存在分类编码更新

确认结果：相同分类编码可以更新名称、上级分类、使用期限、默认单位和状态，但不能修改编码。

专业词解释：主数据更新不会改变已经参与资产编码生成的分类编号。

### 14.188 公司和分类更新留痕

确认结果：每次导入更新都保存修改前后值、导入任务编号、操作人和时间。

专业词解释：主数据版本记录可以还原公司和分类资料的历史变化。

### 14.189 顶级编码父级规则

确认结果：顶级公司和顶级分类的上级编码允许为空，非顶级记录必须填写有效上级编码。

专业词解释：根节点是层级树最上层的数据，不需要父级。

### 14.190 编码按文本读取

确认结果：公司和分类编码在 Excel、数据库和接口中都按文本处理，保留前导零和字母。

专业词解释：文本编码可以防止 Excel 把 `00101` 自动转换成 `101`。

### 14.191 基础数据增量导入

确认结果：只处理本次文件中出现的编码，文件中没有出现的现有公司和分类保持不变。

专业词解释：增量导入不会因为某行未放入当前文件就停用或删除已有数据。

### 14.192 文件内重复编码校验

确认结果：同一 Excel 中出现两行相同编码时整批失败，并显示全部重复行号。

专业词解释：文件内唯一校验保证一批数据中每个编码只有一个明确版本。

### 14.193 基础数据导入自助确认

确认结果：拥有导入权限的管理员可以上传并自己确认，不需要另一人审批，但必须预览差异和二次确认。

专业词解释：导入确认是在正式写入前由操作人核对新增、更新和错误数量。

### 14.194 公司和分类可回导模板

确认结果：可以导出当前公司树和分类树，导出文件格式与更新导入模板一致，可以修改后重新上传。

专业词解释：可回导模板可以减少重新整理字段和层级的工作。

### 14.195 基础数据前向修正

确认结果：已完成的公司和分类导入不能一键撤销，错误通过下一次正确导入修复，已有资产编码不回退。

专业词解释：前向修正保留错误和修复的完整历史，不删除已经产生的业务记录。

### 14.196 仅开发响应式 Web

确认结果：第一版只开发电脑和手机适配的 Web 系统，不开发 iOS 或 Android 原生 App。

专业词解释：响应式 Web 使用同一个网址适配不同屏幕。

### 14.197 不支持离线盘点

确认结果：第一版盘点必须在线访问系统，离线时不能扫码提交或暂存到手机。

专业词解释：在线盘点可以立即校验任务、权限和重复扫码结果。

### 14.198 仅简体中文

确认结果：第一版系统界面、模板、报表和提示仅提供简体中文。

专业词解释：不做国际化可以减少第一版界面和字典维护工作。

### 14.199 仅人民币金额

确认结果：采购金额、维修费用和报废回收金额统一使用人民币，不做多币种和汇率换算。

专业词解释：单一币种可以保证金额统计口径一致。

### 14.200 第一版飞书集成边界

确认结果：飞书负责登录、组织同步、领用退库和盘点通知；转移、维修、报废、导入、异常处理和权限审批在资产系统内部完成。

专业词解释：集成边界用于明确两个系统分别负责哪些业务。

### 14.201 内网服务器基线

确认结果：正式服务器建议至少 4 核 CPU、8GB 内存和 300GB 数据盘，初期服务可以部署在同一台服务器。

专业词解释：服务器基线是当前规模下的最低建议配置。

### 14.202 备份独立存放

确认结果：正式备份保存到另一块磁盘、NAS 或其它服务器，不能只放在系统数据盘。

专业词解释：独立备份介质可以在系统磁盘损坏时继续保留备份。

### 14.203 容量设计目标

确认结果：数据库和接口按至少 5 万件资产、100 人同时在线设计，覆盖当前规模并预留增长空间。

专业词解释：容量余量可以减少业务增长后立即重构系统的风险。

### 14.204 文件存储演进

确认结果：本地开发和首台内网服务器使用本地目录，业务代码通过统一存储接口保留以后切换 MinIO 的能力。

专业词解释：存储适配层可以在不修改业务流程的情况下更换文件保存服务。

### 14.205 完整项目交付包

确认结果：交付源代码、Docker、数据库迁移、环境示例、导入模板、部署说明、用户手册、测试报告和上线验收清单。

专业词解释：完整交付包保证系统不仅能开发完成，也能部署、使用、维护和后续交接。

## 15. 确认完成后的设计顺序

核心需求确认阶段已经完成。后续按照下面顺序进入详细设计和开发：

1. 数据库表、字段、索引和表关系设计。
2. 资产、审批、盘点、导入和飞书状态机设计。
3. FastAPI 路由、Controller、Service、Repository 和 Schema 接口清单。
4. Vue 3 页面、菜单、权限按钮和手机端交互设计。
5. Excel 模板、标签 PDF 和飞书消息卡片样式设计。
6. Docker Compose、本地初始化、测试数据和开发说明。
7. 分阶段实现、自动化测试、迁移演练和上线验收。

详细设计过程中如果发现规则冲突，只补充确认受影响的小项，不重新推翻已经确认的整体方案。
