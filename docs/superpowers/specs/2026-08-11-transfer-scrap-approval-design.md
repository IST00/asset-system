# 转移与报废审批接入设计

日期：2026-08-11

状态：已确认，待实施计划

关联缺陷：`PILOT-009`

## 1. 背景

当前 `/api/v1/asset-actions/transfer` 和 `/api/v1/asset-actions/scrap` 在完成 Schema 校验后，直接调用 `asset_management_service.transfer()` 或 `asset_management_service.scrap()` 修改资产并提交事务。两个入口没有创建 `OperationRequest`、审批步骤、审批人快照或业务锁，因此绕过了系统已经具备的内部审批内核。

产品规则要求：

- 转移默认经过一层资产管理员内部审批，正式环境中申请人不能自审。
- 报废默认经过资产管理员和财务人员两层顺序审批，申请人不能自审。
- 审批完成前资产正式数据不得变化。
- 最终审批通过后，整单资产在一个事务中执行。
- 拒绝、撤回、执行失败、重试和终止必须保留完整记录并正确管理业务锁。

## 2. 本轮范围

本轮修复审批绕过，同时保持现有转移和报废表单业务字段不变。现有公开接口路径保持不变，但语义由“立即执行”改为“提交审批申请”。

本轮包含：

- 转移、报废申请提交服务。
- 专用申请明细模型和 Alembic 迁移。
- `TRANSFER`、`SCRAP` 操作处理器。
- 审批前不可变快照和整单业务锁。
- 最终审批通过后的事务执行。
- 拒绝、撤回、执行失败、重试和终止路径。
- 后端、前端和迁移回归测试。

本轮不包含：

- 报废证明附件。
- 用户在同一张申请中逐件输入不同回收金额。
- 用户为每个附属资产分别选择一起报废、解除关系或转挂。
- 附属资产转挂到另一台主资产。
- 报废日期自动取最终执行成功日期及超级管理员纠正流程。
- 转移字段与产品文档之间的其他业务差异调整。

上述未包含能力应独立登记、设计和实施，避免与审批内核接入相互耦合。

## 3. 方案选择

采用现有操作审批内核，并增加转移、报废专用申请明细和执行处理器。

不采用仅把全部参数写入 `OperationRequestAsset.target_data` 的轻量方案。该方案虽然无需新增业务表，但不利于查询、审计和后续扩展完整报废模型。

不采用暂时关闭接口的方案。关闭接口可以消除直接修改风险，但会让两项核心业务不可用，不能满足试运行目标。

## 4. 架构

调用链调整为：

```text
Blueprint
  -> transfer/scrap submission service
  -> OperationRequest + business detail + asset snapshots
  -> approval flow snapshot + approval tasks + business locks
  -> final approval
  -> operation_executor
  -> TransferHandler / ScrapHandler
  -> internal mutation primitive
  -> lifecycle records + operation logs
```

### 4.1 HTTP 边界

保留以下接口：

- `POST /api/v1/asset-actions/transfer`
- `POST /api/v1/asset-actions/scrap`

Blueprint 只负责 JWT、Schema load、调用提交服务和返回统一 `Result`。接口成功时返回统一的操作申请详情，状态初始为 `PENDING / NOT_STARTED`，不再返回已经修改的资产列表。

Schema 增加可选 `idempotency_key`。前端每次新的用户提交生成新键；同一次请求重试复用原键。

### 4.2 提交服务

新增独立服务模块，分别负责转移和报废提交。服务承担以下职责：

1. 校验 `asset:transfer` 或 `asset:scrap` 权限。
2. 校验资产数据范围、版本、状态和业务锁。
3. 校验目标组织、地点、管理员、使用人或公共使用对象。
4. 在提交阶段确定整单资产范围，包括直接附属资产。
5. 加载对应操作类型的已发布内部审批流。
6. 创建 `OperationRequest`、业务明细、资产快照、审批任务和业务锁。
7. 记录申请提交审计并提交事务。
8. 返回申请详情，不修改资产正式字段。

未发布审批流或任一层没有有效审批人时，提交失败并回滚所有申请数据和锁，不得降级为直接执行。

### 4.3 执行处理器

新增：

- `TransferHandler`，操作类型为 `TRANSFER`。
- `ScrapHandler`，操作类型为 `SCRAP`。

两个处理器注册到现有 `operation_handler_registry`，只能由 `operation_executor` 调用。

处理器包含两个阶段：

- `revalidate_for_execution()` 重新校验申请类型、审批状态、明细完整性、资产版本、资产状态、业务锁和主附关系。
- `execute()` 调用无内部提交的资产变更函数，写入资产履历和操作日志。

当前直接执行方法不得继续作为 Blueprint 可调用能力。内部变更函数不执行 `commit()` 或 `rollback()`，事务完全由 `operation_executor` 管理。

## 5. 数据模型

使用下一个可用 Alembic 版本新增以下表。迁移文件只新增 Schema、约束和索引，不修改已合入迁移。

### 5.1 `asset_transfer_requests`

一条记录对应一个 `OperationRequest`，包含：

- `id`
- `operation_request_id`，唯一外键
- 可空的目标组织、地点、管理员、使用人和公共使用对象外键
- 目标对象提交时快照
- `reason`
- `created_at`
- `updated_at`

目标快照用于保证用户、组织、地点或公共对象后续改名时，历史申请仍能还原提交内容。

### 5.2 `asset_scrap_requests`

一条记录对应一个 `OperationRequest`，包含：

- `id`
- `operation_request_id`，唯一外键
- `reason`
- `scrap_date`
- `created_at`
- `updated_at`

本轮保留当前接口提供的 `scrap_date` 语义。改为最终执行日期属于后续独立需求。

### 5.3 `asset_scrap_request_items`

每条记录关联一个 `OperationRequestAsset`，包含：

- `id`
- `operation_request_asset_id`，唯一外键
- `disposition`，值为 `SCRAP` 或 `DETACH`
- `scrap_amount`，`SCRAP` 时必填且非负，`DETACH` 时为空
- `created_at`
- `updated_at`

当前前端提供整单统一金额和统一子资产动作。提交服务负责把它们展开为逐资产明细，为后续逐件金额和逐件处置保留兼容结构。

### 5.4 通用快照

`OperationRequestAsset.before_data` 保存提交时的资产正式状态，`target_data` 保存用于统一申请详情展示的目标摘要。专用业务明细是执行依据，通用快照是审批展示和通用审计数据。

申请提交后，业务明细和快照均不可编辑。被拒绝或撤回后重新提交时创建新的申请，并使用新的幂等键。

## 6. 转移流程

1. 规范化并去重用户提交的资产和版本。
2. 加载资产并校验权限、状态、数据完整性和目标参数。
3. 对主资产查询直接附属资产，将它们加入同一申请、快照和业务锁。
4. 创建 `AssetTransferRequest`，为每项资产生成 `before_data` 和 `target_data`。
5. 使用 `OperationType.TRANSFER` 创建内部自动执行申请。
6. 按已发布流程固化审批步骤和审批人。
7. 最终审批通过后，处理器重新校验并整单应用目标字段。
8. 写入每项资产的转移履历、整单操作日志和执行记录。

多组织申请中，候选审批人必须具有整单所有资产的数据范围。只有部分资产范围的用户不能成为该申请的有效审批人。

## 7. 报废流程

1. 规范化并去重用户提交的资产和版本。
2. 加载资产并校验权限、状态、数据完整性和金额。
3. 查询主资产的直接附属资产并处理整单动作：
   - `BLOCK`：存在附属资产时拒绝提交。
   - `DETACH`：附属资产加入申请和锁，处置动作展开为 `DETACH`。
   - `SCRAP`：附属资产加入申请和锁，处置动作展开为 `SCRAP`。
4. 创建报废申请头、逐资产明细和通用快照。
5. 使用 `OperationType.SCRAP` 创建内部自动执行申请。
6. 按已发布流程固化审批步骤和审批人。
7. 第一层通过后只激活第二层，资产保持不变。
8. 最终层通过后，处理器在同一事务中执行关系解除和资产报废。
9. 写入每项资产履历、关系履历、整单操作日志和执行记录。

报废操作所有审批层均禁止申请人自审。审批任务接口仍需执行后端校验，不能依赖前端隐藏按钮。

## 8. 审批流规则

审批层数不写死在提交服务中，以已发布流程版本为准：

- 转移默认一层资产管理员审批。
- 报废默认两层顺序审批，第一层资产管理员，第二层财务人员。
- 正式环境中的转移流程默认禁止自审。
- 报废流程始终禁止自审。

迁移不自动发布流程。审批人和角色成员属于部署数据，自动发布可能在正式环境中固化错误人员。部署门禁必须检查：

- `TRANSFER` 已发布有效流程。
- `SCRAP` 已发布有效流程。
- 每一层均能解析出启用且覆盖整单数据范围的审批人。
- 报废流程没有允许自审的层级。

测试 fixture 建立确定的一层转移流程和两层报废流程。开发环境如需验证转移自审例外，应显式创建允许超级管理员自审的测试流程，不改变正式环境规则。

## 9. 状态与事务

### 9.1 提交

申请头、业务明细、通用快照、审批任务和业务锁在同一事务中提交。任一步骤失败时不得留下部分申请或孤立业务锁。

### 9.2 拒绝与撤回

拒绝或撤回后：

- 资产正式数据保持不变。
- 释放整单业务锁。
- 保留申请、审批任务、审批意见和撤回原因。

### 9.3 最终审批和执行

最终层通过后先保存审批完成状态，再由 `operation_executor` 触发执行。执行成功后：

- 整单资产变更生效。
- 执行记录标记成功。
- 释放整单业务锁。

### 9.4 执行失败

任一资产、关系或审计写入失败时，执行事务整体回滚。审批状态保持已通过，执行状态标记失败，锁继续保留。

管理员排除问题后可以重试原申请。重试前再次运行完整校验，不能修改已经审批过的内容。管理员终止失败执行时释放锁并保留终止记录。

接口只返回统一安全错误；原始异常和堆栈仅进入服务端日志。

## 10. 前端调整

现有表单业务字段保持不变，增加技术性幂等键。提交成功后的交互调整为：

- 显示“申请已提交，等待审批”。
- 不假定资产状态已经改变。
- 刷新申请或审批工作流数据。
- 防止按钮重复点击产生多个请求。

API 类型由立即执行结果改为操作申请详情。所有 HTTP 请求继续通过 `@/api/http`。

## 11. 测试设计

### 11.1 提交边界

- 转移、报废提交后资产字段和版本保持不变。
- 正确生成申请、业务明细、资产快照、审批任务和业务锁。
- 相同 `idempotency_key` 返回同一申请。
- 缺少流程、审批人、权限或数据范围时整单回滚。

### 11.2 审批规则

- 转移一层审批通过后执行。
- 报废第一层通过后不执行，第二层通过后执行。
- 报废申请人不能自审。
- 非当前审批人、越级审批和重复审批被拒绝。
- 拒绝、撤回后资产不变且锁释放。

### 11.3 执行和并发

- 最终通过后整单修改资产并生成履历、日志和执行记录。
- 资产版本、状态或主附关系漂移导致执行失败且无部分提交。
- 执行失败保留锁，重试成功或终止后释放锁。
- 并发审批和重复执行只有一个请求实际生效。

### 11.4 主附资产和数据范围

- 主资产转移自动包含直接附属资产。
- 报废 `BLOCK`、`DETACH`、`SCRAP` 覆盖正常和异常路径。
- 跨组织整单校验申请人和审批人的全部资产范围。

### 11.5 API、前端和迁移

- JWT、Schema、统一错误 envelope 和响应字段回归。
- 前端等待审批提示、类型和防重复提交测试。
- Alembic 升级、降级、唯一约束和外键测试。
- 后端 Ruff、格式检查、Mypy、全量 Pytest 和覆盖率。
- 前端 TypeScript、ESLint、Vitest 和生产构建。

## 12. 人工验收

至少完成以下人工场景：

1. 提交转移，确认审批前台账不变，一层通过后整单生效。
2. 提交报废，确认第一层通过后台账不变，第二层通过后整单生效。
3. 验证报废申请人无法处理自己的审批任务。
4. 验证拒绝和撤回后资产不变且可以重新发起申请。
5. 模拟执行失败，验证没有部分资产生效，并完成重试或终止。
6. 核对申请详情、审批记录、资产履历、操作日志和执行记录。

## 13. 完成标准

满足以下条件后，`PILOT-009` 可以进入复验：

- 两个公开接口不再直接修改资产。
- 转移和报废均使用已发布内部审批流。
- 审批前资产不变且业务锁生效。
- 报废顺序审批和禁止自审由后端验证。
- 最终审批后整单事务执行，无部分成功。
- 拒绝、撤回、失败、重试和终止状态符合本设计。
- 自动化质量门禁全部通过。
- 人工验收记录和缺陷登记表已更新。
