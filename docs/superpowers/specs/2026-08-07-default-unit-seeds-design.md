# 默认计量单位初始化修复设计

**日期：** 2026-08-07
**状态：** 对话设计已批准，等待书面规格复核
**分支：** `fix/default-unit-seeds`
**Alembic 基线：** `018_user_preferences`

## 1. 问题与根因

产品约定要求新环境默认提供“台、个、套、部、件、张、把”等常用计量单位，资产分类导入模板也固定使用 `TAI` 作为示例单位编码。

当前 `002_backend_foundation` 只创建 `units` 表，没有插入默认数据。新数据库迁移到最新版本后，`units` 仍为空，因此资产分类导入时，任何“默认计量单位编码”都会被判定为不存在或已停用。

## 2. 目标

- 新环境升级到最新 Alembic head 后具备可直接使用的默认计量单位。
- 已部署环境升级时补齐缺失的默认单位，不覆盖管理员已有数据。
- 下载的资产分类模板保留 `TAI` 示例，并能在完成初始化的数据库中通过单位校验。
- 当前文件使用的 `TAI`、`GE`、`GEN`、`BU` 均有明确且启用的字典项。

## 3. 非目标

- 不修改已经合入的 `002_backend_foundation` 迁移。
- 不放宽资产分类导入对默认单位必填、存在且启用的校验。
- 不在导入预览阶段自动创建计量单位。
- 不自动重写已经生成的失败导入任务；修复后需要重新上传原文件。
- 不改动前端页面或 HTTP 接口。

## 4. 方案选择

采用新增 `019_seed_default_units` 数据迁移的方案。

未采用的方案：

- 只在当前数据库手工新增：无法修复后续新环境。
- 应用启动时自动补数据：会把迁移职责变成隐式启动副作用。
- 修改 `002`：违反已合入迁移不可修改的仓库约定。

## 5. 默认数据契约

迁移补齐以下计量单位：

| 编码 | 名称 |
| --- | --- |
| `TAI` | 台 |
| `GE` | 个 |
| `GEN` | 根 |
| `TAO` | 套 |
| `BU` | 部 |
| `JIAN` | 件 |
| `ZHANG` | 张 |
| `BA` | 把 |

新插入记录统一使用：

- `status = ENABLED`
- `version = 1`
- `created_at` 与 `updated_at` 为迁移执行时间

## 6. 升级兼容与冲突处理

迁移按编码和名称检查现有数据：

- 相同编码且名称相同：保留现有记录，不修改状态、版本或时间。管理员已停用的单位不会被迁移重新启用。
- 编码不存在且名称不存在：插入默认记录。
- 编码已存在但名称不同，或名称已存在但编码不同：迁移明确失败并指出冲突项，不静默覆盖或创建重复语义。

检查和插入使用 Alembic/SQLAlchemy Core，不依赖运行时 model 或 service，兼容 SQLite 与 MySQL。

这是主数据迁移。`downgrade()` 不删除单位，避免升级后已有分类或资产引用这些单位时发生外键失败或业务数据损失；降级只回退版本标记，保留已经写入的主数据。

## 7. 数据流

1. Alembic 从 `018` 升级到 `019`。
2. `019` 校验现有单位编码和名称。
3. 无冲突时补齐缺失默认单位。
4. 用户重新上传资产分类文件。
5. 导入预览通过 `_rows_by_code(Unit)` 取得启用单位。
6. `TAI / GE / GEN / BU` 等编码解析为 `default_unit_id`，分类进入可确认状态。

## 8. 错误处理

- 迁移发现编码或名称冲突时立即失败，错误信息包含默认编码、默认名称和现有冲突值。
- 导入文件中单位编码为空、未知或已停用时，继续沿用现有业务错误，不改变用户可见规则。
- 旧的 `VALIDATION_FAILED` 任务保持不可确认，避免修改持久化预览快照。

## 9. 测试与验证

采用测试驱动实现：

1. 先新增迁移测试并验证其在没有 `019` 时失败。
2. 升级空的 `018` 数据库到 `019`，断言八个单位全部存在、启用且版本为 1。
3. 预置一个相同编码和名称的单位后执行迁移，断言不重复、不覆盖其状态或版本。
4. 构造编码冲突和名称冲突，断言迁移明确失败。
5. 在完成 `019` 的数据库中上传包含 `TAI` 的资产分类数据，断言不再出现“默认计量单位编码不存在或已停用”。
6. 运行后端 Ruff、格式检查、Mypy 和 Pytest。
7. 升级当前本地数据库，重新上传原资产分类文件并验证预览结果。

## 10. 发布与恢复

- 发布前备份数据库。
- 部署时执行标准 `flask db upgrade`。
- 迁移成功后无需重启外部依赖。
- 若迁移因冲突失败，管理员先确认已有单位编码/名称的真实语义，再修正冲突数据并重新升级。
- 回滚应用版本时保留默认单位数据；这些记录与 `018` 的表结构兼容。
