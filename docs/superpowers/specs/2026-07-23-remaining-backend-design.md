# 剩余后端建设总体设计

**日期：** 2026-07-23  
**状态：** 对话设计已批准，等待书面规格复核  
**开发分支：** feature/remaining-backend  
**当前基线：** main 498c2c3，Alembic head 005_asset_usage_return

## 1. 事实来源与决策优先级

本设计以 docs/product/资产系统建设方案.md 为业务事实源，其中第 14 章具体确认记录优先于前文概括性建议。

工程实现继续遵守当前仓库事实：

- 后端为 Flask 3、Python 3.13、SQLAlchemy 2、Alembic。
- 前端为 React 18，不切换 FastAPI、Vue 或其它框架。
- 不使用 Redis，不启动 Docker MySQL。
- 开发和真实验证使用用户提供的外部 MySQL 配置。
- API 依赖方向为 api → services → repositories → models → db。
- HTTP 业务接口只使用 GET 和 POST。
- Blueprint 不直接导入 models 或 db，不返回 SQLAlchemy model。
- 失败通过 BusinessException 和 ResultCode 进入统一响应。
- 已合入迁移不可修改，后续从 006 开始线性追加。

## 2. 当前基线

当前后端已经完成：

- Flask 应用工厂、配置、JWT、RBAC、组织和基础字典。
- 资产台账最小模型、编码生成、主附关系只读展开。
- 公共操作内核：申请、资产快照、业务锁、执行尝试、重试、终止、幂等、CAS、履历和审计。
- 公共审批内核：流程版本、多层审批、或签、会签、审批人快照、内部/飞书模拟/直接确认通道。
- 资产入库。
- 个人和公共领用、个人和公共退库。
- Alembic 001 至 005。

基线验证结果为 Ruff、format、mypy、guard 全通过，pytest 463 passed。真实 MySQL 尚未完成隔离 schema 的升降级验证；此前只完成 MySQL 方言 DDL 编译。

## 3. 目标

在不建立通用低代码平台、不引入 Redis、不过度抽象的前提下，完成以下剩余后端：

1. 资产资料共享扩展。
2. 本地文件存储和附件。
3. 资产使用转移。
4. 资产维修。
5. 资产报废。
6. 单件和批量资产编辑及变更预览。
7. Excel 公司、分类、资产导入与业务导出。
8. 二维码、条形码和 80mm × 30mm 标签 PDF。
9. 完整资产盘点。
10. 真实飞书 SSO、组织同步、回调和通知。
11. Flask/Gunicorn、Nginx、外部 MySQL、备份恢复及上线验收能力。

## 4. 非目标

- 不建设 BPMN、规则引擎、通用 CRUD 生成器或插件自动发现框架。
- 不引入 Redis、消息队列或必须常驻的 Celery worker。
- 不开发打印机厂商驱动。
- 不实现离线盘点。
- 不实现 RFID。
- 不实现多币种、折旧、到期提醒或自动报废。
- 不允许通过导入覆盖既有资产。
- 不把盘点任务强行建模成普通审批申请。
- 不把所有业务附件放进无法保证外键完整性的通用 source_type/source_id 表。

## 5. 方案选择

### 5.1 已选择：按依赖顺序分阶段纵切

每个阶段交付可运行、可迁移、可测试的软件。阶段内部只有真正独立的叶子模块并行，公共注册、权限、迁移和共享模型由主线程串行集成。

优点：

- 每次变更范围可控，容易定位回归。
- 迁移保持单一 head。
- 每个阶段都能执行六维独立审查。
- 公共抽象只在已经出现两个消费者时建立。

### 5.2 未选择：先建设完整横向平台

先建设通用文件、任务、报表、导入和集成平台会推迟业务验证，并容易生成当前用不到的扩展点。

### 5.3 未选择：全部功能在一个巨型批次并行

该方式会使模型聚合、权限种子、Handler 注册和 Alembic 迁移集中冲突，也难以回滚或进行可靠审查。

## 6. 总体架构与依赖顺序

依赖顺序如下：

    资产资料扩展
      ├── 文件存储与附件
      ├── 使用转移 / 维修 / 报废
      ├── 批量编辑
      └── Excel 导入导出 / 标签
                └── 盘点
                      └── 真实飞书通知与组织同步
                            └── 生产部署、备份恢复和上线验收

实施分为六批：

1. 共享资产资料与文件底座。
2. 使用转移、维修、报废和批量编辑。
3. Excel 导入导出及标签。
4. 盘点任务、扫码、复核和报告。
5. 真实飞书。
6. 生产交付和最终验收。

其中使用转移可在共享资产字段冻结后与文件底座并行开发；报废必须等待附件契约和主附关系写入契约冻结。

## 7. 共享资产资料扩展

### 7.1 资产字段

新增或补齐：

- Supplier 主数据及不可变供应商编码。
- supplier_id。
- service_life_months 和 expected_expiry_date。
- custom_attributes JSON。
- data_completeness，取 COMPLETE 或 INCOMPLETE。
- 历史导入原始值通过导入明细保存，不覆盖标准字段。

为兼容历史 Excel，unit_id、source_id 和 location_id 在数据库层改为可空；页面单个新增和普通入库仍由 Service 强制必填。

不在 Asset 表重复保存以下派生数据：

- 二维码和条形码图片。
- 维修历史。
- 报废回收金额和审批历史。
- 最近盘点明细。

这些数据由显式业务表保存并按需查询。

### 7.2 数据完整度

历史导入中来源、单位或地点为空、或原始文字无法匹配时，资产可以入库但标记 INCOMPLETE。原始文字保留在导入明细。

asset:data:complete 只允许把空标准字段首次补齐，不允许借此覆盖已有值。补齐后重新计算完整度，并写每件资产履历和整批操作日志。

### 7.3 编码占用

现有 AssetCodeReservation 与 StockInItem 强耦合。扩展为可以分别关联入库明细或资产导入明细，但一条占用只能归属于一种来源。

编码规则保持：

- 用户提供的历史编码校验唯一后沿用。
- 缺失编码在整批校验通过后统一占用并进入预览。
- 取消、拒绝或撤回后编码永久 VOID，不复用。
- 正式确认只激活原占用，不重新生成编码。

## 8. 文件存储与附件

### 8.1 存储端口

业务层只依赖 StorageProvider：

- save：保存流并返回不透明 storage_key。
- open：按 storage_key 返回受控文件流。
- delete：仅物理删除已允许清理的对象。
- exists：用于健康检查和恢复验证。

第一版提供 LocalStorageProvider，根目录由 STORAGE_LOCAL_ROOT 配置，默认位于 back/storage。数据库不保存绝对路径或公开 URL。

未来 MinIO 只新增 Provider，不修改资产、维修、报废、盘点或导入 Service。

### 8.2 文件元数据

StoredFile 保存：

- storage_key。
- 原始文件名和受控显示名。
- 扩展名、检测出的 MIME、大小和 SHA-256。
- 上传人、上传时间、存储 Provider。
- 临时文件过期时间、物理删除时间和安全状态。

业务关联使用显式外键模型：

- AssetAttachment。
- RepairAttachment。
- ScrapAttachment。
- InventoryResultPhoto。
- ImportTask 输入和错误报告文件。
- GeneratedArtifact 导出、标签和盘点报告。

### 8.3 上传与删除规则

- 普通附件单文件最大 20MB。
- 盘点照片原文件最大 10MB。
- 允许 PDF、Word、Excel、JPG、PNG 和 HEIC。
- 同时校验扩展名和真实文件特征。
- 文件使用随机 storage_key，原始文件名不能参与服务器路径拼接。
- storage 目录不由 Nginx 或 Flask 静态路由直接公开。
- 下载前必须校验 JWT、功能权限和资产/任务数据范围。
- 资产照片每件最多 10 张；没有显式封面时最早有效照片为封面。
- 合同、发票、验收、维修和报废附件只能作废并上传替代版本。
- 普通资产照片可以删除，但必须留下操作日志和元数据删除标记。
- 导出、盘点报告和标签等临时文件保存 7 天，CLI 清理后保留生成与清理日志。

盘点照片使用 Pillow 和 pillow-heif 解码，按任务要求压缩到约 2MB，并加入任务名称、资产编码、提交人和提交时间水印；不采集 GPS。

## 9. 资产使用转移

业务名称统一为“使用转移”，避免被误解为改变资产所有权。

### 9.1 状态与目标

- IDLE 资产只能调整地点和责任管理员；把闲置资产交给个人或公共对象必须走领用。
- IN_USE 资产保持 IN_USE，可以变更个人使用人、公共使用对象、自动解析的使用部门、地点和责任管理员。
- organization_id 和 asset_code 永远不变。
- 个人使用目标必须是启用用户并解析出使用部门。
- 公共使用目标必须是启用公共对象。

### 9.2 主附资产

选择主资产时自动包含全部直接附属资产。附属资产同步使用对象、部门和地点，但保留自己的所属公司和资产编码。

仍挂接的附属资产不能单独转移；需要单独处理时先通过关系维护解除或转挂。

### 9.3 审批与执行

- operation_type 为 TRANSFER。
- approval_channel 为 INTERNAL。
- 默认一层资产管理员或签。
- 正式环境禁止申请人自审。
- 多资产逐件校验权限、状态、业务锁和版本。
- 申请、功能明细、资产快照和业务锁同事务创建。
- 审批通过后整单 CAS，全部成功或全部回滚。

## 10. 资产维修

### 10.1 模型

RepairOrder 关联开始维修的 OperationRequest，并保存供应商、送修时间、开始人、完成 OperationRequest、完成时间和确认人。

RepairItem 每件保存：

- asset_id 和申请快照关联。
- before_status。
- 故障描述。
- 可选维修费用，人民币两位小数，可为 0，不得为负。
- 完成结果和备注。

供应商属于整单统一业务参数，费用按资产明细保存并汇总。

### 10.2 状态流

    IDLE 或 IN_USE
      -> 管理员直接开始维修
      -> REPAIRING
      -> 管理员确认完成
      -> 每件恢复自己的 before_status

- 开始维修和完成维修分别使用 REPAIR_START、REPAIR_COMPLETE。
- 两个操作均为 DIRECT，允许同一管理员开始和完成。
- 开始时故障描述必填，送修时间默认当前时间。
- 完成时结果必填，完成时间默认当前时间。
- 开始维修只把状态改为 REPAIRING，使用人、公共对象、使用部门和地点继续保留；完成时只恢复每件资产自己的 before_status。
- 主资产维修只展示附属资产，默认不自动选中；只有显式选择的资产进入同一维修单。
- 主附关系在维修期间不改变。
- 无法修复时可以发起报废；报废执行成功后维修单以 SCRAPPED 结案，不能再完成维修。

## 11. 资产报废

### 11.1 审批

- 新增 operation_type SCRAP。
- 使用 INTERNAL。
- 默认第 1 层 ASSET_ADMIN，第 2 层 FINANCE，均按角色和数据范围解析审批人。
- 申请人不能审批自己提交的报废申请。
- 任一层没有有效审批人时禁止提交。

### 11.2 数据

ScrapRequest 保存申请级原因、说明和证明附件。

ScrapItem 每件保存：

- 回收金额，人民币两位小数，允许 0，不得为负。
- 报废原因和备注。
- 最终报废日期，默认执行成功日期。
- 主附处置类型。

报废金额和日期保存在显式报废明细，不在 Asset 表重复保存；台账和导出通过关联查询。

### 11.3 主附处置

报废主资产前，每件直接附属资产必须选择：

- SCRAP_TOGETHER：一起报废。
- DETACH：解除关系，保留当时的状态、使用人、部门和地点。
- REPARENT：转挂到另一台有效主资产，并按主附关系规则同步使用人、部门和地点。

缺少任一处置时不能提交。新主资产必须非报废、没有多层或循环关系，并保存版本快照；执行期重新加行锁并校验版本。

单独报废附属资产必须先显式解除关系，再作为普通资产申请。

主资产报废、子资产报废、解除或转挂在同一执行事务内完成。

## 12. 主附关系写入契约

现有关系 Service 只有只读展开能力。新增窄化写接口：

- attach。
- detach。
- reparent。

接口必须：

- 同时校验主、附资产数据范围。
- 按资产 ID 排序取得行锁。
- 拒绝报废资产、循环和多层关系。
- 拒绝附属资产存在未完成业务锁。
- 挂接或转挂时同步附属资产使用人、部门、地点和当时状态。
- 解除时保留附属资产当前业务字段。
- 使用专门的关系 CAS，不把 parent_asset_id 粗放加入任意字段更新白名单。
- 主资产和附属资产分别写履历，并共用一个关系操作号。

## 13. 单件和批量资产编辑

### 13.1 普通编辑

资产编码永不可修改。可编辑字段按基础权限、字段权限和数据范围组合校验。

状态、使用人、使用部门和已有地点默认不进入普通编辑；超级管理员或获得显式纠正权限的角色可以带原因直接纠正，但仍必须满足资产状态一致性。

### 13.2 批量预览

BatchUpdateDraft 保存：

- 操作人。
- 规范化变更字段。
- 选中资产或查询条件快照。
- 每件资产 ID、版本和字段前值。
- 影响数量、过期时间和确认状态。

普通批量编辑只处理明确选中的资产，不自动展开主附资产。

允许字段包括名称、分类、规格、单位、来源、供应商、责任管理员、购入日期、备注、自定义属性和金额。金额还需要 asset:amount:update。

资产编码、使用人、使用部门、状态和已有地点禁止进入普通批量编辑。

确认时重新校验权限、数据范围和每件资产版本，按 ID 取行锁并整批提交。任一版本变化或权限变化都使草稿失效并要求重新预览。每件写履历，整批共用一个批次号。

## 14. Excel 导入导出

### 14.1 两类导入

主数据导入和资产导入是两个独立流程。

公司/分类主数据导入：

- 模板下载、上传、校验、预览、错误报告和二次确认。
- 拥有对应权限的上传人可以自己确认，不走审批。
- 编码按字符串处理并保留前导零。
- 同编码更新名称、父级和允许字段，不创建重复记录。
- 顶级父编码可空；非顶级父编码必须存在于数据库或同一文件。
- 重复编码、缺父级和循环层级使整批失败。
- 文件未出现的既有记录保持不变。
- 已完成导入不能撤销，只能通过下一批前向修正。

资产导入：

- 只允许新增，不覆盖既有资产。
- 上传后只创建 ImportTask 和 ImportItem，不直接写资产表。
- 预览确认后生成 INTERNAL 资产导入申请。
- 默认使用一层 ASSET_ADMIN 或签，且该层禁止申请人自审。
- 申请人不能审批自己的资产导入。
- 审批通过后整批原子写入资产、编码激活、履历和审计。

### 14.2 资产导入校验

- 任一错误使整批不可确认。
- 错误报告包含行号、资产标识、字段、原值和原因。
- 历史状态只接受 IDLE、IN_USE、REPAIRING、SCRAPPED 的明确映射。
- 公司和分类必须已经存在。
- 人员优先按飞书用户 ID 或员工编号匹配；只有姓名唯一时才按姓名匹配。
- 重名或无法匹配使整批失败。
- 序列号忽略大小写和首尾空格后全局唯一，覆盖正式资产、待入库、待确认导入和报废资产。
- Supplier 未匹配时是阻断错误；有 supplier:create 权限的人员可以在预览中补建后重新校验。
- 来源、单位、地点为空或无法匹配时产生警告，正式值为空、原始文字保留，资产标记 INCOMPLETE。

### 14.3 导出

支持台账、当前筛选、员工名下资产、维修、报废和盘点报告导出。

- 必须有对应导出权限。
- 查询必须在 SQL 层应用数据范围。
- 没有 asset:amount:view 时工作簿不包含金额列，而不是输出空值或掩码列。
- 保存导出人、时间、筛选条件、文件名和过期时间。
- 与明确资产集合相关的导出为每件资产写入 EXPORT 履历。
- 输出北京时间。

第一版同步生成文件；任务表仍记录 PENDING、PROCESSING、SUCCESS、FAILED，便于将来替换执行方式，但不引入通用队列。

## 15. 标签、二维码和条形码

- 条形码使用 Code128，内容为不可变资产编码。
- 二维码内容为配置的移动端资产详情 URL。
- 二维码和条形码按需生成，不在 Asset 表保存图片。
- 标签尺寸为 80mm × 30mm。
- 固定抬头为“上海黄豆网络科技有限公司”。
- 标签包含资产编码、资产名称、设备序列号、二维码和条形码；序列号为空时隐藏该行。
- 支持单个和批量 PDF。
- 浏览器负责选择打印机，不开发专用驱动。
- PDF 使用可部署的中文字体资源，不能依赖开发机系统字体。
- 标签文件保存 7 天。
- 生成和下载均写操作日志。

扫码详情必须登录，并按本人资产、当前盘点任务权限或角色数据范围返回。金额继续受 asset:amount:view 控制。

## 16. 资产盘点

### 16.1 独立任务状态

InventoryTask 状态：

- DRAFT。
- IN_PROGRESS。
- REVIEWING。
- COMPLETED。
- CANCELLED。

逾期根据当前时间、截止时间和 IN_PROGRESS 动态计算，不保存容易失真的 OVERDUE 状态。

发布任务时固定：

- 资产范围快照。
- 使用人、公共资产责任人和盘点管理员。
- 照片来源模式。
- 每件最少照片数。
- 截止时间。

范围错误必须取消后重建，不修改已发布快照。

### 16.2 权限与分配

- SUPER_ADMIN 和 ASSET_ADMIN 默认可创建。
- 其它角色需要 inventory:create。
- 每个任务至少一名盘点管理员。
- 任意在职真实员工可被指定为任务管理员，但只获得该任务的管理权限。
- 个人资产按任务发布时的使用人分配。
- 公共资产按地点分组给一名或多名真实员工。
- 责任转交不修改资产台账使用人，并保存前后人员、原因和通知结果。

### 16.3 扫码与结果

结果分三个独立维度保存：

- 实物结果：FOUND、LOSS、SURPLUS、UNSUBMITTED、EXEMPTED。
- 地点结果：MATCHED、DIFFERENT、TEMPORARY、NOT_APPLICABLE。
- 复核状态：DRAFT、AUTO_CONFIRMED、PENDING_REVIEW、RETURNED、CONFIRMED、VOID。

FOUND 必须来自二维码或条形码真实扫描。员工不能手输编码或仅点击清单完成。

FOUND 必须提交标准地点或临时地点，并满足任务的照片数量。正常结果自动确认；LOSS、地点差异、临时地点、任务外资产和未知编码进入异常复核。

主资产和每件附属资产必须分别扫码。扫描不建立、解除或修复主附关系。

同一任务同一资产第一条合法提交成为有效结果，后续扫码记录仍保存但不重复计数。

管理员可以直接标记任务内资产为 FOUND，但必须填写原因，且报告中与真实扫码分开统计。

系统未知编码只保存原始扫码、人员、时间、地点和可选照片，不自动创建资产。

### 16.4 任务结束和异常处理

结束收集后进入 REVIEWING：

- 未提交资产先标记 UNSUBMITTED，不自动盘亏。
- 管理员可以转 LOSS，必须选择原因；或转 EXEMPTED，必须填写原因。
- 可按人员或资产局部重新开放并设置新截止时间。

盘点事实采集不修改台账，也不占 asset_business_locks。

异常处理遵循窄化规则：

- 地点差异可创建 INVENTORY_LOCATION_ADJUSTMENT，复用操作内核和 CAS。
- 盘亏只记录复核结论；后续维修、使用转移或报废走对应正式流程。
- 任务外但系统已存在的资产只建立盘点异常关联。
- 未知资产需要进入正式入库或资产导入，不能在盘点中直接补资产。
- 如果资产存在业务锁或版本已变化，异常执行保持待处理并返回确定冲突原因，不能覆盖当前业务。

全部异常都有明确处理决定后才能 COMPLETED。完成后不可重新开放。

### 16.5 报告

最终 Excel 至少包含：

- 汇总。
- 资产明细。
- 盘亏。
- 地点差异。
- 临时地点。
- 未完成。
- 无需盘点。
- 管理员代确认。
- 人员完成情况。

照片以鉴权下载链接引用。没有 asset:amount:view 时报告不含金额。

## 17. 真实飞书

### 17.1 适配边界

业务 Service 不直接调用 httpx。新增：

- FeishuIdentityClient。
- FeishuContactClient。
- FeishuApprovalClient。
- FeishuNotificationClient。
- FeishuCallbackVerifier。

本地模拟 Provider 保留用于开发和自动化测试，生产 Profile 永不注册模拟路由。

### 17.2 SSO 与会话

- 正式员工通过飞书 OAuth 登录。
- 本地超级管理员保留为应急账号。
- User 保存飞书用户 ID、员工编号和同步状态。
- Organization 保存飞书部门 ID 和同步来源。
- FEISHU_ROOT_ORGANIZATION_ID 把飞书租户根部门映射到一个已存在的本地组织根；同步只维护该根下来源为 FEISHU 的部门节点，不覆盖本地公司编码和资产所属公司。
- 员工使用飞书标记的主部门作为 User.organization_id；缺少唯一主部门时保留原值、记录同步错误并要求管理员处理，不按名称猜测。
- SSO 只允许已经同步且启用的员工登录；未知飞书身份先执行组织同步，登录回调不静默创建缺少组织关系的用户。
- JWT 包含数据库会话 ID。
- LoginSession 保存签发、最后活动、绝对过期和撤销状态。
- 会话最长 8 小时，连续 2 小时无活动失效。
- 无 Redis；请求校验数据库会话，最后活动时间最多每 5 分钟刷新一次，避免每个请求都写数据库。

### 17.3 组织同步

- 支持管理员手动同步和 Flask CLI 定时同步。
- 部署层使用 cron 或 systemd timer 每天凌晨触发。
- 同步任务保存状态、进度、错误摘要和重试记录。
- 不物理删除历史人员或部门。
- 离职或停用员工立即禁止登录，并生成名下资产和任务交接清单。
- 员工部门变化后更新其个人在用资产的 usage_department_id，不改 organization_id 和资产编码，并逐件写履历。

### 17.4 回调

- 先验证签名、verification token 和时间窗口，再解密。
- 以飞书事件 ID 数据库唯一约束去重。
- 重复事件返回成功，但不重复修改审批、资产或履历。
- 只保存必要的脱敏事件摘要；密钥、令牌和完整敏感正文不写日志。

第一版飞书只负责登录、组织同步、领用退库真实事件、盘点发布通知和手动催办。使用转移、维修、报废、导入和盘点异常继续在资产系统内部完成。

## 18. API 设计

路由按领域分开：

- /api/v1/asset-transfer-requests。
- /api/v1/repair-orders。
- /api/v1/scrap-requests。
- /api/v1/asset-attachments。
- /api/v1/asset-batch-update-drafts。
- /api/v1/import-tasks。
- /api/v1/exports。
- /api/v1/labels。
- /api/v1/inventory-tasks。
- /api/v1/integrations/feishu。

查询使用 GET；创建、修改、删除语义和业务动作统一使用 POST。动作路径使用 submit、confirm、cancel、complete、invalidate、replace、publish、finish-collection、reopen、urge 等明确动词。

Blueprint 只负责：

- Marshmallow load/dump。
- jwt_required。
- current_user_id。
- 调用一个 Service 用例。
- 返回 Result。

所有列表使用 SQL 级数据范围过滤和分页。禁止先加载全量数据再在 Python 中过滤。

## 20. 错误、安全和日志

- Schema 处理输入格式错误。
- Service 处理权限、数据范围、状态、业务锁、版本和字段组合。
- 可预期失败抛 BusinessException(ResultCode.X)。
- 并发冲突、预览过期和版本变化返回可操作的业务提示。
- Executor 失败时审批状态不回退，资产事务回滚，业务锁保留，记录脱敏失败尝试。
- SQL、数据库地址、外部响应正文、堆栈、令牌和文件内容不得返回客户端。
- 未知异常统一返回固定内部错误提示，不返回 str(exception)。
- CORS 只声明 GET、POST 和 OPTIONS。
- 密码、飞书密钥、JWT、数据库凭据和附件内容不写日志。
- 下载响应使用安全 Content-Disposition，并禁止 MIME 嗅探。
- 登录失败锁定和 API 入口限流不依赖 Redis：本地管理员失败次数写数据库，HTTP 突发限流由 Nginx 执行。

修改 register_error_handlers、JWT 回调、CORS 或 requirements.txt 属于脚手架公共变更，必须使用独立提交并标记 scaffolding，不能混入业务提交。

如果已跟踪环境文件包含真实凭据，功能开发期间不在输出中展示；正式交付前必须改为部署环境或 ENV_FILE 注入并完成凭据轮换。该动作需要用户明确确认，不能擅自替换现有开发连接。

## 22. 迁移和多 Agent 边界

### 22.1 迁移

- 006 先补共享资产资料和编码占用契约。
- 007 建立存储元数据和附件契约。

- 每个迁移都提供可靠 downgrade，按外键依赖逆序删除。
- 每版执行 SQLite upgrade → downgrade → upgrade、flask db check 和 MySQL 方言编译。

### 22.2 主线程独占

- app/__init__.py、Blueprint 和 Handler 注册。

### 22.3 功能 Agent 边界

## 23. TDD、验证和审查

每个子项目必须：

1. 先写最小失败测试。
2. 运行并确认测试因缺少目标行为而 RED。
3. 写最小生产实现。
4. 运行聚焦测试变 GREEN。
5. 运行相关回归。
6. 集成后运行 Ruff、format、mypy、全量 pytest 和 convention guard。

专项验证包括：

- 迁移 SQLite 往返和 MySQL DDL。
- 使用转移、维修、报废的锁、CAS、幂等和整单回滚。
- Excel 生成后重新读取，验证单元格类型、前导零、金额和错误报告。
- 标签 PDF 页面尺寸严格为 80mm × 30mm，二维码和 Code128 可解码。
- 附件扩展名伪装、路径穿越、超限、越权下载、作废和替代。
- 盘点重复扫码并发、任务外资产、未知编码、照片、局部重开和异常冲突。
- 飞书重复回调、错误签名、同步重试、离职和部门变化。
- 实际 Flask 进程的登录、正式路由、文件流和业务闭环 smoke。

每批集成后启动独立只读审查线程，从以下六方面验证：

1. 需求完整性。
2. 逻辑正确性。
3. 边界情况。
4. 代码质量。
5. 测试覆盖。
6. 实际运行结果。

审查线程不得直接修改代码，只返回修复清单。主线程修复后交给同一审查线程复验，循环至 PASS；如果受到真实飞书、证书、打印机、备份介质或服务器阻塞，必须列出具体未验证项和解除条件。

## 24. 生产交付

- Flask 由 Gunicorn 运行。
- Nginx 提供 HTTPS、前端静态文件和 /api 反向代理。
- MySQL 使用外部配置，不在 Docker Compose 启动。
- 无 Redis 健康检查或配置。
- ready 检查数据库和必要存储目录，live 只检查进程。
- 数据库和业务文件使用同一备份批次号。
- 每日备份、保留 30 天，并保存到另一磁盘、NAS 或服务器。
- 提供备份创建、校验、恢复和恢复验证 CLI。
- 每月恢复演练需要在隔离环境实际执行并保存记录。
- 告警覆盖备份失败、飞书同步失败和回调连续失败，内容必须脱敏。

最终验收包括真实飞书、历史导入、错误报告、80mm × 30mm 实机打印、领退、手机扫码拍照、权限和金额保护、真实 MySQL 迁移以及备份恢复。
